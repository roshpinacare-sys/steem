## 1. Executive Summary

The v8.0 SRS Runtime **mostly works** for a real user. The core workflow (run a task, persist state, recover state, self-improve on second run) is functional and honest. Concurrency (10 threads × 10 tasks = 100 tasks, all correct) is rock-solid. The benchmark completes and reports honest numbers. The 252-test pytest suite passes in 3.33s.

However, the acceptance test surfaced **two genuine crashes** (uncaught Python tracebacks on `execute identify 0` and `execute identify 64 --budget -1`), **one partial self-improvement gap** (only `identify`/`identify_hard` seed advice; `search`/`optimize`/`compute`/`amortize`/`store` do not), **one CLI blind-spot** (interrupted tasks are invisible to the `recover` command when no snapshot exists, and the CLI exposes no `resume` subcommand at all), and **several cosmetic frictions** (bench header says "v7.2" while the runtime is v8.0.0; bench writes `benchmark_results.json` into the project root instead of the runtime home; capabilities dict key names diverge from the human-format labels).

None of these issues are catastrophic. All are fixable in a single polish pass. The runtime can be accepted for production use **with minor issues** that should be tracked for the next point release.

**Overall Acceptance Verdict: ACCEPT WITH MINOR ISSUES**
**Acceptance Score: 7.5 / 10**

All 5 re-executions hit advice → 0 queries. **PASS for identify-family.**

When the 5 tasks span multiple kinds (`identify`, `search`, `optimize`, `compute`):
```
First run identify n= 64: queries= 6
First run identify n=256: queries=13
First run search   n=128: queries=15
First run optimize n= 64: queries= 0   # planner chose a 0-query plan for optimize

Second run optimize n= 64: queries= 0      # planner chose 0 queries again
Second run compute  n= 32: queries=16 !!  # advice MISS — no entry seeded
```

**Friction point (medium severity):** Only `identify` and `identify_hard` seed advice entries (confirmed in `srs/runtime.py` line 507: `if task.kind in ("identify", "identify_hard") and r.correct:`). The other 6 task kinds (`search`, `optimize`, `compute`, `store`, `amortize`, `verify`) never build advice, so they cannot benefit from self-improvement across runs. This means the SRS Runtime's headline "self-improvement" feature is **partial**: it works for the identify family but is silent no-op for the rest.

A user reading the README or `capabilities` output ("Advice entries: N") might reasonably assume that *any* task benefits from caching, which is not the case. The behavior should either be (a) extended to seed advice for all task kinds, or (b) clearly documented as identify-family-only.

**Bonus friction point:** The capabilities dict returned by `Runtime.capabilities()` uses keys that don't match the human-format CLI labels:
- Human: "Snapshots on disk:" → JSON: `"snapshots"` (not `"snapshots_on_disk"`)
- Human: "Avg queries/task:" → JSON: `"avg_queries_per_execution"` (label says "task", key says "execution")
- Human: "Total queries made:" → JSON: `"total_queries_made"` (consistent — but the only one that is)

A user scripting against the JSON output will hit `KeyError` if they guess key names from the human labels. Discovered this firsthand — my first Scenario 5 script crashed on `caps['snapshots_on_disk']`.

### Scenario 6 — Error Handling

| Input | Behavior | Verdict |
|-------|----------|---------|
| `execute invalid_kind 64` | argparse rejects with `error: argument kind: invalid choice 'invalid_kind' (choose from identify, identify_hard, search, verify, compute)` | PASS — friendly, exit 2 |
| `execute identify 999999999` | CLI catches with `Error: n=999999999 is too large. Maximum supported value is 1000000. Please use a smaller value.` exit 1 | PASS — friendly, no traceback |
| `execute identify -5` | CLI catches with `Error: n=-5 must be 0 or greater.` exit 1 | PASS — friendly, no traceback |
| `execute identify 0` | **Uncaught traceback:** `ValueError: task kind 'identify' requires a non-empty hypotheses list (got length 0); target_idx=0 has nothing to index into` raised from `_validate_task` and propagated all the way out of `main()`. The user sees a full Python stack trace. | **FAIL — crash** |
| `execute identify 64 --budget 0` | CLI runs, planner picks `['E']` (execution-only, no queries possible), returns `correct=False, queries=0`, exit code 2 | PASS — graceful degradation |
| `execute identify 64 --budget -1` | **Uncaught traceback:** `ValueError: Task.budget must be 0 or greater, got -1` raised from `Task.__post_init__` and propagated out of `main()`. | **FAIL — crash** |

The `n=0` and `budget=-1` cases are the only true crashes found in the entire acceptance test. Both produce full Python tracebacks, which is unacceptable for an end-user CLI. The CLI's `cmd_execute` function validates `n > MAX_N` and `n < 0` explicitly but delegates `n == 0` and `budget < 0` to the runtime, where they raise `ValueError` that is never caught.

**Fix:** Wrap the `task = Task(...)` / `r = rt.execute(task)` block in `cmd_execute` with `try: ... except ValueError as e: print(f"Error: {e}", file=sys.stderr); return 1`. Two lines of code, closes both crashes.

### Scenario 11 — Recovery from Crash

**Step 1:** Start a Python script that runs `execute(task, resume=True)` on a 100k-hypothesis identify task. The `resume=True` flag forces the runtime to write an in-flight file (`inflight_crashme-task-100k.json`) at the start of execution.

**Step 2:** Send `SIGKILL` to the process 0.5s after the marker file appears. The process dies mid-execution.

**Step 3:** Inspect `~/.srs/snapshots/`. The in-flight file remains:
```json
{
  "task_id": "crashme-task-100k",
  "kind": "identify",
  "payload_summary": {"n": 100000, "axis": "queries"},
  "queries_made": 0,
  "budget_total": 128,
  "budget_remaining": 128,
  "rng_state": null,
  "timestamp": "2026-07-18T10:28:04.022200+00:00",
  "inflight_hash": "7256a0540b70..."
}
```
No snapshot was written (the process was killed before `store_state()` ran).

**Step 4:** `python3 srs/cli.py recover`:
```
No snapshot found
```
**Friction point (medium severity):** The `recover` command says "No snapshot found" and exits 1. It does **not** mention that there is an interrupted task on disk. A user running `recover` after a crash would conclude there's nothing to recover, even though there is. The user has to run `capabilities` separately to see `Interrupted tasks: 1`. The `cmd_recover` function in `srs/cli.py` only reports interrupted tasks *after* a successful snapshot recovery (line 425-448) — the no-snapshot branch (line 450-454) is silent about inflight files.

**Step 5:** Resume the interrupted task via the Python API:
```python
rt = Runtime(home="~/.srs/snapshots")
task = Task(kind="identify", payload=..., budget=128, task_id="crashme-task-100k")
r = rt.execute(task, resume=True)
```
Output:
```
Resuming task with resume=True...
Result: queries=17 correct=True answer=50000
Primitives used: ['A', 'C']
Wall time: 1760.18 ms
OK: in-flight file cleared after successful resume
```
The resume worked. Because the in-flight file recorded `queries_made=0` (the process was killed before any query completed), the resume started from scratch and made 17 queries — same as a fresh run would have. In a real crash mid-query, the resume would skip the already-made queries and use only the remaining budget.

**Friction point (medium severity):** There is **no CLI subcommand to resume an interrupted task**. The `execute` subcommand does not accept `--resume`. A user who wants to resume must write Python code. For a CLI-first tool, this is a significant gap — the crash-recovery story is only half-implemented at the CLI layer.

### Scenario 12 — Planning Without Execution

All 8 task kinds plan successfully:

```
plan identify      --n 256 --budget 16 → queries:8  work:40960  primitives:['A','C']
plan identify_hard --n 256 --budget 16 → queries:8  work:40960  primitives:['A','C']    # identical to identify
plan search        --n 256 --budget 16 → queries:16 work:4128   primitives:['E','Q']
plan optimize      --n 256 --budget 16 → queries:8  work:40960  primitives:['A','C']    # identical to identify
plan verify        --n 256 --budget 16 → queries:5  work:5      primitives:['V']
plan compute       --n 256 --budget 16 → queries:16 work:4112   primitives:['E']
plan store         --n 256 --budget 16 → queries:0  work:0      primitives:['C']        # degenerate
plan amortize      --n 256 --budget 16 → queries:8  work:40960  primitives:['A','C']    # identical to identify
```

**Friction point (low severity):** `identify`, `identify_hard`, `optimize`, and `amortize` produce **identical** plans. The planner code (`srs/planner.py` line 202) treats them all as the same case with the same candidate primitive sets. There is no semantic differentiation in the cost model — `identify_hard` is not actually harder, `optimize` is not actually optimization, `amortize` is not actually amortized. From the planner's perspective, they are aliases. A user who plans `identify_hard` expecting higher cost than `identify` will be surprised.

**Friction point (low severity):** When advice is available (any advice entry exists), the planner includes `Adv` in the primitive set for `search`, `compute`, etc. and estimates `queries=0`. But the actual execution will only hit advice if a matching `(hypotheses, target)` entry was seeded — and advice is only seeded for `identify`/`identify_hard` (see Scenario 5). So the planner's `queries=0` estimate for non-identify kinds is **misleadingly optimistic** when advice is available. The planner should either (a) only add `Adv` to candidates when the specific task kind seeds advice, or (b) emit a warning that the 0-query estimate is conditional on a hit.

**Friction point (very low severity):** `plan store` returns `work_units=0, depth=0, queries=0` — a degenerate plan. This is probably correct (storing requires no queries and minimal work), but `depth=0` is odd. A user might wonder if the plan is broken.

**PASS** overall — the planner runs, produces cost estimates, and the estimates that *are* differentiated are reasonable (verify has 5 verification calls, compute has work_units=4112, search has queries=16 = budget).

## 4. Friction Points (Things That Work But Are Confusing or Annoying)

These are not bugs — the runtime behaves as designed — but a real user will trip on them.

1. **Self-improvement is identify-family-only.** The README and bench output emphasize "self-improvement" and "advice hit on second run: 0 queries". But this only works for `identify` and `identify_hard`. A user running `search` or `compute` twice will see the same query count both times. Either extend advice seeding to all kinds, or document the limitation prominently.

2. **Capabilities JSON key names diverge from human labels.** Human output says "Snapshots on disk:" but the JSON key is `"snapshots"`. Human says "Avg queries/task:" but the JSON key is `"avg_queries_per_execution"`. A user scripting against the JSON output will hit `KeyError` if they guess from the human labels.

3. **Bench header says "v7.2", JSON version says "7.3.0", runtime is v8.0.0.** A user running `bench` will think they have an outdated runtime. Three different version strings in one tool is confusing.

4. **Bench writes `benchmark_results.json` to the project root**, not the runtime home. Running `bench` from a clean checkout pollutes the source tree.

5. **`recover` is silent about interrupted tasks when no snapshot exists.** After a crash that killed the process before `store_state()` ran, `recover` says "No snapshot found" and exits 1, with no mention of the inflight file. The user has to run `capabilities` to discover the interrupted task.

6. **No CLI subcommand for resume.** The `execute` subcommand has no `--resume` flag. Resuming an interrupted task requires Python code. The crash-recovery story is incomplete at the CLI layer.

7. **Planner aliases identify / identify_hard / optimize / amortize.** Four task kinds produce identical cost estimates. The semantic distinction (if any) is invisible at the planning layer.

8. **Planner is overly optimistic for non-identify kinds when advice is available.** `plan search --n 64 --budget 16` says `queries:0` when advice is available, but the actual execution will use queries because no advice entry exists for search tasks. The estimate is conditional on a hit that won't happen.

9. **`notes.v73_real_compression` in JSON output.** The string "v73" (a version label) leaks into the user-facing JSON. Cosmetic.

10. **Total queries made double-counts across primitives.** A single identify task that makes 6 underlying queries reports `total_queries_made=12` in capabilities (because both A and C each record 6). This is documented in the capabilities docstring, but a user reading the number will be confused. The per-primitive breakdown clarifies, but the headline number is misleading.

11. **`--format human execute` still prints INFO log lines** before the result block (unless `--quiet` is also passed). A user who wants clean human output has to remember to add `--quiet`. `--format json` correctly implies quiet; `--format human` does not. (Arguable design choice — having logs visible by default is useful for debugging — but inconsistent with the JSON behavior.)

12. **N=0 and budget=-1 leak tracebacks.** (Already counted as crashes in Section 5.)

## 5. Crashes (Unexpected Errors)

Two crashes were found, both in Scenario 6, both uncaught Python tracebacks leaked to the user.

### Crash 1: `execute identify 0`

**Command:** `python3 srs/cli.py execute identify 0`

**Stdout:** (empty)

**Stderr:**
```
Traceback (most recent call last):
  File "/home/z/my-project/download/srs/cli.py", line 609, in <module>
    sys.exit(main())
  File "/home/z/my-project/download/srs/cli.py", line 593, in main
    return cmd_execute(args)
  File "/home/z/my-project/download/srs/cli.py", line 390, in cmd_execute
    r = rt.execute(task)
  File "/home/z/my-project/download/srs/runtime.py", line 242, in execute
    _validate_task(task)
  File "/home/z/my-project/download/srs/types.py", line 414, in _validate_task
    raise ValueError(
ValueError: task kind 'identify' requires a non-empty hypotheses list (got length 0); target_idx=0 has nothing to index into
```

**Exit code:** 1

**Root cause:** `cmd_execute` builds `hyps = [hashlib.sha256(f"h{i}".encode()).digest() for i in range(n)]` with `n=0`, producing an empty list. It then constructs `Task(kind="identify", payload={"hypotheses": [], "target_idx": 0, ...})` and calls `rt.execute(task)`. The runtime's `_validate_task` raises `ValueError` because `target_idx=0` cannot index into an empty list. The CLI does not catch this — the exception propagates out of `main()` and Python prints the traceback.

**Fix:** In `cmd_execute`, add an `n == 0` check alongside the existing `n < 0` check:
```python
if n == 0:
    print(f"Error: n=0 is not valid; identify requires at least 1 hypothesis.",
          file=sys.stderr)
    return 1
```
Or, more generally, wrap the `Task(...)` / `rt.execute(...)` calls in `try: ... except ValueError as e: print(f"Error: {e}", file=sys.stderr); return 1` to catch any future validation errors gracefully.

(Likely fine in practice — the planner caps queries at log2(N) regardless of budget — but the lack of an explicit budget cap is a latent issue.)
