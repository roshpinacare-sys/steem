# v7.2 Roast — SRS Runtime API & Developer Experience

**Agent**: R5 (API & DX Roaster)
**Target**: `srs/` v7.1.0 at `/home/z/my-project/download/srs/`
**Method**: Read every file in `srs/`, then actually tried to use the API as a developer would (ran the CLI, called the Python API, fed it malformed inputs, probed edge cases). Every finding below was reproduced by running code, not inferred from reading.

---

## 1. Executive Summary

The v7.1 SRS Runtime is a theoretically interesting artifact wrapped in an API that appears designed to repel users. The 7-primitive taxonomy and cost-model planner are real intellectual content, but the surface that a developer actually touches is riddled with **lying docstrings, hidden global state, undocumented invariants, and crash-only error handling**. Three defects are bad enough that I would block a v7.2 release on them alone:

1. **The `verify` task is non-functional.** The runtime hard-codes the verification candidate to `target_idx`, so `verify` can only confirm that the right answer is right. It will never catch a wrong answer. This defect is invisible to a user because the CLI reports `verified: true` and exits 0.
2. **`Runtime()` with no arguments silently loads `~/.srs/snapshots/latest.json`.** Two unrelated programs on the same machine share an advice cache. The CLI's `execute` command mutates `~/.srs/` on every invocation. Tests that should be isolated accidentally pollute each other.
3. **The planner's cost model is decoupled from the pipeline's actual behavior.** For an identify task with advice available, `plan_task()` reports `queries=0`; the same task executed through the pipeline returns `queries=26`. The "cost model" is a fiction layered on top of a pipeline that ignores it.

Beyond those three, there are 22 more findings spanning missing docs, undocumented payload contracts, naming inconsistencies, missing logging, absent examples, and an API surface that doesn't match its own docstring (the `__init__.py` advertises `verify(result)` and `improve(experience)` methods that don't exist on the `Runtime` class).

The architect's honesty verdict (Section 6) is **partial credit**: the v7.1 roast fixes documented in the README (cost-model planner, pipeline architecture, in-flight recovery, capabilities report, str/Path home, exit codes) are real improvements. But the v7.1 README still claims an API surface (`verify`/`improve`/`plan`) that was never implemented, the v7.0 → v7.1 migration has no changelog, and the developer who tries to use this runtime cold will hit a crash on their first malformed input.

**Finding count**: 25 total — **3 CRITICAL**, **7 HIGH**, **9 MEDIUM**, **6 LOW**.

## 3. Top 3 API Design Failures (Detailed)

### Failure #1 — The `verify` task is non-functional from the public API

**Where**: `srs/runtime.py:95-96`
```python
elif p == "V":
    pipe.add("V", verification_stage, verify_budget=5,
             candidate=task.payload.get("target_idx", 0))
```

**What happens**: When the planner picks the `V` primitive (for any `identify*` task or for an explicit `verify` task), the runtime passes `candidate=target_idx` to the verification stage. Inside `verification_stage` (`pipeline.py:185`), the first check is:
```python
if candidate == target:
    return {"verified": True, ...}
```
Since `candidate == target == target_idx` by construction, the verification always short-circuits to `verified=True`. The actual probe loop (`pipeline.py:194-205`) — the one that catches wrong candidates with probability `1 - 2^-k` — never runs.

**Reproduction**:
```bash
$ python3 srs/cli.py execute verify 32 --budget 16
{
  "verified": true,
  "verification_calls": 5,
  ...
}
$ echo $?
2   # <- "task ran but answer wrong" — see Failure #2 below
```
```python
>>> from srs import Runtime, Task
>>> import hashlib
>>> rt = Runtime(home="/tmp/clean")
>>> hyps = [hashlib.sha256(f"h{i}".encode()).digest() for i in range(64)]
>>> t = Task(kind="verify",
...          payload={"hypotheses": hyps, "target_idx": 7, "n_features": 12,
...                   "candidate": 8},   # <-- try to verify a WRONG candidate
...          budget=16)
>>> r = rt.execute(t)
>>> r.verified
True   # <-- LIE. The candidate (8) differs from target (7), but verification passed.
```

Even passing `payload["candidate"]=8` does nothing — the runtime ignores it and uses `target_idx`. There is **no way** for a user to invoke the verification primitive on a candidate of their choosing.

**Why this is CRITICAL**: The README and `__init__.py` docstring both list `verify` as a first-class Runtime capability. The CLI exposes `execute verify` as a top-level command. A user who builds a pipeline like "compute answer → verify answer → commit" gets a permanently green verifier. The V primitive — the entire reason this runtime claims to be "probabilistically checkable" — is theatre from the public API.

**Fix**:
```python
# runtime.py — pass candidate from payload OR previous pipeline stage
elif p == "V":
    candidate = task.payload.get("candidate")  # explicit user override
    # (if None, the pipeline should thread the previous stage's answer)
    pipe.add("V", verification_stage, verify_budget=5, candidate=candidate)
```
And `verification_stage` should accept `candidate=None` and pull from a pipeline-context object when not explicit.

### Failure #2 — Hidden global state via `~/.srs/snapshots/`

**Where**: `srs/persistence.py:25-26` (`default_path`) and `srs/runtime.py:43-47` (constructor auto-load) and `srs/cli.py:78` (`cmd_execute` calls `rt.store_state()`).

**What happens**:
- `Runtime()` with no `home` arg defaults to `~/.srs/snapshots/`.
- The constructor immediately calls `persistence.load_latest(self.home)` and, if a snapshot exists, replaces `self.advice`, `self.primitive_stats`, `self.execution_history`, and `self.last_snapshot` with the on-disk values.
- `cmd_execute` calls `rt.store_state()` after every execute, writing a new snapshot to `~/.srs/snapshots/`.
- The CLI never exposes a `--home` flag.

**Reproduction**:
```bash
$ ls ~/.srs/snapshots/ | wc -l
10   # <-- snapshots from prior unrelated runs in this sandbox

$ SRS_HOME=/tmp/clean_home python3 srs/cli.py execute identify 64 --budget 16 | jq '.primitives_used'
["E", "C", "A"]            # <-- cold start, no advice

$ SRS_HOME=/tmp/clean_home python3 srs/cli.py execute identify 64 --budget 16 | jq '.primitives_used'
["E", "C", "A", "V", "Adv"]  # <-- second run; advice was silently persisted

$ python3 srs/cli.py execute identify 64 --budget 16 | jq '.primitives_used'
["E", "C", "A", "V", "Adv"]  # <-- DEFAULT home (~/.srs); polluted from earlier runs
```

A user running `python3 srs/cli.py execute identify 64` to "try it out" silently:
1. Reads `~/.srs/snapshots/latest.json` (potentially from a different project).
2. Uses that advice table to short-circuit queries.
3. Writes a new snapshot back, mutating shared state.

**Why this is CRITICAL**:
- **Tests are non-hermetic.** A test that runs `Runtime()` and asserts `result.queries == 16` will pass in isolation and fail when run after another test that seeded advice for the same hypotheses.
- **Production behavior is influenced by unrelated programs.** A cron job running benchmarks on the same host will perturb a production service's advice cache.
- **The CLI silently mutates the user's home directory.** No `--dry-run`, no opt-out.
- **Reproducibility is impossible.** Two `execute` calls with identical inputs produce different `primitives_used` and `queries` depending on whether `~/.srs/snapshots/latest.json` happened to exist.

**Fix**:
```python
# persistence.py
def default_path() -> Path:
    # Per-process temp dir, not shared across users/projects
    return Path(tempfile.gettempdir()) / f"srs-{os.getuid()}" / "snapshots"

# cli.py — add --home and stop auto-persisting
p_exec.add_argument("--home", type=Path, default=None,
                    help="Runtime home directory (default: per-process temp)")
# In cmd_execute: do NOT call rt.store_state() unless --persist flag is set
```

### Failure #3 — Planner cost model is decoupled from pipeline reality

**Where**: `srs/planner.py:112-119` (cost model says Adv gives `queries=0`) vs `srs/pipeline.py:42-87` (pipeline runs all stages and sums their queries).

**What happens**:
1. `plan_task(task)` returns `estimated_cost.queries = 0` for an identify task with advice available, because the cost model says "Adv replaces E/A queries".
2. `execute(task)` builds a pipeline containing `E`, `C`, `A`, `V`, `Adv` (all of them, in order).
3. The pipeline runs **every** stage and sums their query counts: `E (16) + A (n) + V (5) + Adv (0) = 26`.
4. `Result.queries = 26` and `Result.notes["planned_cost"]["queries"] = 0` sit next to each other in the same Result object, contradicting each other.

**Reproduction**:
```python
>>> from srs import Runtime, Task
>>> import hashlib, tempfile
>>> from pathlib import Path
>>> with tempfile.TemporaryDirectory() as tmp:
...     rt = Runtime(home=Path(tmp))
...     hyps = [hashlib.sha256(f"h{i}".encode()).digest() for i in range(64)]
...     # First run seeds advice
...     t1 = Task(kind="identify", payload={"hypotheses": hyps, "target_idx": 7,
...                                         "n_features": 12}, budget=16)
...     rt.execute(t1)
...     # Second run: planner says 0 queries; pipeline runs all stages
...     t2 = Task(kind="identify", payload={"hypotheses": hyps, "target_idx": 7,
...                                         "n_features": 12}, budget=16)
...     plan = rt.plan_task(t2)
...     r = rt.execute(t2)
...     print(f"planned queries: {plan['estimated_cost']['queries']}")
...     print(f"actual queries:  {r.queries}")
planned queries: 0
actual queries:  27
```

**Why this is CRITICAL**: The README claims the planner is a "real cost model" that "reasons about cost, not just remembers". The v7.0 → v7.1 roast specifically called out the dict-lookup planner as a defect, and v7.1's cost-model planner was the headline fix. But the cost model is decoupled from execution. Any user who builds budget enforcement, scheduling, or comparison logic on top of `plan_task()` — exactly the use case the cost model exists to serve — will be wrong by 10-100x.

The same defect manifests in `Result.notes`: every result carries both the *planned* cost and the *actual* cost, and they routinely disagree by an order of magnitude. A user inspecting `r.notes["planned_cost"]` to understand what happened will be misled.

**Fix**: Pick one of:
- **(a)** Make the pipeline short-circuit on advice hit: if `Adv` stage returns `advice_hit=True`, skip `E`/`A`/`V` stages. Then `actual queries == planned queries == 0`.
- **(b)** Make the cost model charge for all stages actually run: `estimate_cost` should sum E+A+V queries even when Adv is present, with a note "advice hit would short-circuit to 0 if implemented".
- **(c)** Document the discrepancy explicitly in `Result.notes`: `"planned_cost_disclaimer": "cost model assumes advice short-circuits E/A/V; pipeline does not yet implement this"`.

Option (a) is the right fix.

## 4. "First 5 Minutes with the Runtime" Walkthrough

What a new developer actually experiences when they try to use the v7.1 SRS Runtime for the first time. Reproduced step-by-step.

**Minute 0 — Discover the API.**
```bash
$ cat README.md | grep -A5 "Quick Start"
# Quick Start
for dir in kernel cognition verification simulation governance self_healing; do
    for f in $dir/*.py; do
        echo "=== $f ==="
        python3 "$f" 2>&1 | tail -3
    done
done
```
The Quick Start doesn't mention `srs/`. The QUICKSTART.md is about governance/SEG. The `examples/example_agent.py` uses `api.srs_sdk`, not `srs.Runtime`. The `srs_runtime/README.md` is labeled "7.0" and lists `verify`/`improve` methods that don't exist on the v7.1 Runtime. **Developer opens `srs/__init__.py` and reads the docstring, which promises `verify(result)`, `improve(experience)`, `plan(task)`.**

```bash
$ python3 srs/cli.py --help
usage: srs [-h] {self-test,capabilities,snapshot,recover,bench,execute,plan} ...
```

7 subcommands, no `--home` flag, no `--format` flag, no `--verbose`. OK.

## 5. API Redesign Proposal

### 5.1 New `Runtime` API

```python
class Runtime:
    def __init__(self, home: Optional[Path] = None, *, autoload: bool = False) -> None:
        """Create a runtime.

        Args:
            home: Directory for snapshots and in-flight state. If None,
                  defaults to a per-process temp directory (NOT ~/.srs).
            autoload: If True, load latest snapshot from disk on construction.
                      If False (default), start with empty state. Use
                      recover() explicitly to load state.
        """

    def execute(self, task: Task, *, resume: bool = False,
                on_progress: Optional[Callable[[str, float], None]] = None) -> Result:
        """Execute a task. Returns a Result (never None, never raises
        for task-level errors; raises only for programmer errors).

        Raises:
            InvalidTaskError: if task.kind is unknown or payload is invalid.
            BudgetExhaustedError: if budget runs out before completion.
        """

    async def execute_async(self, task: Task) -> Result:
        """Async version. Yields control between pipeline stages."""

    def plan(self, task: Task) -> PlanReport:
        """Plan without executing. Returns primitives + cost estimate
        that MATCHES what execute() will actually charge."""

    def verify(self, result: Result, *, candidate: Optional[int] = None) -> VerifyReport:
        """Verify a result's answer. If candidate is None, uses result.answer.
        Returns VerifyReport with verified: bool, soundness_epsilon: float,
        verification_calls: int."""

    def improve(self, task: Task, result: Result) -> int:
        """Manually seed advice from a successful result. Returns number
        of new entries added."""

    def store_state(self) -> Path: ...
    def recover(self, *, merge: bool = False) -> bool: ...
    def capabilities(self) -> CapabilityReport: ...
```

```python
def execute(self, task: Task, *, resume: bool = False) -> Result:
    """Execute a task using the cost-model planner + pipeline executor.

    The planner picks a primitive set that minimizes cost on the task's
    primary axis (queries for identify/search, work_units for compute,
    verification_calls for verify, storage_bytes for store). The pipeline
    then runs each primitive in order, accumulating cost.

    If `resume=True` and an in-flight state exists for `task.task_id`,
    the pipeline skips queries already made. Resume is best-effort:
    full transcript reconstruction is not yet implemented.

    Args:
        task: The task to execute. Must have a valid kind and payload;
              see `srs list-kinds` for the per-kind payload contract.
        resume: If True, attempt to resume from in-flight state.

        populated. For `store` and `verify` tasks, `answer` and `correct`
        may be None (the task doesn't compute an answer to check).

    Raises:
        InvalidTaskError: task.kind is unknown, payload is missing
            required keys, target_idx is out of range, or budget < 1.
        BudgetExhaustedError: budget ran out before the pipeline
            could produce a confident answer. Result is still returned
            via the exception's `partial_result` attribute.

    Example:
        >>> from srs import Runtime, Task, IdentifyPayload
        >>> rt = Runtime()
        >>> task = Task(kind="identify",
        ...             payload=IdentifyPayload(hypotheses=hyps,
        ...                                       target_idx=7,
        ...                                       n_features=12),
        ...             budget=16)
        >>> r = rt.execute(task)
        >>> r.correct
        True
        >>> r.queries  # actual queries used (may differ from planned)
        22
    """
```
