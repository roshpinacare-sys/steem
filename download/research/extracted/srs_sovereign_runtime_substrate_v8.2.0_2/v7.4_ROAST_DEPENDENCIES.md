## 1. Executive Summary

The v7.3 release advertises a "stdlib-only" `srs/` runtime, and that claim is
**verified**: every external import in `srs/*.py` and `srs/primitives/*.py`
resolves to the Python 3.10+ standard library (`argparse`, `hashlib`, `json`,
`logging`, `os`, `sys`, `time`, `uuid`, `random`, `math`, `re`, `threading`,
`tempfile`, `pathlib`, `collections`, `dataclasses`, `enum`, `typing`, and
`__future__`). I ran the exact grep requested in the brief —
`rg "^import|^from" srs/*.py srs/primitives/*.py | rg -v "from \.|from srs" | sort -u` —
and confirmed 65 unique import statements, all of them stdlib. **That is the
single bright spot in an otherwise dismal dependency story.**

Outside `srs/`, the supply chain is a mess. The repository declares **6 runtime
Python dependencies** (numpy, torch, z3-solver, pypdf, Pillow, matplotlib),
**9 dev dependencies** (pytest, pytest-cov, pytest-xdist, hypothesis, ruff,
mypy, bandit, qiskit, qiskit-aer, py_ecc), **2 Rust crates** (tock-registers,
cortex-a), **13+ apt packages** in the Dockerfile, and **3 Docker base
images** — but every single one of these is **unpinned or only loosely
pinned** with `>=` / `"0.9"` / `:latest`, none of them are hash-pinned, and
there is **no lockfile, no SBOM, and no `constraints.txt`**.

Worse, the audit found a pile of contradictions and silent gaps:

1. **Three production-grade Python packages — `fastapi`, `uvicorn`, `psycopg2` —
   are imported by `api/server.py`, `api/metrics.py`, `api/rate_limiter.py`,
   `api/websocket.py`, and `api/postgres_adapter.py` but are listed in
   NEITHER `requirements.txt` NOR `pyproject.toml`.** The `srs-api` service
   in `docker-compose.yml` cannot start after `pip install -r requirements.txt`
   — it crashes with `ModuleNotFoundError: No module named 'fastapi'`. This is
   the same class of bug that R10 found for `default_path()` in v7.2: a release
   that was never run end-to-end.
2. The sibling file `srs_runtime/requirements.txt` explicitly states
   "no external dependencies required. Python 3.9+ standard library is
   sufficient." The main `requirements.txt` demands **6 heavy external
   packages including torch (~900 MB) and z3-solver**. The two files
   **directly contradict each other** about the same codebase.
3. The README openly admits: *"Original v6.3 tests: 1093 passing (96 fail
   due to missing torch/z3 — pre-existing)"*. A 96-test pre-existing
   regression has been carried across two major version bumps without
   anyone fixing it.
4. The Dockerfile installs `py_ecc` as a one-off `pip install --no-cache-dir
   py_ecc` (line 51) **in addition to** listing it in `requirements-dev.txt`
   (line 19). Two sources of truth, neither pinned.
5. Two of the three `[project.scripts]` entry points in `pyproject.toml`
   (`srs-smoke-test = "srs.scripts.smoke_test:main"` and
   `srs-z3-proof = "srs.verification.z3_power_proof:main"`) point to module
   paths that **do not exist** (`srs/scripts/` and `srs/verification/` are
   not directories; the real files are at `tests/smoke_test.py` and
   `verification/z3_power_proof.py`). After `pip install .`, invoking either
   console script will raise `ModuleNotFoundError`.
6. Graceful degradation for optional dependencies exists in exactly **two
   modules** (`simulation/qiskit_adapter.py` with `QISKIT_AVAILABLE`,
   `cognition/grpo_advantage_map.py` with a matplotlib try/except). The
   remaining four heavy-dependency consumers — `cognition/agemem_controller.py`,
   `cognition/agemem_adm_trainer.py`, `verification/z3_power_proof.py`,
   `governance/bls_signatures.py` — import `torch`, `z3`, or `py_ecc`
   unconditionally at module top level. If any of those packages is missing,
   the importing module **crashes on import** rather than failing cleanly.
7. The Dockerfile installs Rust 1.75.0 (released December 2023, now well past
   the 6-week release cadence support window — Rust 1.83 shipped December 2024)
   via the classic `curl … | sh -s -- -y` antipattern with **no checksum
   verification** of the `rustup-init` binary. This is textbook supply-chain
   risk.
8. The `docker-compose.yml` uses `prom/prometheus:latest` and
   `grafana/grafana:latest` — floating tags that can and do change
   underneath deployments. A patched Grafana image that breaks config
   compatibility would silently break production.

**Dependency hygiene score: 3 / 10.** The `srs/` package itself is exemplary;
everything around it is undisciplined. The repo would not pass a corporate
supply-chain review (no lockfile, no SBOM, no hash pinning, undocumented
deps, broken console scripts).

## 5. Top 3 Dependency Risks

### Risk #1 — Undeclared `fastapi`/`uvicorn`/`psycopg2` in `api/`

The most damaging supply-chain bug in the release. The `srs-api` service defined
in `docker-compose.yml` builds from the Dockerfile (which installs only what's
in `requirements.txt` and `requirements-dev.txt`), then tries to run
`api/server.py` which immediately `from fastapi import FastAPI, HTTPException,
Header, Depends, Request`. Result: `ModuleNotFoundError: No module named
'fastapi'`. The entire enterprise REST API — the surface that
`ENTERPRISE_VALUE.md`, `api/dashboard.html`, `api/admin.html`, and the
`prometheus`/`grafana` observability stack depend on — **cannot start**. This
is the same class of bug R10 found in v7.2 for `default_path()`: the package
was shipped without anyone running the documented deployment path end-to-end.
Bonus: `api/postgres_adapter.py:69` does `import psycopg2` inside the method
(lazy), so it doesn't crash on import — it crashes on the first call, which
is worse for production (works in dev, fails in prod).

### Risk #2 — Zero version pinning + no lockfile

Every single declared dependency uses `>=` (numpy, torch, z3-solver, pypdf,
Pillow, matplotlib, pytest, hypothesis, qiskit, py_ecc, all of them). Two CI
runs a month apart will resolve to different transitive trees. A
`pip install -r requirements.txt` today pulls torch 2.13.0 (~2 GB with CUDA
wheels on a GPU box, ~900 MB CPU-only on a CPU box); the same command in
March 2024 would have pulled torch 2.2.x. **There is no `requirements.lock`,
no `uv.lock`, no `poetry.lock`, no `pip-tools` output, no `--require-hashes`
anywhere.** Combined with the Dockerfile's unpinned `python:3.12-slim` base
image, unpinned apt packages, and `:latest` Docker tags in
`docker-compose.yml`, the entire deployment is a floating-point operation:
you will never get the same image twice. For a system that advertises
"formally verified hyper-kernel" and "Sovereign Runtime Substrate," this is
deeply ironic — the formal proofs are reproducible but the runtime that
executes them is not.

### Risk #3 — Heavy deps with no graceful degradation + known CVEs

Four modules — `cognition/agemem_controller.py`, `cognition/agemem_adm_trainer.py`,
`verification/z3_power_proof.py`, `governance/bls_signatures.py` — import
`torch`, `z3`, or `py_ecc` at module top level with no `try/except`. Any
importer that touches these modules without those packages installed will
crash with a raw `ModuleNotFoundError`. The pattern for graceful degradation
already exists in the codebase (`simulation/qiskit_adapter.py:32-38` sets
`QISKIT_AVAILABLE = False` on `ImportError`), but it was not applied
consistently. Combined with the CVEs in the allowed version range
(`torch>=2.0` allows CVE-2024-7565 and CVE-2024-48026; `Pillow>=10.0`
allows CVE-2023-50447 arbitrary code execution), the runtime has both a
reliability gap (modules crash on missing deps) and a security gap (lower
bounds allow vulnerable versions). The README's admission that "96 tests
fail due to missing torch/z3 — pre-existing" is the visible symptom of the
reliability gap; the CVEs are the invisible symptom of the security gap.

## 8. Closing Note

The v7.3 release's claim that the new `srs/` runtime is "stdlib-only" is
**true and verified** — that part of the codebase is exemplary. But the
broader repository's dependency story is the worst of all worlds: heavy
deps (torch, z3, qiskit, py_ecc) are declared but unpinned; production deps
(fastapi, uvicorn, psycopg2) are used but **not declared at all**; the
Dockerfile uses `curl|sh` to install EOL Rust with no checksum; the
docker-compose file pins nothing; there is no lockfile, no SBOM, no
dependabot. The 96-test "pre-existing" failure rate is the visible
symptom — the invisible symptom is that a fresh `pip install -r
requirements.txt` will install torch 2.13.0 today but could have installed
the vulnerable torch 2.0.x in March 2024, and nothing in the supply chain
would have caught it.

The fixes are well-understood (pin everything, declare everything,
gracefully degrade everything, generate SBOM, automate patching). The
architect should treat this as a P0 alongside the v7.2 `default_path()` bug
R10 found — same class of bug (release never run end-to-end), different
symptom.

**End of roast.**
