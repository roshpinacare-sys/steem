## Fix 1: Windows `os.replace` retry (R15.2, HIGH)

**Problem.** `os.replace(tmp, path)` raises `PermissionError` on Windows
when another process holds the destination file open. Because POSIX
advisory locks (`fcntl.flock`) are no-ops on Windows, a concurrent
`load_latest()` reader can hold the file open and crash a concurrent
`save()` writer.

**Fix.** Wrap the `os.replace` call in a 5-attempt retry loop with
exponential backoff (1, 2, 4, 8, 16 ms = 31 ms worst-case) when running
on Windows. POSIX behavior is unchanged.

**Validation.** Patched `platform.system` to return `"Windows"` and
`os.replace` to fail N times in a row, then verified:

| Scenario | Attempts | Sleeps | Total backoff | Outcome |
|----------|----------|--------|---------------|---------|
| Fail 2 attempts, succeed on 3rd | 3 | `[0.001, 0.002]` | 3 ms | Write succeeds |
| Fail all 5 attempts | 5 | `[0.001, 0.002, 0.004, 0.008]` | 15 ms | `PermissionError` raised; tempfile unlinked |

Both scenarios finish well under the 31 ms worst-case bound. The
existing tempfile-cleanup path correctly removes the leftover `.tmp_*.json`
file on failure.

## Fix 2: ISO 8601 timestamps (R16.4, CRITICAL)

**Problem.** All timestamps were `time.time()` epoch floats (e.g.
`1784313766.4212925`). Screen readers pronounced every digit; humans
couldn't sort or filter by date without `date -d @...`; no time zone
was carried.

**Fix.** Added a `_iso_now()` helper that returns
`datetime.now(timezone.utc).isoformat()` (e.g.
`"2026-07-18T01:35:16.398363+00:00"`). Replaced every
`time.time()`-for-timestamp use across `srs/runtime.py` and
`srs/persistence.py`:

| Site | Old | New |
|------|-----|-----|
| `runtime.py` execution_history entry | `"timestamp": time.time()` | `"timestamp": persistence._iso_now()` |
| `runtime.py` Snapshot construction | `timestamp=time.time()` | `timestamp=persistence._iso_now()` |
| `runtime.py` snapshot_id seed | `str(time.time())` | `f"{time.time_ns()}_{snap_ts}"` (R15.5 fix: also bumps resolution from ~16ms to nanosecond on pre-Win10) |
| `persistence.py` inflight timestamp | `"timestamp": time.time()` | `"timestamp": _iso_now()` |

`time.perf_counter()` is still used for `wall_time_ms` (intentional — it
is a monotonic duration, not a wall-clock instant).

**Type change.** `Snapshot.timestamp` is now annotated `str` (was
`float`).

**Backward compatibility.** `Snapshot.from_dict()` calls a new
`_coerce_timestamp()` helper that accepts:
- ISO 8601 strings (no-op, just validated)
- `int`/`float` epoch seconds (converted via `datetime.fromtimestamp(..., tz=timezone.utc).isoformat()`)
- `None` (returns current time)
- Anything else (logs a warning, returns current time rather than
  crashing on corrupt data)

Verified: loading a hand-constructed v7.5-style snapshot with
`timestamp: 1784313766.4212925` returns a `Snapshot` with
`timestamp == "2026-07-17T18:42:46.421293+00:00"` and `isinstance(str)`.

## Fix 3: `--format human` for capabilities/recover/execute (R16.2, R16.3, HIGH)

**Problem.** `cmd_capabilities` and `cmd_recover` ignored the
`--format` flag — both branches of `if args.format == "json"` emitted
the same JSON. Users who explicitly asked for human output got a wall
of indented JSON that screen readers pronounced token-by-token.

**Fix.** Added two real human renderers in `srs/cli.py`:

- `_format_human_capabilities(caps)` — short summary header (version,
  totals, success rate, advice count, snapshots, interrupted tasks,
  last snapshot id) followed by a per-primitive breakdown table.
- `_format_human_result(result)` — one line per field with a clear
  label and (where useful) a units suffix (e.g. `Wall time: 4.10 ms`).

`cmd_recover` now prints a short summary ("Recovered snapshot X / N
snapshots on disk / N interrupted tasks") and only prints the
interrupted-task details if there is one.

## Fix 4: Plain-English error messages (R16.7, R16.18, HIGH)

**Problem.** Error messages leaked internal roast IDs (`R10.2`),
developer jargon (`OOM`), and math half-open interval notation
(`[0, n)`).

**Fix.** Rewrote every user-facing error message in `srs/cli.py`,
`srs/types.py`, and `srs/planner.py`:

| Site | Before | After |
|------|--------|-------|
| `cli.py` n-too-large | `Error: n={n} exceeds maximum {MAX_N} (R10.2 fix: prevents OOM). Use n <= {MAX_N}.` | `Error: n={n} is too large. Maximum supported value is {MAX_N}. Please use a smaller value.` |
| `cli.py` negative n | `Error: n={n} must be >= 0` | `Error: n={n} must be 0 or greater.` |
| `cli.py` target_idx OOB | `Error: target_idx {target_idx} out of range [0, {n})` | `Error: target_idx {target_idx} is out of range. Valid range is 0 to {n - 1} (for {n} hypotheses).` |
| `cli.py` candidate OOB | `Error: candidate {args.candidate} out of range [0, {n})` | `Error: candidate {args.candidate} is out of range. Valid range is 0 to {n - 1} (for {n} hypotheses).` |
| `types.py` Task huge list | `length {n} exceeds cap MAX_HYPOTHESES={MAX_HYPOTHESES} (prevents OOM)` | `length {n} is too large. Maximum supported length is {MAX_HYPOTHESES}. Please use a smaller list.` |
| `types.py` negative budget | `Task.budget must be >= 0, got {self.budget}` | `Task.budget must be 0 or greater, got {self.budget}` |
| `types.py` target_idx negative | `is negative; must be in [0, {n})` | `is negative. Valid range is 0 to {n - 1} (for {n} hypotheses).` |
| `types.py` target_idx OOB | `out of range [0, {n})` | `is out of range. Valid range is 0 to {n - 1} (for {n} hypotheses).` |
| `planner.py` unknown primitive | `Unknown primitive: {p}` | `Unknown primitive {p!r}. Valid primitives are: {sorted(valid)}.` |

Roast IDs and `OOM` were dropped entirely. Half-open `[0, n)` notation
was replaced with plain-English `0 to {n - 1} (for {n} hypotheses)` so
non-native speakers and screen readers parse it correctly. Unknown-value
errors now list the valid set so the caller can fix the typo without
consulting the docs.

## Fix 5: Replace `asyncio.get_event_loop()` (R15.3, MEDIUM)

**Problem.** `Runtime.execute_async` used `asyncio.get_event_loop()`,
which is deprecated in Python 3.10+ and raises `RuntimeError` in
Python 3.12 when no loop is running. Will be removed in Python 3.14.

**Fix.** Replaced with `asyncio.to_thread(self.execute, task, resume=resume)`
(Python 3.9+). The new form uses the currently running loop (which
must exist because we are inside an `async def`) and falls back to the
default ThreadPoolExecutor — exactly the documented replacement for
"run a sync function in a thread".

**Validation.** Verified `execute_async` returns the correct Result
shape AND that the event loop is NOT blocked (concurrent `gather` of
`execute_async` + `asyncio.sleep(0.05)` finishes in ~50 ms, not the
~80+ ms it would take if serialized).

## Fix 6: NO_COLOR support + ASCII description + version sync (R16.1, R16.8)

**Problem.**
1. No `NO_COLOR` env-var policy (latent gap — no color is currently
   emitted, but there was no escape hatch for future additions).
2. The argparse `description` used an em-dash (`—`, U+2014) which
   renders as `?` on ASCII-only terminals and is read verbatim by some
   screen readers.
3. The argparse description said `SRS Runtime v7.3` while
   `__version__` is `7.5.0` — `--help` and `capabilities()` disagreed.

**Fix.**
- Added a module-level `USE_COLOR` gate at the top of `cli.py`:
  ```python
  USE_COLOR = (
      os.environ.get("NO_COLOR") is None
      and sys.stdout.isatty()
      and os.environ.get("TERM", "") not in ("", "dumb")
  )
  ```
  Honors `NO_COLOR` (any value disables color per https://no-color.org),
  requires a TTY, and respects `TERM=dumb`. Currently a no-op (no color
  is emitted); documented as the canonical check that any future
  color-emitting code MUST use.
- Replaced the em-dash in the argparse description with `--` (ASCII).
- Replaced the hardcoded `"v7.3"` with `f"v{__version__}"` so `--help`
  always agrees with `capabilities()`.

**Validation.**
```
$ python3 srs/cli.py --help
usage: srs [-h] [--home HOME] [--format {json,human}] ...

SRS Runtime v7.5.0 -- unified 7-primitive platform (real compression +
structured logging)
```

`USE_COLOR` correctly returns `False` when `NO_COLOR` is set or when
stdout is not a TTY.
