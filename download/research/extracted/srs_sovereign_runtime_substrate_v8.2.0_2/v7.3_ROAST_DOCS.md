# R9 — Documentation & Developer Onboarding Roast of the v7.2 SRS Runtime

**Agent:** R9 (Documentation & Developer Onboarding Roaster)
**Target:** `/home/z/my-project/download/srs/` (v7.2.0 SRS Runtime) and its surrounding docs surface (`README.md`, `QUICKSTART.md`, `DEVELOPER_GUIDE.md`, `docs/`, `examples/`, CLI `--help` output, docstrings, `Makefile`, `pyproject.toml`)
**Date:** v7.3 pre-flight roast
**Mission:** Find every documentation gap and onboarding failure. Walk through what a brand-new developer experiences, step by step, from `git clone` to "interpret the result of my first task."

---

## 1. Executive Summary

The v7.2 SRS Runtime ships with a **richly-written but factually inconsistent** documentation surface. The single most damaging problem is not a missing file or a typo — it is that **the README contradicts the code in ways that a new developer cannot resolve without reading the source**. Specifically:

1. **The default home directory is broken.** `Runtime(home=None)` calls `persistence.default_path()`, which does not exist in `srs/persistence.py` (it was dropped during the v7.0→v7.2 refactor; the v6.x `srs_runtime/srs/persistence.py` still has it). The result: every CLI command that constructs a `Runtime` without `--home` crashes with `AttributeError: module 'srs.persistence' has no attribute 'default_path'`. The README's own Quick Start contains a line — `python3 srs/cli.py --format json plan identify --n 256 --budget 16` — that crashes verbatim on first run.

2. **The "Known Limitations" section is stale by two minor versions.** Limitations #3 (stale-advice bug) and #4 (advice key omits target_idx) describe v7.1 behavior. The v7.2 code **already fixes both** (verified by running `python3 srs/cli.py bench` → "[5/5] Advice keying audit (R4.3 fix) … Bug present: False"). The bench suite itself prints the verdict, yet the README still says the bug is unfixed. This is the worst kind of doc rot: the code is honest, the docs are alarmist.

3. **The onboarding path is split-brained.** The repo contains two parallel universes: the v6.x "SRS service" universe (kernel/, cognition/, governance/, api/server.py, `examples/example_agent.{py,ts,go}`) and the v7.x "SRS runtime" universe (`srs/`). `QUICKSTART.md` and `DEVELOPER_GUIDE.md` onboarding the developer into the **v6.x universe** (Python SDK, REST API, BLS governance). `README.md` onboards into the **v7.x universe** (CLI, 7 primitives). A new developer cannot tell which is current. The README never says "ignore QUICKSTART.md and DEVELOPER_GUIDE.md."

4. **No CHANGELOG entries for v6.0–v7.2.** `docs/CHANGELOG.md` ends at v5.4.0. There are ~95 shipped versions and a major architectural pivot (v6.x service → v7.x runtime) with zero changelog coverage. There is no MIGRATION.md, no TROUBLESHOOTING.md, no CODE_OF_CONDUCT.md.

5. **The API reference does not cover the v7.2 runtime.** `docs/API_REFERENCE.md` is auto-generated from docstrings of the v6.x modules (governance, kernel, cognition, simulation, verification, self_healing). The v7.2 `srs/` package — `Runtime`, `Task`, `Result`, `Snapshot`, `Pipeline`, `plan`, `CostEstimate`, `improve` — has **no API reference at all**. Docstrings exist but no `Runtime.execute` docstring shows a usage example.

6. **There are no Python examples for the v7.2 runtime.** `examples/` contains `example_agent.py/.ts/.go`, all of which import `api.srs_sdk` and talk to an HTTP server — none of them import `srs.Runtime`. A new developer who wants to embed the runtime in a script has no template.

The result: **a strong developer can be productive in ~30 minutes by reading the source**; **a new developer who trusts the docs will hit a wall in 30 seconds** (`AttributeError` on first CLI invocation without `--home`) and then spend 15–20 minutes reconciling contradictions before they realize which docs to trust.

**Documentation score: 4/10.** The raw material is good — the v7.2 README is unusually honest, the bench suite is excellent, the code is readable — but the documentation **fails its primary job**: a new developer cannot run the documented commands and get the documented results without debugging the docs themselves.

## 2. "First 5 Minutes" Walkthrough — What a New Developer Experiences

Below is a literal transcription of what I (acting as a new developer) encountered following the README. Every step is reproducible.

### Step 0 — `cat README.md`

The README opens with "Version 7.2.0 | 65/65 v7.2 tests passing | honest benchmarks | CLI with `--home`/`--format`/`--persist`". The "Quality Gates" table at the top asserts:
- "v7.2 srs tests | 54/54 passing in <1s (was 39/39 in v7.1)"
- "Total v7.2 tests | 65/65 passing"
- "v7.2 module self-tests | 13/13 passing"

The README then dives into a long fix-by-fix changelog of R2/R4/R5 roast findings, a "Known Limitations" section with 12 numbered items, and a 200-line "Repository Structure" tree. **There is no "What is SRS?" section, no conceptual model, no definition of what a "task" or a "primitive" is.** The first executable command appears at line 221.

### Step 1 — `python3 srs/cli.py list-kinds`

Works. Output:
```
Valid task kinds (8):
  amortize        primary_axis: queries
  compute         primary_axis: work_units
  identify        primary_axis: queries
  identify_hard   primary_axis: queries
  optimize        primary_axis: queries
  search          primary_axis: queries
  store           primary_axis: storage_bytes
  verify          primary_axis: verification_calls
```
8 kinds listed. Good.

### Step 2 — `python3 srs/cli.py self-test` (the README's stated onboarding command)

Works. Output: `13/13 modules passed`. There is a stray stderr line — `advice hash mismatch (stored=9724c1e20e6e, actual=fb07f1a1b3b9); discarding advice` — because the default `~/.srs/` directory has a tampered/stale snapshot from prior runs. **The README does not mention this warning or tell me to ignore it.** I worry that my install is broken.

### Step 3 — `python3 srs/cli.py --home /tmp/srs_run1 execute identify 64 --budget 16`

Works (the README wisely leads with `--home`). Output is a JSON object. The README never explained that the default output format is JSON for `execute` (despite `--format` defaulting to `human`); the user is left to infer this from the output. The output contains fields like `primitives_used: ["A", "C"]`, `queries: 6`, `notes.compression_ratio: "256/18"`. **No field is documented anywhere.** I don't know what `compression_ratio` means or why it says `256/18`.

### Step 4 — `python3 srs/cli.py capabilities`

**CRASHES:**
```
AttributeError: module 'srs.persistence' has no attribute 'default_path'
```
Same crash for `python3 srs/cli.py plan identify`, `python3 srs/cli.py execute identify 64` (without `--home`), `python3 srs/cli.py snapshot`, `python3 srs/cli.py recover`. The README's `--home` help text says "default: ~/.srs/snapshots/" — but the code path that computes that default is broken.

### Step 5 — `python3 srs/cli.py --format json plan identify --n 256 --budget 16`

This is **line 235 of the README, copied verbatim**. It crashes with the same `AttributeError`. The README's own Quick Start command fails on first run.

### Step 6 — `python3 srs/cli.py execute amortize 64`

After Step 1 showed `amortize` as a valid task kind, I tried to execute it. **argparse rejects it:**
```
srs execute: error: argument kind: invalid choice: 'amortize' (choose from identify, identify_hard, search, verify, compute)
```
Three of the eight kinds advertised by `list-kinds` (`amortize`, `optimize`, `store`) **cannot be executed via the CLI at all**. The README doesn't mention this.

### Step 7 — `pytest tests/` (the universal "did I install correctly?" command)

**10 collection errors** because the v6.x test files import `z3`, `torch`, `qiskit`, `blspy`. The README's Quality Gates table mentions "Original v6.3 tests | 1093 passing (96 fail due to missing torch/z3 — pre-existing)" — but my `pytest tests/` shows 10 *collection errors* and 1 *skip*, not 96 *failures*. **The numbers don't match the README.** I have no idea whether my install is OK. (The fix is `pytest tests/test_srs_runtime.py tests/test_integration_v7.py`, or `make test-srs` — neither is mentioned in the README.)

### Step 8 — Read "Known Limitations" #3 and #4

The README says:
> "**The `improvement.improve()` function has a stale-advice bug.** Calling `improve(adv, hyps, 3, True)` then `improve(adv, hyps, 5, True)` returns `n=0` and leaves `advice.lookup(hyps) == 3`"
> "**The `AdviceTable` key omits `target_idx`.** Advice built for `(hyps, target=5)` is returned for a lookup on `(hyps, target=7)`, yielding `correct=False` silently in 0 queries."

I verified by running the code (see R9.5 below): both claims are **false for v7.2**. `improve(adv, hyps, 3, True)` returns 1; `improve(adv, hyps, 5, True)` also returns 1 (adds a new entry); `advice.lookup(hyps, 3)` returns 3 and `advice.lookup(hyps, 5)` returns 5. The `lookup()` signature requires `target_idx`. The bench suite itself prints `[5/5] Advice keying audit (R4.3 fix) … Bug present: False`. **The README contradicts the code and the bench.**

### Step 9 — Try to use `Runtime` from Python

The README's Quick Start only shows CLI usage. There is no Python example. `examples/example_agent.py` imports `api.srs_sdk` (the v6.x HTTP client), not `srs.Runtime`. I open `srs/__init__.py` and read:
```
The runtime provides:
  - execute(task)         : run a task using selected primitives
  - plan(task)            : choose primitives for a task
  - store_state(snapshot) : persist to disk
  - recover()             : reload last snapshot
  - verify(result)        : probabilistic check
  - improve(experience)   : update advice table from outcomes
  - capabilities()        : measurable capability report
```
Half of these methods (`verify`, `improve`, `plan` as a method) **don't exist on `Runtime`**. The docstring describes a v7.0-era API that was refactored. I now have to read `runtime.py` source to figure out the actual API.

### Step 10 — Five-minute verdict

I have spent 5 minutes. I have:
- Crashed the default constructor 5 times.
- Discovered that the README's "Known Limitations" are wrong.
- Discovered that 3 of 8 task kinds are not executable.
- Failed to find a Python usage example.
- Failed to find an API reference.
- Failed to find a CHANGELOG entry for v7.0, v7.1, or v7.2.
- Failed to find a TROUBLESHOOTING doc that explains the `AttributeError`.

I have also:
- Successfully run `list-kinds`, `self-test`, `bench`, and (with `--home`) `execute`.
- Read source code that is clean, honest, and readable.

The runtime is real. The docs are not.

## 4. Top 3 Documentation Failures (Detailed)

### Failure #1: The Default Home is Broken — and the README Hides It

**What:** `Runtime(home=None)` calls `persistence.default_path()`, which does not exist in `srs/persistence.py`. Every CLI command that constructs a `Runtime` without `--home` (`execute`, `plan`, `capabilities`, `snapshot`, `recover`) crashes with `AttributeError: module 'srs.persistence' has no attribute 'default_path'`. The `--home` help text claims "default: ~/.srs/snapshots/" — but the code path that computes that default is missing.

**Evidence:**
```
$ python3 srs/cli.py execute identify 64
Traceback (most recent call last):
  File "/home/z/my-project/download/srs/cli.py", line 342, in <module>
    sys.exit(main())
  ...
  File "/home/z/my-project/download/srs/runtime.py", line 38, in __init__
    self.home = persistence._coerce_path(home or persistence.default_path())
                                                 ^^^^^^^^^^^^^^^^^^^^^^^^^
AttributeError: module 'srs.persistence' has no attribute 'default_path'
```
```
$ python3 -c "from srs import persistence; print(hasattr(persistence, 'default_path'))"
False
```
The v6.x `srs_runtime/srs/persistence.py:16` has `def default_path() -> Path: return Path.home() / ".srs" / "snapshots"`. The v7.2 refactor dropped it. Three call sites in `srs/persistence.py` (lines 98, 119, 158) and one in `srs/runtime.py:38` still reference it.

**Why it's the worst:** The README's Quick Start (line 235) literally says `python3 srs/cli.py --format json plan identify --n 256 --budget 16` — no `--home`. **This command crashes verbatim.** The README's Quick Start at lines 224-229 wisely uses `--home /tmp/srs_run1` for `execute` — but never explains why, and the `plan` example at line 235 forgets. A new developer's first reaction is "the install failed" or "I have the wrong Python version" — not "the default home computation is broken."

**Compounding factor:** The README's "Known Limitations" doesn't list this. There's no TROUBLESHOOTING.md. The error is a raw Python traceback, not a friendly message. The crash affects 5 of the 8 subcommands.

**Fix:** Add to `srs/persistence.py`:
```python
def default_path() -> Path:
    """Default home directory for SRS snapshots (~/.srs/snapshots/)."""
    return Path.home() / ".srs" / "snapshots"
```
Add a regression test `tests/test_default_home.py` that asserts `Runtime()` (no args) constructs without error and writes to `~/.srs/snapshots/` (or a `SRS_HOME` env override for test isolation). Add a top-level try/except in `cli.py:main` that catches `AttributeError` and prints "This is a known issue (R9.1). See docs/TROUBLESHOOTING.md."

### Failure #2: The "Known Limitations" Section Lies About the Code

**What:** README.md lines 97-103 list two "Known Limitations" (#3 stale-advice bug, #4 advice key omits target_idx) that describe v7.1 behavior. The v7.2 code **already fixes both**. The bench suite itself prints "Bug present: False".

**Evidence:**
```
$ python3 -c "
from srs.improvement import improve
from srs.primitives.advice import AdviceTable
import hashlib
adv = AdviceTable()
hyps = [hashlib.sha256(f'h{i}'.encode()).digest() for i in range(8)]
n1 = improve(adv, hyps, 3, True)
n2 = improve(adv, hyps, 5, True)
print('n1=', n1, 'n2=', n2)
print('lookup(hyps,3)=', adv.lookup(hyps, 3))
print('lookup(hyps,5)=', adv.lookup(hyps, 5))"
n1= 1 n2= 1
lookup(hyps,3)= 3
lookup(hyps,5)= 5
```
The README claims `n2 == 0` and `advice.lookup(hyps) == 3` (stale). The code returns `n2 == 1` and `advice.lookup(hyps, 3) == 3` / `advice.lookup(hyps, 5) == 5` (correct). Furthermore, the `lookup()` method **requires** `target_idx` — the README's `advice.lookup(hyps) == 3` (single-argument) call doesn't even match the current API signature.

The bench suite (`python3 srs/cli.py bench`) confirms:
```
[5/5] Advice keying audit (R4.3 fix)
  Advice built for target=5, queried for target=7
  Target-aware lookup returns: None
  ...
  Bug present: False
  Interpretation: v7.2 R4.3 fix: advice is now target-aware. ... Bug is FIXED.
```

**Why it's the worst:** The "Known Limitations" section is the most trust-critical part of any README. It's where the project admits its flaws. When those flaws are fabricated (or stale), the developer loses trust in **every other claim** in the document. They start to wonder: "If the README lies about advice keying, does it also lie about the test pass rate? About the benchmark honesty? About the license?"

**Compounding factor:** The bench command itself prints the truth, but the README never says "run `bench` to see the current state of each limitation." The two sources of truth (README prose, bench output) disagree, and the README is the one a new developer reads first.

**Fix:** Audit all 12 Known Limitations items against v7.2 code:
- #3 (stale-advice): **FIXED** — remove or rewrite as "v7.2 fix: improve() now adds separate entries per target_idx (R4.3 fixed)."
- #4 (advice key omits target_idx): **FIXED** — remove or rewrite as "v7.2 fix: key is now `sha256(hyps)[:16]:target_idx` (R4.3 fixed). Legacy `lookup_any_target()` still exists but is unused by `execute_identify`."
- Verify #1, #2, #5, #6, #7, #8, #9, #10, #11, #12 are still true; mark each with [VERIFIED v7.2] or [FIXED v7.2].
