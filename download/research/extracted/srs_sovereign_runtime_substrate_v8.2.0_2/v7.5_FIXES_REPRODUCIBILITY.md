## 2. Fix 1: Deterministic RNG Seeding (R6.5 — verified)

### Problem

The v7.3 fix replaced Python's `hash(task_id)` (which is salted per
process by `PYTHONHASHSEED`) with `sha256(task_id)[:4]`. This was
correct in principle, but the v7.4 cycle never added a test that
verifies the seed is identical across separate Python subprocesses —
so a regression that re-introduces `hash()` could have slipped
through.

### Verification

`_deterministic_seed(task_id)` in `srs/runtime.py` (lines 83–96):

```python
def _deterministic_seed(task_id: str) -> int:
    """Derive a 32-bit RNG seed from task_id deterministically (R6.5 fix)."""
    digest = hashlib.sha256(str(task_id).encode("utf-8")).digest()
    return int.from_bytes(digest[:4], "big")
```

This is already cross-platform-stable:

- **sha256** is defined by NIST FIPS 180-4 and produces identical
  output on every conforming implementation (Python's `hashlib.sha256`
  wraps OpenSSL on Linux/macOS and the Windows CNG/Bcrypt provider on
  Windows — both certified).
- **`str(task_id).encode("utf-8")`** is a deterministic byte sequence
  for any `str` input (UTF-8 is byte-stable for ASCII task_ids, which
  is what `uuid.uuid4().hex[:12]` produces).
- **`int.from_bytes(digest[:4], "big")`** is byte-order-explicit; the
  `"big"` argument makes it independent of the host's native byte
  order (no `sys.byteorder` dependency).

### Cross-Process Test

Added `test_deterministic_seed_across_processes` and
`test_deterministic_seed_with_pythonhashseed_random` to
`tests/test_v7_5_reproducibility.py`:

```bash
$ for i in 1 2 3; do python3 -c \
    "from srs.runtime import _deterministic_seed; \
     print(_deterministic_seed('test_task_123'))"; done
992822634
992822634
992822634
```

The `PYTHONHASHSEED=random` test explicitly verifies that the seed is
invariant under hash randomization — a regression that replaces
`sha256` with `hash()` would fail this test.

### Cross-Python-Version Stability

The implementation uses only:

- `hashlib.sha256` — present and stable since Python 3.0.
- `int.from_bytes(bytes, "big")` — present and stable since Python 3.2.
- `str.encode("utf-8")` — present and stable since Python 2.x.

No version-specific behavior. The seed will be identical on Python
3.10, 3.11, and 3.12.

### Cross-OS Stability

The implementation does NOT use:

- `os.urandom` (would be `/dev/urandom` on Linux, BCryptGenRandom on
  Windows — both cryptographically random, NOT deterministic).
- `time.time()` / `time.perf_counter()` (host-clock dependent).
- `os.getpid()` (OS-dependent process id).
- `random.SystemRandom` (wraps `os.urandom`).

So the seed is byte-identical on Linux, macOS, and Windows.

## 3. Fix 2: Snapshot Determinism

### Problem

Two `store_state()` calls on a Runtime with the same in-memory state
must produce byte-identical snapshot files (modulo the inherently
time-based `snapshot_id` and `timestamp` fields). Without
`sort_keys=True` in the JSON serializer, Python's dict insertion order
determines the key order in the output — which is stable within a
single process but can vary across processes that build the dict in
different orders.

### Fix

`_atomic_write_json` in `srs/persistence.py` now defaults to
`sort_keys=True`:

```python
def _atomic_write_json(path: Path, data: Any, indent: int = 2,
                       sort_keys: bool = True) -> None:
    ...
    with os.fdopen(fd, "w") as f:
        # v7.5: sort_keys=True for byte-identical reproducible output.
        json.dump(data, f, indent=indent, default=str, sort_keys=sort_keys)
```

This applies to:

- `snap_*.json` (snapshot files) — written via `_atomic_write_json` in
  `save()`.
- `latest.json` (snapshot index) — written via `_atomic_write_json` in
  `save()`.
- `inflight_*.json` (in-flight state) — written via
  `_atomic_write_json` in `save_in_flight()`.

### Test

`test_snapshot_content_is_deterministic` and
`test_snapshot_bytes_are_deterministic_modulo_id_and_timestamp` in
`tests/test_v7_5_reproducibility.py`. The byte-level test normalizes
the two snapshots by replacing `snapshot_id` and `timestamp` with
placeholders and re-serializing with `sort_keys=True`, then asserts
the byte strings are identical.

## 4. Fix 3: JSON Output Determinism (sort_keys=True)

### Problem

The CLI emits JSON via `print(json.dumps(data, indent=2,
default=str))` in `srs/cli.py`. Without `sort_keys=True`, the same
`data` dict can produce different byte sequences across runs (because
dict insertion order varies if the dict is built differently — e.g.
loaded from a JSON file with key order A vs constructed in code with
key order B).

### Fix

All `json.dumps()` calls in `srs/cli.py` now use `sort_keys=True`:

1. `emit()` (lines 138–158) — the central output function used by
   `cmd_capabilities`, `cmd_execute`, `cmd_snapshot`, `cmd_recover`,
   `cmd_plan`, `cmd_list_kinds`, `cmd_self_test`.
2. `cmd_recover()` (line 321) — the inline `print(json.dumps(caps,
   ...))` in the human-readable branch.

`_atomic_write_json` in `srs/persistence.py` also defaults to
`sort_keys=True` (Fix 2 above), so all snapshot writes are sorted too.

`srs/types.py` already used `sort_keys=True` in `Task.fingerprint()`
(line 100) — no change needed there.

### Test

`test_cli_output_is_deterministic` and
`test_cli_capabilities_output_is_deterministic` in
`tests/test_v7_5_reproducibility.py`. The first runs
`execute identify 64 --budget 16` in two fresh home directories and
asserts the JSON output is identical after stripping `wall_time_ms`
and `task_id`. The second runs `capabilities` in two fresh homes and
asserts byte-identical stdout (no fields need stripping — a fresh home
has zero state, so the output is fully deterministic).

## 5. Fix 4: Execution History Ordering

### Problem

`Runtime.execution_history` is a list of dicts, appended to in
`execute()` call order. When saved to a snapshot, the list order is
preserved by JSON serialization (lists are ordered, so `sort_keys=True`
doesn't apply). The problem: two processes sharing a home directory
(one writes, the other loads and writes again) can produce different
list orders for the same logical set of executions, even though the
individual entries are identical.

### Fix

`Runtime.store_state()` in `srs/runtime.py` now sorts
`execution_history` by `(timestamp, task_id)` before persisting:

```python
sorted_history = sorted(
    list(self.execution_history),
    key=lambda e: (e.get("timestamp", 0.0),
                   str(e.get("task_id", ""))),
)
stats_snapshot = {**self.primitive_stats,
                  "execution_history": sorted_history,
                  "_total_tasks": self._total_tasks}
```

The sort is stable, so two entries with identical `(timestamp,
task_id)` preserve their insertion order. The in-memory list is left
in append order (the runtime's `recent_executions` capability still
returns the most-recent-first view); only the persisted form is
sorted.

### Test

`test_load_resave_preserves_content` in
`tests/test_v7_5_reproducibility.py` — saves a snapshot, loads it
into a fresh Runtime, re-saves, and asserts the content (modulo
`snapshot_id` / `timestamp`) is identical. The sort guarantees that
the load+resave round-trip is byte-stable.

| `test_deterministic_seed_across_processes` | `_deterministic_seed` returns the same value in 3 subprocess invocations. |
| `test_deterministic_seed_with_pythonhashseed_random` | The seed is invariant under `PYTHONHASHSEED=random` (catches regressions that replace `sha256` with `hash()`). |

| `test_two_independent_runtimes_same_result` | Two fresh Runtime instances executing the same task with the same `task_id` produce identical results (strongest end-to-end check). |

### Design Notes

- The cross-process tests spawn fresh `subprocess.run([sys.executable,
  ...])` invocations so they catch non-determinism from
  `PYTHONHASHSEED`, `os.getpid()`, and any other per-process state.
- The `PYTHONHASHSEED=random` test explicitly verifies that the seed
  is hash-randomization-invariant — a regression that replaces
  `sha256` with `hash()` would fail this test on the second run.
- The byte-identical snapshot test normalizes by re-serializing with
  `sort_keys=True` so that key order drift (which `sort_keys=True` in
  `_atomic_write_json` prevents) AND list-order drift in
  `execution_history` (which the `(timestamp, task_id)` sort in
  `store_state()` prevents) are both caught.
- The "two independent runtimes" test uses two fresh `TemporaryDirectory`
  home dirs so the advice table from runtime 1 doesn't carry over to
  runtime 2 (which would change `primitives_used` because the planner
  would short-circuit to `["Adv", ...]`).

## 11. Remaining Non-Determinism (Intentional)

These fields are **inherently** time- or process-based and CANNOT be
made deterministic without breaking their semantics. They are
documented in the README's "What is NOT Deterministic" table and
stripped by the reproducibility tests before comparison:

| Field | Source | Why non-deterministic |
|-------|--------|------------------------|
| `snapshot_id` | `sha256(str(time.time()))[:12]` | Wall-clock dependent — needed so two snapshots saved in the same second don't collide on the filesystem. |
| `snapshot.timestamp` | `time.time()` | Wall-clock dependent — needed so consumers can order snapshots chronologically. |
| `result.wall_time_ms` | `time.perf_counter()` | Process scheduling / system load — needed for performance reporting. |
| `task.task_id` | `uuid.uuid4().hex[:12]` | Random per-Task — needed so concurrent runs of "the same" task don't produce colliding query sequences. **Callers can override by setting `task.task_id` directly.** |
| `inflight_*.json.timestamp` | `time.time()` | Wall-clock dependent — needed so `resume_interrupted()` can pick the most recent in-flight task. |
| `capabilities().last_snapshot_id` | Inherits from `snapshot_id` | Wall-clock dependent. |
| `capabilities().recent_executions[].timestamp` | `time.time()` at `execute()` | Wall-clock dependent — needed for chronological ordering of recent executions. |

These are **NOT bugs** — they are documented, intentional sources of
non-determinism. The reproducibility tests verify that EVERYTHING ELSE
is deterministic.

## Out of Scope

The following items are NOT addressed by F9 (they belong to other
agents or future cycles):

- **`improve()` stale-advice bug** (R2.23 / R4.3): the advice table
  is keyed on `sha256(b"|".join(hypotheses))[:16]`, omitting
  `target_idx`. This is a CORRECTNESS bug (wrong advice returned for
  a different target), NOT a reproducibility bug — the wrong answer
  is deterministic. Deferred to a future fix agent.
- **Cross-Python-version snapshot compatibility**: snapshots written
  by Python 3.10 may not load cleanly in Python 3.12 if the
  `advice_table` or `primitive_stats` contains types that changed
  representation (e.g. `dict` ordering, `int` vs `float`). The
  v7.5 fixes make the WRITER deterministic; cross-version READER
  compatibility is a separate concern.
- **Cross-platform path normalization**: snapshot `path` field uses
  `str(fpath)` which is platform-specific (Linux `/`, Windows `\`).
  This affects the `latest.json` index, not the snapshot content.
  Could be normalized to `/`-separated in a future fix.
- **Wall-time-based fields**: `wall_time_ms`, `snapshot_id`,
  `timestamp` are documented as intentionally non-deterministic.
  Making them deterministic would require either pinning the wall
  clock (impossible) or replacing them with monotonic counters
  (would break their semantics — `timestamp` is used for
  chronological ordering of snapshots).
