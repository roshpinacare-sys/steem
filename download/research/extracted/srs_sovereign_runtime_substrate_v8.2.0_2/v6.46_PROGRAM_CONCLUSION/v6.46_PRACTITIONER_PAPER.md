# Five Primitives for Thinking About Computational Advantage

### An engineering taxonomy — not a theorem — for sorting "new paradigm" claims

**Z.ai Research**

---

## The Question

Every few months, a new computational paradigm is announced with a press release claiming a "quantum leap," a "neuromorphic breakthrough," a "quantum-inspired speedup," "counterfactual computation," or an "AI-native accelerator." Vendors ship SDKs. Conferences convene. Founders raise rounds. And the practitioner — the architect staring at a latency SLO, the R&D lead evaluating a proof-of-concept, the engineer choosing between a GPU, an FPGA, and a custom ASIC — is left with the same question every time: *is this actually an asymptotic improvement, or is it a re-packaging of something I already have?*

The honest answer is usually "it depends," but the practitioner does not have time to read every paper. They need a sorting framework: a small set of categories into which any claimed advantage can be dropped, so that the question becomes "which category does this fall into, and what does that category actually buy me on the axis I care about?"

This article proposes such a framework. It is **not a theorem.** After a long internal investigation (which culminated in an unsuccessful attempt to prove this as a closure theorem — see the discussion of limitations in Section 6), we concluded that the framework does not survive as a mathematical result. As a *theorem*, every claim we initially made was either falsified, already known, or hypothesis-dependent. As an *engineering taxonomy*, however, it has proven useful: it gives practitioners a shared vocabulary for asking the right question, and it tells them when to stop chasing. We were tempted, in earlier drafts, to market the framework as a "new theory of computation"; the reviewer feedback that rejected that framing was correct, and we have retreated to the more honest position that the framework's value is organizational, not deductive.

The framework consists of **five core primitives** — Compression (C), Adaptivity (A), Scheduling (S), Verification (V), and Execution (E) — that cover uniform single-machine computation, plus **two extensions** — Advice and Quantum — that lift the framework to non-uniform and quantum computation, respectively. Each primitive corresponds to a distinct resource axis. Each axis has standard lower-bound theorems already in the literature. The framework's value is organizational: it tells you, given a claimed advantage, which axis the advantage lives on, and therefore which theorem governs it.

We give the primitives informally. We give concrete engineering examples. We discuss when the framework applies and — more importantly — when it does not.

## Five Primitives

We use single-letter codes throughout. Each primitive has a formal complexity-class counterpart (mentioned parenthetically for the theorist reader), but the *engineering* definition is what matters.

**E — Execution (formally: P).** The baseline. A computation that runs in polynomial time on a single machine, sequentially, with no special tricks. Most of what your code does is E. The resource axis is wall-clock time. When you replace an O(n³) algorithm with an O(n log n) one — quicksort over bubble sort, FFT over DFT, suffix arrays over suffix trees for indexing — you are using E. The advantage comes from doing less work per unit input.

*Engineering example.* Replacing an O(n²) nested-loop join in a query planner with an O(n log n) hash join. This is the textbook case: the algorithm changes, the machine does not, and the asymptotic gain is a factor of n / log n.

**C — Compression (formally: L, with Kolmogorov complexity K as the information-theoretic floor).** Reducing the working state below the size of the input. The resource axis is *space*. When you replace a full materialized copy of your data with a succinct index, a Bloom filter, a learned index, a trie, a wavelet tree, or a compressed representation (gzip, zstd, Parquet columnar, Roaring bitmaps), you are using C. The Kolmogorov complexity K(f) of your function's behavior is the unbeatable floor: no representation of f uses fewer than K(f) bits (Li-Vitányi, 2008).

*Engineering example.* A learned index (Kraska et al., 2018) replaces a B-tree of several gigabytes with a small neural net (~kilobytes) that approximates the CDF of the keys. The asymptotic advantage is space: O(n) keys stored in O(polylog n) parameters. The price is approximation; the win is cache locality.

**S — Scheduling (formally: NC).** Reorganizing a sequential computation so that many operations can proceed in parallel. The resource axis is *depth* (parallel time). Brent's theorem (1974) — the foundational result — says that any computation with work W and critical-path length D can be executed on p processors in time O(W/p + D). The advantage comes from collapsing the depth, not from reducing the work.

*Engineering example.* A MapReduce pipeline that takes a 100 TB log scan from 100 hours (single-machine) to 1 hour (100-node cluster). Total work is unchanged. The asymptotic improvement is purely on the depth axis. If your bottleneck is wall-clock and you have spare hardware, S is the primitive you want.

**A — Adaptivity (formally: P^NP[log] = Θ₂^P; equivalently, adaptive query complexity).** Choosing your next query, sample, or probe based on the answers you have already received. The resource axis is *number of queries* (or samples, or probes). Active learning, multi-armed bandits, binary search, decision-tree algorithms, adaptive testing, and Bayesian optimization all live here. The advantage comes from gathering information *only where it matters*.

*Engineering example.* A recommendation system that, instead of serving random items to learn user preferences, picks the next item to maximize information gain about the user's taste vector (Dasgupta, 2004). On a 10⁶-item catalog, random exploration needs O(10⁶) impressions; adaptive exploration can identify the user's preference to within ε in O(d log(1/ε)) impressions, where d is the latent dimension. The asymptotic gain is on the *query axis*.

**V — Verification (formally: NP = PCP[O(log n), O(1)]).** Proving that a computation was done correctly using far fewer resources than the computation itself. The resource axis is *verification cost*. PCP-style verification, zk-SNARKs, STARKs, Merkle proofs, and probabilistically checkable proofs all live here. The PCP theorem (Arora et al., 1998) is the foundational result: any NP proof can be rewritten so that the verifier reads only O(1) bits and is fooled with probability ≤ ½.

*Engineering example.* A rollup on Ethereum posts a zk-SNARK proving that 10,000 transactions were processed correctly. The L1 verifier checks the SNARK in milliseconds, not the minutes that re-executing 10,000 transactions would take. The asymptotic gain is on the *verification axis*: verifier time goes from O(n) to O(log n) or O(1).

A useful summary table appears in Sidebar 1. The five primitives cover uniform, single-machine, worst-case, deterministic (or BPP — since BPP ⊆ P/poly by Adleman's theorem, randomized classical computation reduces to Advice) computation. Most industry code lives here. But not all of it does — and that is where the extensions come in.

## Two Extensions

The five-primitive framework, restricted to uniform single-machine computation, was the version we first attempted to prove as a closure theorem. It fails. We list the failures honestly in Section 6. The two most important failures — both already known in the literature — are *non-uniform advice* and *quantum computation*. We add them as extensions rather than as primitives 6 and 7 in the core set, because they correspond to *changes in the computational model*, not changes in the resource axis. Practitioners should think of them as "model extensions" you opt into when your hardware or input distribution permits.

**Advice (formally: P/poly; the foundational result is Karp-Lipton, 1980).** A polynomial-length string, depending only on the input size n, that is given to the algorithm for free. The string is non-uniform: it is different for each n. This is a model change: the algorithm receives input that the "machine" has pre-baked into it. The advantage is that, for some problems, a poly(n)-bit advice string can encode an exponential amount of precomputed structure. The cleanest demonstration: there are *undecidable* unary languages in P/poly (the standard Arora-Barak exercise 6.5), because the advice string can encode the halting pattern at each length.

*Engineering interpretation.* "Advice" is the formal name for any precomputed table, machine-learned parameter set, hardware lookup ROM, or pretrained model that is shipped with the binary and applied uniformly across inputs of a given size. If you ship a 10 GB pretrained model that lets a 1 KB inference outperform a hand-written heuristic at scale, that is P/poly. The asymptotic advantage is real; the catch is that someone (or something) had to do the work to produce the advice string, and that work is *not* charged to your query-time budget.

*Status.* Honest: Advice escapes the 5-primitive framework. It is an extension, not a derived primitive. We include it because almost all modern ML-deployed systems use Advice implicitly — the pretrained weights are the advice string.

**Quantum (formally: BQP).** A quantum computer running a polynomial-size, polynomial-depth circuit over a universal gate set. Foundational results: Bernstein-Vazirani (1997) defined BQP; Shor (1994) showed factoring is in BQP (conjectured not in BPP); Grover (1996) showed unstructured search in O(√n) quantum queries.

*Engineering interpretation.* Quantum computation is a model extension: the bits become qubits, the operations become unitary, and the resource axis gains a new dimension (entanglement). For specific problems — factoring, unstructured search, certain linear-algebra tasks (HHL, recommendation systems) — quantum gives a *provable* asymptotic advantage (under standard conjectures). For most industry problems, it does not. The framework tells you: if your claimed advantage is "quantum," it should reduce to BQP, and you should be able to point to the specific quantum subroutine (Shor, Grover, QAOA, VQE, etc.) that delivers the speedup.

*Status.* Honest: BQP's relationship to P/poly is open (Aaronson, 2010). It is possible that BQP ⊆ P/poly, in which case Quantum reduces to Advice and the framework collapses back to 6 primitives. It is also possible that BQP ⊄ P/poly, in which case Quantum is genuinely a 7th primitive. We don't know. We treat Quantum as an extension because it is operationally distinct: it requires different hardware, different algorithms, and different lower-bound techniques from the 5 classical primitives.

## Using the Framework

We give three concrete examples of how the framework changes design decisions. In each case, the value is *not* in the framework itself but in the question it forces: *which primitive gives the advantage?*

**Database system design.** You are designing a columnar OLAP engine and want a 10× latency improvement over the incumbent on TPC-H Q1 (a large aggregation scan). The naïve approach is to throw more cores at the scan (S). Brent's theorem tells you the speedup is bounded by 1/D, where D is the depth of the aggregation. For Q1, the aggregation is essentially linear, so D = O(log n), and S gives you a good but bounded gain — perhaps 4× on 16 cores. To get past that, ask the framework: what other primitive applies? The answer is C: columnar compression (run-length encoding, dictionary encoding, bit-packing) reduces the bytes scanned from O(n) to O(K(n)), where K(n) is the entropy of the column. The combination of C (smaller working set) and S (parallel scan over the smaller set) is what gives the 50× gains that modern columnar engines (ClickHouse, DuckDB, Presto) achieve over row stores. The framework correctly predicts that pure-S approaches (sharding a row store) plateau quickly, and that the asymptotic win must come from C. A second, less-obvious move is to use V: skip-scan with a zone-map or Bloom-filter index lets the engine *verify* in O(1) that a row-group cannot contain a matching row, without scanning the row-group at all. Zone maps are a V primitive in disguise: they certify "definitely not here" cheaply.

**ML system design.** You are designing a content moderation system that must classify 10⁹ images per day with a 100 ms p99 latency budget. The baseline is a single large transformer (E), which costs ~50 ms per image on an H100. To meet the budget on 10⁹ images, you would need ~580 H100s running flat. The framework asks: which primitive reduces the per-image cost? The answer is A (adaptivity) composed with V (verification). Use A: a small cheap "router" model classifies each image as obvious-benign, obvious-violating, or ambiguous; only the ambiguous images (perhaps 5%) go to the large model. The router makes an *adaptive decision* based on the image — a one-bit query that costs ~1 ms. The expected per-image cost drops from 50 ms to 50 ms × 0.05 + 1 ms = 3.5 ms, a 14× improvement. Use V: for the images the large model classifies as violating, generate a SNARK or a probabilistic certificate that downstream consumers (legal review, user-appeal pipeline) can verify in O(1) without re-running the model. The framework's prediction: the asymptotic win comes from A and V, not from buying more GPUs. The 580-H100 baseline is a pure-E solution; the 4-H100 solution that meets the same SLO is A+V. The framework names the gap.

**Distributed system design.** You are designing a configuration service that must maintain consistency across 5 datacenters. The baseline is Paxos (Lamport, 1998), which gives O(n) message complexity per decision for n replicas. You read a paper claiming a "new paradigm" that achieves O(log n) message complexity by using a "counterfactual broadcast." The framework asks: which primitive is being used? Counterfactual reasoning reduces to A (adaptive query) composed with V (verification) — the protocol adaptively chooses which replicas to query based on previous answers (A), and verifies responses with short certificates (V). The "new paradigm" is a re-packaging of two known primitives; the O(log n) gain is the standard adaptive-query gain (Auer et al., 2002, for bandits; Dasgupta 2004 for active learning). The framework's prediction: this is not a new primitive; it is A+V applied to a specific problem. The practitioner's takeaway: do not over-invest in the "new paradigm" framing; treat it as a known pattern and focus engineering effort on the actual implementation — failure handling, asynchrony, etc., which are NOT covered by the framework (see Section 6).

A meta-pattern across these examples: **when the framework identifies two primitives, the right architecture usually composes them.** Pure-S systems plateau on Amdahl's law; pure-A systems are bottlenecked on the per-query cost; pure-V systems assume an untrusted prover that you must still execute somewhere. The interesting asymptotic wins in modern systems — columnar OLAP, federated ML inference, distributed ledgers — almost always come from composing two or three primitives, not from a single one.

## What NOT to Build

The framework's most valuable use is *negative*: it tells you when an advantage is **not** achievable. The rule is simple. If your claimed advantage does not reduce to one of the 5 primitives (plus Advice and Quantum, if applicable), then **no asymptotic advantage exists on the standard axes**, and your system will be at most a constant-factor improvement over the baseline. Constant factors matter, but they should be optimized with constant-factor engineering (better caches, faster kernels, lower overhead), not marketed as a "new paradigm."

We give three examples of "new paradigm" claims that the framework exposes as re-packagings.

**Quantum-inspired classical algorithms.** Several papers (e.g., Tang, 2019) demonstrate "quantum-inspired" classical algorithms for recommendation and linear algebra that achieve the same asymptotic complexity as their quantum counterparts (HHL, quantum recommendation systems) — but run on classical hardware. The framework's analysis: the quantum algorithms were using S (parallelism in the quantum Fourier transform) composed with A (adaptive sampling for matrix approximation). The classical counterparts use the *same* primitives (randomized SVD, leverage-score sampling are both A) — they just drop the requirement of quantum hardware. The "quantum-inspired" framing is marketing; the algorithmic content is A.

**Counterfactual reasoning.** Some "counterfactual computation" frameworks claim to extract information from a computation that did not actually run. The framework's analysis: counterfactual queries reduce to A (adaptive query complexity) composed with V (probabilistic verification). The "did not run" framing is a story; the underlying mechanism is standard adaptive sampling. No new primitive.

**Neuromorphic computing.** Spiking neural networks and neuromorphic chips (Loihi, SpiNNaker, TrueNorth) are sometimes marketed as a "fundamentally new" computational model. The framework's analysis: neuromorphic computation is a *hardware implementation* of algorithms that use S (event-driven parallelism), A (adaptive spike routing), and C (sparse representation). The asymptotic advantage, if any, is on these standard axes — typically S and C, when the workload is sparse and event-driven. The framework tells the practitioner: do not expect a "neuromorphic primitive" beyond {C, A, S, V, E}. If your workload is dense and synchronous, neuromorphic hardware will likely be slower than a GPU.

**"AI-native" databases.** A class of products markets itself as "AI-native" databases that use machine learning to "fundamentally rethink" query execution. The framework's analysis: the algorithmic content is almost always C (learned indexes replacing B-trees) composed with A (adaptive query planning that learns from workload traces). Both are real, useful primitives. But neither is new in the asymptotic sense — learned indexes have the same Kolmogorov-floor space bound as any other compressor, and adaptive query planning is the same primitive Auer et al. (2002) formalized for bandits. The "AI-native" framing is marketing; the engineering content is C+A. The framework tells the practitioner: evaluate these systems on whether their C and A implementations are actually better than the incumbent's, not on the "AI-native" label.

The general rule: when you encounter a "new paradigm," ask *which of the 5 (or 7) primitives does this use?* If you cannot answer in one sentence, the claim is likely either (a) a re-packaging of known primitives or (b) unsupported by current theory. In case (a), proceed with engineering. In case (b), demand evidence — typically a separation theorem or a benchmark on a workload that genuinely exercises the claimed primitive. A useful sanity check: if the vendor's white paper does not name a specific resource axis (time, space, depth, queries, verification cost) on which the advantage is measured, treat the claim with maximum skepticism. Real asymptotic advantages are stated in terms of specific axes; "fundamentally better" is not a complexity claim.

## Honest Limitations

We have tried to be honest throughout. This section is the most important, because the framework's credibility depends on the practitioner knowing exactly where it stops applying.

**The framework is an engineering taxonomy, not a mathematical theorem.** We attempted to prove it as a closure theorem (a claim that every computational advantage reduces to one of the 5, then 7, primitives) and the proof failed. The falsifying counterexamples — non-uniform advice (Karp-Lipton, 1980), interactive proofs (Shamir, 1992, IP = PSPACE), distributed consensus (Fischer-Lynch-Paterson, 1985), and average-case analysis (Spielman-Teng, 2001) — are all standard results in the literature. We attempted to extend the framework to absorb these counterexamples, ending with a 7-primitive set {C, A, S, V, E, Advice, Quantum}. An independent PC-style review (conducted internally, modeling STOC/FOCS standards) concluded that this 7-primitive closure is **hypothesized, not proven** — it depends on the open question of whether BQP ⊆ P/poly. We have not snuck the theorem back in. The taxonomy's value is organizational, not deductive.

**The framework depends on the Bold Church-Turing thesis and physical realizability.** It assumes that any physically realizable computation can be simulated by a Turing machine with polynomial overhead. This excludes hypercomputation (Zeno machines, real-valued "blur" computers), unbounded-prover interactive proofs (which require a prover more powerful than any Turing machine), and post-quantum theories (PR boxes, indefinite causal order) unless those are themselves reducible to BQP. If your claimed advantage relies on one of these, the framework does not apply.

**The framework does not handle average-case analysis.** Spielman and Teng's smoothed analysis (2001) shows that algorithms with exponential worst-case complexity (the simplex method, k-means) can have polynomial average-case complexity on realistic input distributions. The framework's 5 primitives are worst-case notions. Average-case gains are real and important, but they live outside the framework. A practitioner who claims an average-case advantage should cite Spielman-Teng, not the framework.

**The framework does not handle distributed asynchrony.** The FLP impossibility result (Fischer-Lynch-Paterson, 1985) shows that asynchronous distributed consensus is impossible with even one faulty process. The framework's 5 primitives assume a single machine; distributed computation requires an extension. The honest practitioner treats distributed-system design as a separate field (Lynch, 1996) and uses the framework only for the per-node resource analysis.

**The framework does not handle proof complexity.** Some "new paradigm" claims involve new proof systems (deep inference, Frege systems, extended Frege). These are out of scope; the framework's V primitive is restricted to PCP-style verification. Use Cook-Reckhow (1979) and the proof-complexity literature.

If your problem falls into one of these excluded categories, the framework will not help you. Use the appropriate specialized theory (Lynch for distributed, Spielman-Teng for average-case, Cook-Reckhow for proof complexity, etc.).

## Conclusion

The framework's value is organizational, not theoretical. It helps practitioners ask the right question — *which primitive gives the advantage?* — rather than chasing "new paradigms" that, on inspection, reduce to known primitives. The five core primitives {Compression, Adaptivity, Scheduling, Verification, Execution} cover the standard resource axes for uniform single-machine computation. The two extensions {Advice, Quantum} cover non-uniform and quantum computation, respectively. Each primitive has a foundational theorem (Kolmogorov complexity, Brent's theorem, PCP, etc.) that gives the lower bound; the framework's contribution is the *organization*, not the theorems.

When you encounter a new computational paradigm, ask: *which primitive does this use?* If the answer is one of {C, A, S, V, E, Advice, Quantum}, proceed with engineering — the asymptotic gain is governed by a known theorem. If the answer is "none of the above," proceed with skepticism — the claim is likely either a constant-factor improvement dressed in paradigm language, or an unsupported conjecture. If the answer is "a new primitive," demand evidence: a separation theorem, a benchmark, a lower-bound proof.

The framework will not make you a better engineer. It will, however, save you from chasing phantoms — and that, in a field increasingly crowded with "new paradigms," is no small thing. The cost of using it is small: the five core primitives plus two extensions fit on a single page (Sidebar 1), and the negative test ("does this reduce to one of the seven?") takes a few minutes to apply. The cost of *not* using it is large: practitioners who chased "quantum-inspired" speedups that turned out to be classical randomized SVD, or "neuromorphic" advantages that turned out to be sparse-linear-algebra gains, can lose quarters of engineering effort. The framework's value, in the end, is the same as any good taxonomy: it does not tell you what to build, but it tells you, quickly and reliably, what *not* to build.

## Sidebar 2: When the Framework Fails

The framework does **not** apply in the following cases. Use the appropriate specialized theory instead.

- **Average-case complexity.** Use Spielman-Teng (2001) smoothed analysis; Impagliazzo (1995) average-case complexity.
- **Distributed asynchrony with failures.** Use Lynch (1996), *Distributed Algorithms*; FLP impossibility (Fischer-Lynch-Paterson, 1985).
- **Interactive proofs with unbounded provers.** Use Shamir (1992), IP = PSPACE; Goldwasser-Micali-Rackoff (1985).
- **Algebraic complexity.** Use Valiant (1979) VP/VNP; Bürgisser (2000).
- **Proof complexity.** Use Cook-Reckhow (1979); Razborov (1998).
- **Hypercomputation.** Excluded by the Bold Church-Turing thesis; framework does not apply.
- **Post-quantum theories** (PR boxes, indefinite causal order). Conditional on whether they reduce to BQP. If they do not, framework does not apply.
- **Continuous / analog computation.** Outside the Boolean / Turing-machine model; framework does not apply.
- **Unbounded-prover protocols.** Excluded by physical-realizability assumption.

When in doubt, ask: *does my problem live in P, NP, P/poly, BQP, NC, L, Θ₂^P, or PSPACE?* If yes, the framework applies. If your problem lives in PSPACE (interactive proofs with unbounded provers), in distributional classes (AvgP), or in distributed failure models (which have no clean complexity-class correspondence), the framework does not apply and you need a specialized theory.
