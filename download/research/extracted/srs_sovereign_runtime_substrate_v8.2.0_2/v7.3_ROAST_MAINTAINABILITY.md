## 1. Executive Summary

The v7.2 SRS runtime is *correct* (the F1/F2 fix agents did real work: verification is no longer theatre, the planner matches the pipeline, advice short-circuits). But "works today" is not the same as "can be maintained for the next three years by people who didn't write it." On that axis the runtime scores **6/10**, not the 9/10 the original architect self-assigned.

Three structural problems dominate:

1. **Algorithmic duplication.** The exact same alive-set pruning + greedy-split-input loop is copy-pasted across `primitives/adaptivity.py`, `primitives/scheduling.py`, and `pipeline.py:adaptivity_stage`. The `hash_bit` helper is re-implemented with an extra parameter in `primitives/adversarial.py`. The `[hashlib.sha256(f"h{i}".encode()).digest() for i in range(N)]` hypothesis-builder appears 18 times in production code and 34 times in `test_srs_runtime.py` alone. Any future fix to that loop has to be applied in three places; one missed copy silently drifts and tests can't catch it because each copy is exercised by different tests.

2. **A 123-line, 24-branch god function.** `Runtime.execute` (`runtime.py:57`) handles resume-state restoration, planner invocation, pipeline construction (an 8-branch `if/elif` chain over primitive names), in-flight state save, `try/finally`, primitive-stat accumulation, execution-history truncation, and advice seeding — all in one method. There is no seam for unit-testing any of those concerns in isolation. Adding a single new primitive means editing this function *and* the planner's `estimate_cost` *and* the planner's `plan` candidate enumeration *and* the pipeline stage dispatch — four files, no compiler-checked mapping between them.

3. **Fix-tag comment pollution combined with no developer docs.** Source comments are sprinkled with `# R1.1 fix:`, `# R4.4 fix:`, `# R5.6 fix:` references to external roast reports that a new contributor has no way to resolve. There is no `CONTRIBUTING.md`, no `CHANGELOG.md`, no architecture doc for the `srs/` subpackage, and the `DEVELOPER_GUIDE.md` covers only `kernel/`, `cognition/`, etc. — not `srs/`. The fix-tag convention made sense during the v7.1→v7.2 transition; it becomes technical debt the moment someone outside the original team touches the code.

Compounding these: the CI workflow lints, type-checks, and security-scans `kernel/ cognition/ verification/ simulation/ governance/ self_healing/ tests/` but **omits `srs/` entirely** (`.github/workflows/ci.yml:32,36,40`). The runtime package — the canonical entry point advertised in the README — has zero automated quality gates beyond pytest. Version is triple-sourced (`__init__.py`, `runtime.py:251`, `pyproject.toml`). Private member `AdviceTable._table` is accessed directly from `runtime.py` (4 sites) and `cli.py` (1 site), breaking encapsulation.

The runtime is salvageable. The fixes are mechanical, well-scoped, and listed in §7. None require architectural rewrites. But until they land, every future change carries an outsized regression risk because the duplication + god-function + fix-tag-comments combo makes partial fixes invisible.

## 4. Top 3 Maintainability Risks (Detailed)

### Risk 1: Duplicated alive-set pruning algorithm across 3 sites

**Files:** `primitives/adaptivity.py:27-46`, `primitives/scheduling.py:30-52`, `pipeline.py:171-197`

The core "adaptive identification" algorithm — keep an `alive` set, sample 20 candidate inputs, pick the one that most evenly splits the alive set by hash_bit response, query the target, prune the alive set — is implemented three times. The three implementations are not textually identical (variable names differ: `hypotheses` vs `hyps`, `target_idx` vs `target`, `budget` vs `effective_budget`), but the algorithm is the same.

**Why this is the top risk:**

- Any future fix to the algorithm (e.g., switching from random sampling to a deterministic maximin strategy, or replacing `hash_bit` with a real cryptographic oracle) must be applied in three places.
- Each copy is exercised by a different test suite: `adaptivity.py` by `test_adaptivity_*`, `scheduling.py` by `test_scheduling_*`, `pipeline.py:adaptivity_stage` by `test_pipeline_*`. A partial fix that updates only `adaptivity.py` will pass all of `test_adaptivity_*` while silently leaving the pipeline's copy broken — and the pipeline is what `Runtime.execute` actually calls.
- The `scheduling.py` copy has an additional wrinkle: it computes `parallel_depth = max(1, ceil(log2(N) / log2(n_workers)))` per iteration and adds it to `depth`. If a maintainer "simplifies" by extracting the shared loop into a helper, they must remember to preserve this side-effect — but the side-effect is the only thing distinguishing scheduling from adaptivity, so the helper extraction is non-trivial.
- The `pipeline.py:adaptivity_stage` copy adds an early-return (`if state.answer is not None: return`) for the R4.5 "A defers to E" fix. This is exactly the kind of fix that gets lost in duplication: a future maintainer extracting a shared helper might preserve the early-return in the helper (breaking the standalone primitive) or omit it (breaking the pipeline's short-circuit).

**Impact estimate:** Probability of regression per algorithm-touch = ~50% (3 sites, each with a ~17% chance of being missed). Expected cost: 1-2 hours of debugging per missed site, plus the silent-wrong-answer risk if the missed site is the pipeline's.

**Fix:** Extract `primitives/_splitting.py`:

```python
def pick_best_split_input(hyps, alive, rng, n_features, n_candidates=20, hash_fn=hash_bit):
    """Return (best_x, work_done) — the input that most evenly splits `alive`."""
    best_x, best_score, work = None, float("-inf"), 0
    for _ in range(n_candidates):
        x = rng.getrandbits(n_features)
        zeros = sum(1 for h in alive if hash_fn(hyps[h], x) == 0)
        ones = len(alive) - zeros
        score = -max(zeros, ones)
        if score > best_score:
            best_score, best_x = score, x
        work += len(alive)
    return best_x, work

def prune_alive(hyps, alive, x, y, hash_fn=hash_bit):
    """Return new alive set: only hypotheses whose hash_fn(h, x) == y."""
    return {h for h in alive if hash_fn(hyps[h], x) == y}
```

Call these from all three sites. Total LOC reduction: ~30 lines. Drift risk: zero (one implementation).

### Risk 2: God function `Runtime.execute` (123 lines, 24 branches)

**File:** `runtime.py:57-179`

`Runtime.execute` does, in order: compute `t0`; restore RNG state for resume (5 lines, 3 branches); call `plan()` (4 lines); reorder primitives to put Adv first and drop E when A is present (5 lines, 2 branches); build the `Pipeline` by dispatching over primitive names (16 lines, 8 branches); save in-flight state (4 lines); `try: pipe.execute(...) ... finally: clear_in_flight` (20 lines, 1 branch); update `primitive_stats` (8 lines, 1 branch); append to `execution_history` and truncate (7 lines, 1 branch); seed advice if applicable (5 lines, 2 branches); return result.

**Why this is the #2 risk:**

- **Untestable in isolation.** To test "does `execution_history` truncate at 100?" you must construct a `Runtime`, build a `Task`, call `execute` 101 times, and check the list length. You cannot test the truncation logic directly because it's inlined into the method. Same for resume-state restoration, stats accumulation, and advice seeding.
- **Coupling cascade.** Adding a new primitive (say, `M` for "memoization") requires editing: (a) `pipeline.py` to add `M_stage`, (b) `runtime.py:_build_pipeline` to add `elif p == "M": pipe.add("M", m_stage)`, (c) `planner.py:estimate_cost` to add `elif p == "M": ...`, (d) `planner.py:plan` candidate enumeration to add `M` to candidate sets, (e) `planner.py:PRIMITIVE_BOUNDS` documentation, (f) `cli.py` choices lists. Six files, no compiler-checked mapping. A missed edit produces a silent `KeyError` or `AttributeError` at runtime, not at import time.
- **Resume logic is fragile.** The `try/except (TypeError, ValueError, IndexError)` at line 80 catches RNG-state deserialization errors and falls back to a fresh seed. This is the right behavior, but it's three lines buried in a 123-line method — easy to break by accident.
- **Stats and history updates run outside the try/finally.** If `pipe.execute` succeeds but `r.correct` raises (e.g., due to a custom Result subclass), the in-flight state is cleared (good) but stats are never updated (bad — the user sees a stale `capabilities()` report). The intent is "stats are best-effort," but that intent is not documented.
- **The 8-branch `if/elif p == "E"/"C"/"A"/"S"/"V"/"Adv"/"Q"` pipeline-builder** is a textbook case for a dispatch table. It's currently the only way to map a primitive name to a stage function, and it lives inside `execute` — so it's rebuilt on every call. A module-level `STAGE_DISPATCH: Dict[str, Tuple[Callable, Dict]]` would be faster (no rebuild) and grep-able.

**Impact estimate:** Every new primitive added to the runtime costs ~2 hours of editing across 6 files, with a ~20% chance of a silent dispatch miss. Every refactor to resume/stats/history logic risks an unrelated regression in the other concerns inlined into `execute`.

**Fix:** Extract 5 private methods:

```python
def _restore_rng_for_resume(self, task: Task) -> Tuple[random.Random, int]:
    """Return (rng, skip_queries) — restored from in-flight state if resume=True."""

def _build_pipeline_from_plan(self, ordered: List[str]) -> Pipeline:
    """Dispatch primitive names to stage functions via STAGE_DISPATCH table."""

def _run_pipeline_with_recovery(self, task, rng, skip_queries, n, axis, cost) -> Result:
    """try/finally wrapper: save in-flight, run, clear on success."""

def _accumulate_primitive_stats(self, primitives: List[str], result: Result) -> None:
    """Update self.primitive_stats — best-effort, never raises."""

def _seed_advice_on_success(self, task: Task, result: Result) -> None:
    """If identify + correct, seed advice table for future reuse."""
```

`execute` becomes ~15 lines orchestrating these. Each helper is independently testable.

### Risk 3: Fix-tag comment pollution + missing developer docs

**Files:** `pipeline.py` (15 fix-tag comments), `runtime.py` (11), `planner.py` (8), `persistence.py` (9), `cli.py` (12), `types.py` (3), `improvement.py` (2), `primitives/advice.py` (4). Total: **64 fix-tag comments** referencing `R1.x`, `R3.x`, `R4.x`, `R5.x` roast finding IDs.

**Why this is the #3 risk:**

- **A new contributor cannot resolve `R1.1` without finding the original roast report.** The roast reports (`v7.2_ROAST_ARCHITECTURE.md`, etc.) exist in the repo, but nothing in the source code points to them. The fix-tag comments are essentially breadcrumbs to documentation that lives elsewhere.

## 8. Summary

The v7.2 SRS runtime is functional and honest (the F1/F2 fix agents did real work). But it is not yet maintainable. The three structural problems — duplicated algorithm, god function, fix-tag comment pollution — are not bugs; they are slow-acting regressors. Each future feature added without addressing them increases the surface area for silent drift.

The fixes are mechanical (§7.1-7.14 total ~6 hours of refactoring) and well-scoped. The documentation work (§7.15) is larger but independent. None require architectural rewrites. All preserve backward compatibility (with deprecation warnings where needed).

**Recommendation:** Land §7.1-7.4 (the structural refactors) before any new primitive is added. Land §7.8-7.9 (CI + versioning) immediately — they are 15-minute changes that prevent real bugs. Land §7.10-7.15 (docs + fix-tag retirement) before the next roast cycle, so v7.3 doesn't add another 64 fix-tag comments on top of the existing 64.

**Maintainability score: 6/10.** Path to 8/10: complete §7.1-7.4, §7.6-7.9, §7.15. Path to 9/10: also complete §7.5, §7.10-7.14. Path to 10/10: not achievable without a real type system (mypy strict mode) and property-based tests (hypothesis) — out of scope for a refactor cycle.
