## 1. Executive Summary

The SRS v7.4 CLI is **minimally accessible but not i18n-ready**. It scores **5 / 10** on the R16 accessibility rubric. The runtime does almost nothing actively hostile to disabled or international users — there are no ANSI color codes, no spinners, no animations, and the CLI is by definition keyboard-driven — but it does almost nothing *helpful* either. The most damaging failures are:

1. **Timestamps are raw epoch floats** (`"timestamp": 1784313766.2976105`) in every persisted snapshot, every `recent_executions` entry, and every in-flight record. Humans cannot read them, screen readers read them digit by digit, and they carry no time-zone information.

2. **The `--format human` flag is silently ignored** by `cmd_capabilities` and `cmd_recover`. Users who explicitly ask for human-readable output get raw JSON, which is the worst of both worlds: too noisy for a human glance and not valid for a screen reader to navigate semantically.

3. **Error messages leak internal roast IDs** (`"(R10.2 fix: prevents OOM)"`, `"(R10.2 fix)"`) and **half-open interval math notation** (`"out of range [0, {n})"`) into user-facing output. Non-native English speakers and end users have no context for "R10.2" — it's developer-internal scaffolding that should never have escaped into production messages.

4. **No `encoding="utf-8"` is declared on any `open()` call** across 13 file I/O sites in `persistence.py` and `runtime.py`. On Linux and macOS this happens to work because the default encoding is UTF-8; on Windows (where the default is `cp1252`) any non-ASCII payload byte will raise `UnicodeDecodeError` on load, bricking the runtime. There is no platform-portability story.

5. **Zero i18n readiness**: every user-facing string is an inline f-string with no `gettext`/`_()` wrapping, no message catalog, no message IDs. Translating the CLI to Spanish, German, Japanese, or Arabic would require rewriting every `print(f"Error: ...")` site and every `raise ValueError(f"...")` site by hand. There is no path from here to a localized release that doesn't involve a multi-week refactor.

The remaining issues are lesser but still real: a non-ASCII em-dash (`—`, U+2014) in the `--help` banner, a version-string mismatch (CLI description says "v7.3" while `__version__` is `"7.4.0"`), WARNING logs that bleed through `--format json` into stderr and break JSON consumers, locale-naive `sorted()` calls, and a `--format` flag that only works *before* the subcommand with no "did you mean?" hint.

**Top-line recommendation:** ship v7.5 with (a) ISO 8601 UTC timestamps everywhere, (b) a real human-format renderer for `capabilities` and `recover`, (c) jargon-stripped error messages, (d) `encoding="utf-8"` on every `open()` call, and (e) a `gettext`-based message-ID layer for the top 30 user-facing strings. That sequence alone would move the score from 5 to 8.

## 3. Top 3 Accessibility Failures (Detailed)

### Failure 1: Timestamps are raw epoch floats everywhere (R16.4, CRITICAL)

**Where:** `runtime.py:463` (`"timestamp": time.time()` in `execution_history`), `runtime.py:539-540` (`Snapshot(snapshot_id=hashlib.sha256(str(time.time()).encode())...), timestamp=time.time()`), `persistence.py:510` (`"timestamp": time.time()` in `save_in_flight`), `persistence.py:523` (same), and the `recent_executions` array surfaced by `capabilities()`.

**What the user sees:** Running `srs capabilities` emits:

```json
"recent_executions": [
  {
    "task_id": "01fbaeb544b9",
    "kind": "compute",
    "correct": true,
    "queries": 16,
    "wall_time_ms": 1.9010080000152811,
    "primitives": ["E"],
    "timestamp": 1784313766.4212925
  }
]
```

**Why this is the worst accessibility failure:**

1. **Humans cannot read `1784313766.4212925`.** There is no calendar that accepts this format directly. The user has to mentally run `date -d @1784313766` (which gives `Mon Jan 13 22:05:30 UTC 2025` for the test run) or paste it into a converter. For an operator debugging a 3 a.m. incident, this is friction they do not need.

2. **Screen readers read it digit by digit.** NVDA and VoiceOver both default to reading long numbers as individual digits: "one seven eight four three one three seven six six point four two one two nine two five". That's 18 words for a single timestamp. A `recent_executions` array with 5 entries becomes 90 words of pure timestamp noise before any actual content is heard.

3. **No time-zone information.** The float is `time.time()` which is UTC seconds since epoch, but there's no field saying so. A user in Tokyo and a user in New York see the same number and have no way to know whether it's local time, UTC, or something else. The `Snapshot.timestamp` field documentation says nothing about time zone.

4. **No ISO 8601 compliance.** ISO 8601 (`2025-01-13T22:05:30Z`) is sortable lexicographically, grep-able, and directly parseable by every programming language's standard library. The epoch float is none of these.

5. **Breaks log correlation.** The logging module uses `datefmt="%H:%M:%S"` (no date, no tz — see R16.5), while `capabilities()` uses epoch floats. The two timestamp representations cannot be cross-referenced without conversion.

**Fix:** Replace every `time.time()` in user-facing or persisted output with `datetime.now(timezone.utc).isoformat().replace("+00:00", "Z")` (the `Z` suffix is the canonical ISO 8601 UTC indicator). For backward compatibility, also include an `epoch_s` float alongside the ISO string. Update the `Snapshot` docstring to state "Timestamps are UTC, ISO 8601 format."

### Failure 2: `--format human` is silently ignored by `capabilities` and `recover` (R16.2, R16.3, HIGH)

**Where:** `cli.py:210-218` (`cmd_capabilities`) and `cli.py:319-321` (`cmd_recover`).

**What the user sees:** `python3 srs/cli.py capabilities --format human` (or with `--format human` before the subcommand, since that's the only place it works — see R16.13) emits the exact same JSON as `--format json`. The "human" branch of the `if` statement is dead code:

```python
def cmd_capabilities(args: argparse.Namespace) -> int:
    """Print capability report."""
    rt = Runtime(home=args.home)
    c = rt.capabilities()
    if getattr(args, "format", "human") == "json":
        emit(args, c)
    else:
        emit(args, c)  # capabilities is already a dict; emit as JSON
    return 0
```

Both branches call `emit(args, c)` with no `human_text` argument. The `emit` function then falls back to `print(json.dumps(data, indent=2, default=str))` regardless of the requested format.

**Why this is an accessibility failure:**

1. **The `--format human` flag is a contract with the user.** A user who passes it is explicitly saying "I am a human, please format for me." Silently ignoring that request and emitting JSON is a lie. It's worse than not having the flag at all, because it gives users the false impression that they have control over the output format.

2. **JSON is hostile to screen readers.** A screen reader reading `{"version": "7.4.0", "primitives": ["E", "C", "A", "S", "V", "Adv", "Q"], "total_primitive_runs": 25, ...}` hears every brace, bracket, quote, comma, and colon as a separate token. The actual information ("25 primitive runs, 0 tasks, 92% success rate") is buried under syntax noise.

3. **The `recover` command is the worst case.** A user runs `srs recover` after a crash, desperately wanting to know "did my snapshot survive? is my interrupted task resumable?". Instead of a one-line answer, they get 80+ lines of JSON with `sort_keys=True` (so the keys are alphabetical, not in priority order). The information they need (`last_snapshot_id`, `interrupted_tasks`) is buried at lines 30 and 50 of the dump.

4. **There is no escape hatch.** A screen reader user cannot get a concise summary even by piping through `head` or `jq`, because the JSON is on stdout and the summary header (`"Recovered:"`) is on the same stream.

**Fix:** Implement real human renderers:

```python
def cmd_capabilities(args):
    rt = Runtime(home=args.home)
    c = rt.capabilities()
    if getattr(args, "format", "human") == "json":
        emit(args, c)
    else:
        print(f"SRS Runtime v{c['version']}")
        print(f"  Tasks executed: {c['total_tasks']}")
        print(f"  Primitive runs: {c['total_primitive_runs']}")
        print(f"  Success rate:   {c['success_rate']*100:.1f}%")
        print(f"  Advice entries: {c['advice_entries']} ({c['advice_size_bytes']} bytes)")
        print(f"  Snapshots:      {c['snapshots']} (last: {c['last_snapshot_id']})")
        print(f"  Interrupted:    {c['interrupted_tasks']}")
        print()
        print("Per-primitive stats:")
        for p in sorted(c['primitive_stats'].keys()):
            s = c['primitive_stats'][p]
            print(f"  {p:4}  runs={s['runs']:3}  ok={s['successes']:3}  "
                  f"queries={s['total_queries']:4}  time={s['total_wall_ms']:.1f}ms")
    return 0
```

The key properties: (a) every line has a labeled field (`Tasks executed: N`), (b) numbers are formatted with units (`ms`, `%`, `bytes`), (c) the layout is predictable so a screen reader user can navigate by line.

### Failure 3: Error messages leak internal roast IDs and math jargon (R16.7, R16.18, HIGH)

**Where:** `cli.py:240` (`"(R10.2 fix: prevents OOM)"`), `cli.py:251` and `cli.py:264` (`"out of range [0, {n})"`), `types.py:175` (same), `cli.py:335` (`"Error: unknown task kind {kind!r}. Valid kinds: {valid}"`), and the pervasive `R5.x`/`R10.x`/`R-REG-x` comments throughout the codebase that surface in tracebacks.

**What the user sees:**

```
$ python3 srs/cli.py execute identify 999999999
Error: n=999999999 exceeds maximum 1000000 (R10.2 fix: prevents OOM). Use n <= 1000000.
```

```
$ python3 srs/cli.py execute identify 8 --candidate 12
Error: candidate 12 out of range [0, 8)
```

**Why this is an accessibility failure:**

1. **"R10.2" is meaningless to end users.** It's an internal tracking ID for the development team's roast process. A user seeing it has no way to look it up (there's no public-facing `R10.2` documentation), no way to use it to file a bug (they don't know the issue tracker convention), and no way to know if it's stable across versions (it isn't — `R10.2` was a v7.3 finding and may be renumbered in v7.5). Including it in the error message is pure noise.

2. **"prevents OOM" is developer jargon.** "OOM" stands for "Out Of Memory". A non-technical user doesn't know this acronym. A non-native English speaker may not recognize it even if they know the concept. The actual user-facing information ("the value you passed is too large; please use a smaller number") is buried after the jargon.

3. **`[0, 8)` is math notation, not natural language.** The square bracket `[` means "inclusive" and the parenthesis `)` means "exclusive" in interval notation. This is taught in high-school mathematics but not common knowledge. A user who tries `--candidate 8` after seeing `out of range [0, 8)` gets the same error and is confused: "but 8 is in the range, isn't it? The bracket was square!"

4. **The `{kind!r}` repr-quoting is Python-specific.** `Error: unknown task kind 'bogus'.` uses single quotes because `!r` calls `repr()`. A user from a JavaScript or Go background expects double quotes. A non-technical user doesn't expect quotes at all.

**Fix:** Strip all roast IDs from user-facing strings. Replace math notation with natural language. Use the same quoting convention as the user's expectation (or no quotes for simple identifiers):

```python
# Before:
print(f"Error: n={n} exceeds maximum {MAX_N} (R10.2 fix: prevents OOM). "
      f"Use n <= {MAX_N}.", file=sys.stderr)
# After:
print(f"Error: the value {n} is too large. The maximum supported value is "
      f"{MAX_N}. Please pass a smaller number.", file=sys.stderr)

# Before:
print(f"Error: candidate {args.candidate} out of range [0, {n})", file=sys.stderr)
# After:
print(f"Error: --candidate must be between 0 and {n-1} (you passed "
      f"{args.candidate}).", file=sys.stderr)
```

## 5. I18n Readiness Assessment

**Verdict: NOT READY.** Translating the SRS CLI to any non-English language would require a multi-week refactor.

### What would need to change

1. **Wrap every user-facing string in `gettext`.** There are approximately 30 distinct user-facing strings in `cli.py` (error messages, help text, summary lines), 15 in `types.py` (validation error messages), and another 10 in `persistence.py` (corrupt-file warnings). All are inline f-strings. Each must be rewritten as `_("...")` with the f-string variables passed as named parameters:
   ```python
   # Before:
   print(f"Error: n={n} exceeds maximum {MAX_N}")
   # After:
   print(_("Error: n={n} exceeds maximum {max_n}").format(n=n, max_n=MAX_N))
   ```
   Note: f-strings cannot be directly wrapped in `gettext._()` because the interpolation happens before the lookup. The format-string pattern is required.

2. **Create a message catalog scaffold.**
   ```
   srs/
     locales/
       __init__.py
       es/LC_MESSAGES/srs.po
       de/LC_MESSAGES/srs.po
       ja/LC_MESSAGES/srs.po
       ar/LC_MESSAGES/srs.po
   ```
   Each `.po` file starts empty and is populated via `xgettext` extraction.

3. **Add a `--lang` flag (or honor `LANG`/`LC_MESSAGES`).** The CLI should detect the user's locale and load the appropriate catalog at startup. Fall back to English if the catalog is missing.

4. **Handle plurals.** Messages like `"13/13 modules passed"` and `"{n} interrupted task found"` need `ngettext` for languages with complex plural rules (Arabic has 6 plural forms, Russian has 3, Polish has 3).

5. **Externalize the help text.** The `argparse` `description=` strings and `help=` strings are currently inline. For translation, they need to be loaded from a catalog and passed in. `argparse` does not natively support this; a wrapper function is needed.

6. **Document the encoding policy.** All file I/O must declare `encoding="utf-8"` (R16.9) so that non-ASCII task kinds, error messages, and advice-table entries round-trip correctly on all platforms.

7. **Adopt message IDs for stable translation keys.** Instead of using the English string as the lookup key (which breaks if the English string is reworded), use opaque IDs:
   ```python
   # Bad: gettext lookup by English string
   _("Error: n exceeds maximum")
   # Good: lookup by stable ID
   gettext.gettext("err.n_exceeds_max")
   ```
   This is a design decision that should be made before the first translation, not after.

### What is already i18n-friendly

- The CLI is keyboard-driven (no UI strings to translate).
- The output is mostly ASCII (only 1 em-dash surfaces in `--help`).
- The JSON output format is language-neutral (keys are ASCII).
- The task kinds (`identify`, `search`, etc.) are ASCII identifiers, not localized strings — this is correct and should not change.

### Estimated effort

- Wrap 50 strings in `gettext`: **2 days**.
- Create the catalog scaffold and extract strings: **1 day**.
- Translate to one additional language (e.g. Spanish): **3 days** for a fluent translator.
- Plural-form handling and `ngettext` migration: **2 days**.
- Encoding policy + Windows testing: **2 days**.
- Documentation: **1 day**.

**Total: ~2 weeks for a single-language translation; +3 days per additional language.**

## 8. Conclusion

The SRS v7.4 CLI is a competent technical tool that has not yet been designed for humans. It works well for the developer who wrote it (who knows what `R10.2` means, who can mentally convert epoch floats, who finds JSON perfectly readable). It works poorly for the operator on call at 3 a.m., the screen-reader user navigating by line, the Windows user with a non-ASCII home directory, and the Spanish-speaking user who needs to translate the error messages.

The fixes are not expensive. The P0 list (timestamps, human renderers, jargon stripping, encoding declarations, version string) is approximately 2 days of work for a developer who knows the codebase. The P1 list (logging format, JSON-mode log suppression, Unicode cleanup, number formatting, color policy) is another 2 days. Together they would move the accessibility score from 5 to 8. The remaining gap to 10 requires the P2/P3 i18n work, which is a 2-week project but unlocks every future translation.

**Ship v7.5 with at least the P0 fixes. The accessibility score of 5 is not acceptable for a runtime that aspires to be a "sovereign substrate."**
