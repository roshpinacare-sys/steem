## 1. Executive Summary

The v7.2 SRS Runtime is **functionally honest** about its algorithmic
behavior — prior roasts (R1–R5) eliminated the v7.1 theatre, path
traversal, advice poisoning, and pipeline-state-sharing defects. The
runtime passes all 65 tests and 13 self-tests. **But it is brittle.**

Across 13 modules I found **24 distinct error-handling and resilience
defects**: 5 CRITICAL, 8 HIGH, 8 MEDIUM, 3 LOW. The fundamental problem
is that the runtime was hardened against *adversarial input* (R3
defenses are excellent — `_sanitize_id`, advice hash, path-confinement)
but **not against accidental failure modes**: missing payload keys,
corrupt JSON on disk, partial writes during crash, type-mismatched
deserialized data, RNG state that drifts across processes, and stages
that raise mid-execution leaving half-mutated `PipelineState`.

The defect pattern is consistent: **every `task.payload["..."]` access
is an unvalidated `KeyError` waiting to fire**; **every `json.load` is
an uncaught `JSONDecodeError`**; **every multi-step disk write is a
non-atomic torn-write hazard**; **every `except (TypeError, ValueError,
IndexError)` silently swallows context**; and **there is not a single
timeout, deadline, or retry anywhere in the codebase**. The runtime
will, under realistic failure conditions (disk full, killed process,
corrupt snapshot, malformed task), either propagate a cryptic
traceback to the user or — worse — silently produce wrong answers
from half-recovered state.

**Resilience score: 4 / 10.** Functional correctness under happy-path
is high (~9/10), but the *unhappy path* is largely unhandled. The
v7.2 fixes (R1.x, R3.x) moved the needle on integrity, but resilience
to partial failure is still v7.0-era.

## 3. Top 3 Critical Error-Handling Failures (Detailed)

### 3.1 R7.1 — Bare `task.payload["..."]` subscripts propagate `KeyError` with no context

**Location:** `pipeline.py:112-113` (and 5 more sites).

```python
def execution_stage(task, state, rng, effective_budget=None, **kw):
    from .primitives.execution import hash_bit
    hyps = task.payload["hypotheses"]      # line 112
    target = task.payload["target_idx"]    # line 113
    n_features = task.payload.get("n_features", 12)
    ...
```

**Concrete trigger:**
```python
from srs import Runtime, Task
rt = Runtime(home="/tmp/srs")
task = Task(kind="identify", payload={}, budget=16)   # empty payload
rt.execute(task)
```

**What happens:**
1. `Runtime.execute` (runtime.py:85) computes `n = len(task.payload.get("hypotheses", [])) if "hypotheses" in task.payload else 64` → `n=64` (silent default!).
2. `plan("identify", n=64, ...)` succeeds, picks `["A","C","V"]`.
3. Pipeline builds and runs.
4. `adaptivity_stage` (pipeline.py:163-164) executes `hyps = task.payload["hypotheses"]` → **`KeyError: 'hypotheses'`**.
5. The exception propagates through `Pipeline.execute` → `Runtime.execute`'s `try/finally` (which preserves in-flight state, good) → user.
6. User sees: `KeyError: 'hypotheses'` — no mention of which task, which stage, what was expected, or how to fix it.

**Why this is CRITICAL:**
- The default `n=64` at runtime.py:85 *hides* the missing key from the planner, so the planner happily returns a plan that the pipeline cannot execute. The validation gap is between planner and pipeline.
- The error message is useless for debugging. A user seeing `KeyError: 'hypotheses'` has no idea the field is required, what type it should be, or that `n_features` is also needed.
- The same defect exists in 6 places (one per stage), so even patching one doesn't fix the others.

**Fix:**
```python
# runtime.py — add at the top of execute()
_REQUIRED_PAYLOAD_KEYS = {
    "identify": ("hypotheses", "target_idx"),
    "identify_hard": ("hypotheses", "target_idx"),
    "search": ("hypotheses", "target_idx"),
    "verify": ("hypotheses", "target_idx"),
    "compute": ("hypotheses", "target_idx"),
}

def _validate_task(self, task: Task) -> None:
    required = _REQUIRED_PAYLOAD_KEYS.get(task.kind, ())
    missing = [k for k in required if k not in task.payload]
    if missing:
        raise ValueError(
            f"task {task.task_id!r} (kind={task.kind!r}) is missing "
            f"required payload keys: {missing}. "
            f"Expected keys: {list(required)} + optional 'n_features' (default 12)."
        )
    hyps = task.payload["hypotheses"]
    if not isinstance(hyps, list) or not hyps:
        raise ValueError(f"hypotheses must be a non-empty list, got {type(hyps).__name__} len={len(hyps) if hasattr(hyps,'__len__') else 'n/a'}")
    if not all(isinstance(h, (bytes, bytearray)) for h in hyps):
        raise TypeError("all hypotheses must be bytes")
    tgt = task.payload["target_idx"]
    if not isinstance(tgt, int) or not (0 <= tgt < len(hyps)):
        raise ValueError(f"target_idx {tgt!r} out of range [0, {len(hyps)})")
    nf = task.payload.get("n_features", 12)
    if not isinstance(nf, int) or not (1 <= nf <= 1024):
        raise ValueError(f"n_features must be int in [1, 1024], got {nf!r}")
```

### 3.2 R7.3 — Non-atomic snapshot persistence leaves `latest.json` torn on crash

**Location:** `persistence.py:108-113`.

```python
def save(snap, path=None):
    p = _coerce_path(path or default_path())
    p.mkdir(parents=True, exist_ok=True)
    _sanitize_id(snap.snapshot_id)
    advice_hash = _compute_advice_hash(snap.advice_table)
    fname = f"snap_{snap.snapshot_id}.json"
    fpath = p / fname
    payload = snap.to_dict()
    payload["advice_hash"] = advice_hash
    with open(fpath, "w") as f:                      # write 1
        json.dump(payload, f, indent=2, default=str)
    latest = p / "latest.json"
    with open(latest, "w") as f:                      # write 2 — NOT atomic w/ write 1
        json.dump({"snapshot_id": snap.snapshot_id, "path": str(fpath),
                    "timestamp": snap.timestamp}, f)
    return fpath
```

**Concrete trigger:**
1. Disk has 5 KB free.
2. User calls `rt.store_state()`. Snapshot payload is 4 KB.
3. `open(fpath, "w")` truncates `snap_xxx.json` to 0 bytes.
4. `json.dump(payload, f)` writes 4 KB. Disk now has 1 KB free. File is complete.
5. `open(latest, "w")` truncates `latest.json` to 0 bytes.
6. `json.dump({...}, f)` writes ~120 bytes... succeeds.
7. **Now imagine a different failure:** the process receives `SIGKILL` between step 5 and step 6. `latest.json` is left as a 0-byte file.

**Alternative trigger (more realistic):** A user runs `srs snapshot` repeatedly in a tight loop, the OS flushes one write but not the next, and `latest.json` ends up containing `{"snapshot_id": "abc123", "path": "/tmp/s` (truncated mid-string).

**What happens next:**
- Next process: `Runtime(home=...)` → `persistence.load_latest(self.home)` (runtime.py:44).
- `load_latest` reads `latest.json` → `json.load(f)` → **`JSONDecodeError: Expecting property name enclosed in double quotes: line 1 column 2 (char 1)`**.
- Exception propagates through `Runtime.__init__`. **Runtime cannot be constructed.** Every CLI command fails.
- Worse: the user has no idea why. They see a JSON parse error, not "your latest.json is torn; delete it or restore from `snap_xxx.json`".

**Why this is CRITICAL:**
- The defect breaks the *entire runtime* on a single torn write, not just one snapshot.
- The torn-write window is small but non-zero on every save. Production systems hit this regularly under disk pressure, SIGKILLs (OOM killer), or power loss.
- `save_in_flight` (persistence.py:197-198) has the same defect for `inflight_xxx.json` — but at least there it's a single file, so the failure mode is "in-flight lost" rather than "runtime bricked".

**Fix:** atomic write via temp file + `os.replace()`:

```python
import os, tempfile

def _atomic_write_json(path: Path, obj: Any) -> None:
    """Write JSON atomically: write to temp, fsync, rename."""
    path.parent.mkdir(parents=True, exist_ok=True)
    fd, tmp = tempfile.mkstemp(dir=path.parent, prefix=f".{path.name}.", suffix=".tmp")
    try:
        with os.fdopen(fd, "w") as f:
            json.dump(obj, f, indent=2, default=str)
            f.flush()
            os.fsync(f.fileno())
        os.replace(tmp, path)  # atomic on POSIX and Windows
    except Exception:
        try: os.unlink(tmp)
        except OSError: pass
        raise
```

Then both `save()` and `save_in_flight()` use `_atomic_write_json(fpath, payload)`. On crash, the temp file is left behind (cleanup-on-startup can sweep `.*.tmp`), but the target file is either the old version or the new version — never torn.

### 3.3 R7.4 — `recover()` is non-atomic; partial corruption leaves runtime in inconsistent state

**Location:** `runtime.py:216-226`.

```python
def recover(self) -> bool:
    snap = persistence.load_latest(self.home)
    if snap is None:
        return False
    self.advice = AdviceTable.from_dict(snap.advice_table)        # overwrite 1
    self.primitive_stats = snap.primitive_stats                   # overwrite 2
    self.last_snapshot = snap                                     # overwrite 3
    if "execution_history" in self.primitive_stats:
        self.execution_history = self.primitive_stats["execution_history"]  # overwrite 4
    return True
```

**Concrete trigger:**
1. User has a valid v7.2 snapshot on disk. `advice_table = {"abc:7": 7}`, `primitive_stats = {"A": {"runs": 5, "successes": 5, ...}, "execution_history": [...]}`.
2. A bit-flip (cosmic ray, disk error, manual edit) corrupts `primitive_stats` to the string `"corrupt"` (or to `null`).
3. The advice_hash still matches `advice_table` (only `primitive_stats` is corrupt), so `load_latest` does not discard anything.
4. `Snapshot.from_dict` accepts the corrupt `primitive_stats` (no type validation — see R7.18).
5. `recover()` runs:
   - `self.advice = AdviceTable.from_dict({"abc:7": 7})` → succeeds.
   - `self.primitive_stats = "corrupt"` → succeeds (Python is dynamically typed).
   - `self.last_snapshot = snap` → succeeds.
   - `"execution_history" in self.primitive_stats` → `"execution_history" in "corrupt"` → `False` (substring check on a string!). No overwrite.
6. `recover()` returns `True`. The runtime thinks it recovered successfully.
7. User calls `rt.capabilities()`:
   ```python
   total_runs = sum(s.get("runs", 0) for s in self.primitive_stats.values()
                    if isinstance(s, dict) and "runs" in s)
   ```
   `self.primitive_stats.values()` on a string iterates characters: `'c', 'o', 'r', 'r', ...`. Each `c.get(...)` → `AttributeError: 'str' object has no attribute 'get'`.
8. **The runtime is now in a half-recovered state:** advice is loaded (good), but primitive_stats is corrupt (bad). Every `capabilities()` call crashes. Every `execute()` call will hit `self.primitive_stats.setdefault(p, {...})` (runtime.py:151) → `AttributeError: 'str' object has no attribute 'setdefault'`.

**Why this is CRITICAL:**
- The defect is **silent** — `recover()` returns `True`, lying about success.
- It cannot be fixed by re-running `recover()` — the corrupt snapshot is still on disk.
- The user has no way to know *which* field is corrupt without digging into the snapshot file.
- The check at runtime.py:50 (`if "execution_history" in recovered.primitive_stats`) is itself buggy on string `primitive_stats` — `"execution_history" in "corrupt"` does a substring match, returning `False`. This is a latent bug masked by the normal case where `primitive_stats` is a dict.

**Fix:** Build a candidate state, validate, then swap atomically:

```python
def recover(self) -> bool:
    snap = persistence.load_latest(self.home)
    if snap is None:
        return False
    # Build candidate state with full type validation
    try:
        new_advice = AdviceTable.from_dict(snap.advice_table or {})
        if not isinstance(snap.primitive_stats, dict):
            raise TypeError(f"primitive_stats must be dict, got {type(snap.primitive_stats).__name__}")
        new_stats = {k: v for k, v in snap.primitive_stats.items()
                     if isinstance(v, dict) and k != "execution_history"}
        new_history = snap.primitive_stats.get("execution_history", [])
        if not isinstance(new_history, list):
            raise TypeError("execution_history must be list")
    except (TypeError, ValueError) as e:
        logger.error("snapshot %s failed validation: %s; refusing to recover", 
                     snap.snapshot_id, e)
        return False
    # Atomic swap — only happens if all validation passed
    self.advice = new_advice
    self.primitive_stats = new_stats
    self.last_snapshot = snap
    self.execution_history = new_history[-100:]
    return True
```

## 4. Error-Handling Strategy Proposal

### 4.1 Exceptions vs. Result Types

**Recommendation: typed exceptions, not result types.** The codebase is already exception-based and Pythonic; switching to `Result[T, E]` would be a rewrite. Instead, introduce a small exception hierarchy so callers can catch precisely:

```python
class SRSError(Exception):               # base
    """Base class for all SRS runtime errors."""

class TaskValidationError(SRSError):     # R7.1, R7.2, R7.17
    """Task payload missing/invalid keys or out-of-range values."""

class SnapshotCorruptError(SRSError):    # R7.3, R7.7, R7.12, R7.18
    """Snapshot file is missing, truncated, or schema-invalid."""

class RecoveryError(SRSError):           # R7.4, R7.13
    """Recovery failed; runtime state unchanged."""

class StageExecutionError(SRSError):     # R7.10
    """A pipeline stage raised; partial state captured in Result.notes."""

class PersistenceError(SRSError):        # R7.3, R7.8, R7.9
    """Disk I/O failure during save/load."""
```

Callers can then `except TaskValidationError as e:` without catching unrelated bugs.

### 4.2 Error Codes

For the CLI, map each `SRSError` subclass to a stable exit code:

| Code | Meaning |
|------|---------|
| 0  | success |
| 1  | usage error / unknown error |
| 2  | task ran but answer wrong (correct=False) |
| 3  | task ran but verification failed (verified=False) |
| 10 | `TaskValidationError` — bad payload |
| 11 | `SnapshotCorruptError` — disk state unusable |
| 12 | `RecoveryError` — recover() failed |
| 13 | `PersistenceError` — disk write failed |
| 14 | `StageExecutionError` — pipeline stage raised |

This lets shell scripts distinguish "wrong answer" (retry with bigger budget) from "bad input" (fix the script).

### 4.3 Logging

Replace all silent `except` clauses with `logger.warning(...)` (the `logging` module is already imported in `persistence.py` but used in only 4 places). Add a `--log-level` CLI flag. Surface non-fatal warnings in `Result.notes["recovery_warnings"]` so library users see them without checking logs.

### 4.4 Timeouts and Deadlines

Add an optional `deadline_ms` parameter to `Runtime.execute`:

```python
def execute(self, task: Task, resume: bool = False, 
            deadline_ms: Optional[float] = None) -> Result:
    import signal
    if deadline_ms is not None and hasattr(signal, 'SIGALRM'):
        def _handler(signum, frame): raise TimeoutError(f"task exceeded {deadline_ms}ms")
        old = signal.signal(signal.SIGALRM, _handler)
        signal.setitimer(signal.ITIMER_REAL, deadline_ms / 1000.0)
        try:
            return self._execute_inner(task, resume)
        finally:
            signal.setitimer(signal.ITIMER_REAL, 0)
            signal.signal(signal.SIGALRM, old)
    return self._execute_inner(task, resume)
```

(Caveat: `signal.SIGALRM` is Unix-only; on Windows, fall back to a watchdog thread or skip.)

### 4.5 Atomicity and Checkpointing

1. All disk writes go through `_atomic_write_json` (§3.2 fix).
2. Long-running pipelines checkpoint `state` to `inflight_xxx.json` every N queries (e.g., every 16) so a mid-stage crash preserves the partial transcript, not just the pre-execution in-flight file.
3. `recover()` is atomic (§3.3 fix): build candidate, validate, swap.

### 4.6 Input Validation Layer

Single chokepoint `_validate_task(task)` called at the top of `Runtime.execute` and `Runtime.plan_task`. Catches R7.1, R7.2, R7.17, R7.20, R7.23 before any pipeline code runs.

### Fix 2 (CRITICAL — R7.3): Atomic JSON writes in `persistence.py`

# persistence.py — add near top
import os, tempfile

def _atomic_write_json(path: Path, obj: Any) -> None:
    """Atomically write `obj` as JSON to `path`. Writes to a temp file
    in the same dir, fsyncs, then os.replace() (atomic on POSIX/Windows).
    On crash, leaves a stale .tmp file but never a torn target file."""
    path.parent.mkdir(parents=True, exist_ok=True)
    fd, tmp = tempfile.mkstemp(dir=path.parent, prefix=f".{path.name}.", suffix=".tmp")
    try:
        with os.fdopen(fd, "w") as f:
            json.dump(obj, f, indent=2, default=str)
            f.flush()
            os.fsync(f.fileno())
        os.replace(tmp, path)
    except BaseException:
        try: os.unlink(tmp)
        except OSError: pass
        raise

def recover(self) -> bool:
    """Reload last snapshot from disk. Atomic: either fully swaps state
    or leaves self untouched. Returns False on any validation failure."""

        snap = persistence.load_latest(self.home)

def _compute_snapshot_hash(payload: dict, advice_hash: str) -> str:
    """Hash everything except the hash fields themselves."""

## 7. Closing Note

The v7.2 SRS Runtime is **honest about its algorithms** but **naive about its
failures**. The codebase reads like it was written by someone who assumed
disk writes always succeed, JSON files are always well-formed, task
payloads are always complete, and stages never raise. None of those
assumptions hold in production. The fixes above are not architectural
rewrites — they are 10 surgical patches totaling ~150 LOC that would
move the resilience score from 4/10 to 8/10. The most important is
**Fix 2 (atomic writes)**, because the current torn-write hazard can
brick the entire runtime with a single interrupted `srs snapshot` call.
