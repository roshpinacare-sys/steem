## 3. Top 3 Benchmark Dishonesties (Detailed)

### Dishonesty #1: The "Truly Adversarial" 5-prim vs 6-prim Benchmark Is Rigged

**Location:** `benchmarks/srs/run_benchmarks.py:102-188` + `srs/primitives/adversarial.py`

**The claim:** "5-prim CANNOT distinguish adversarial hypotheses within budget; 6-prim (with advice) answers in 0 queries."

**The reality:** The benchmark's `_adversarial_5prim` function is **not the real 5-prim algorithm**. It is a hand-rolled strawman that:

1. **Uses a different query function.** The real 5-prim uses `execution.hash_bit` (defined as `sha256(seed + x.to_bytes(8, 'big'))[0] & 1`). The strawman uses `adversarial_hash_bit`, which is a different function defined only in the adversarial module. The two are never compared on the same query function.

2. **Passes a fake shared prefix.** `build_adversarial_hypotheses` returns a `prefix` derived from `sha256("adversarial_prefix_seed")`. But `_adversarial_5prim` calls `adversarial_hash_bit(h, x, k, [0]*k)` — passing `[0]*k` (all zeros) as the prefix, **not the real prefix**. The real prefix is `001110110000000` for k=15. The comment `# shared_prefix forced` admits this.

3. **Queries the wrong inputs.** The strawman queries `x = 0, 1, 2, …, budget-1` — all of which are `< k=15`. By construction of `adversarial_hash_bit`, all hypotheses return the same answer for `x < k`. So the alive set never shrinks, and the strawman guesses randomly. The real `adaptivity.execute_identify` samples `x = rng.getrandbits(n_features)` with `n_features=12`, so `x ∈ [0, 4096)`. The probability that `x < k=15` is `15/4096 = 0.37%`. So 99.63% of real queries are `≥ k` and **would distinguish** the hypotheses.

4. **The verification check is vacuous.** `is_truly_adversarial(hyps, prefix, k, 12)` checks that all hypotheses agree on `x ∈ [0, k)` *using `adversarial_hash_bit`*. Under the real `hash_bit`, every `x` (including `x=0`) distinguishes the hypotheses (verified Probe 2: 15/15 inputs in `[0, 15)` distinguish them under real `hash_bit`).

**Direct verification (Probe 1):** Running the REAL `adaptivity.execute_identify` on the "truly adversarial" hypotheses succeeds with **6 queries** and `correct=True`. The real `scheduling.execute_identify` also succeeds with 6 queries. The real `verification.execute_identify` succeeds with 10 queries. Only the real baseline `execution.execute_identify` fails (because it uses non-adaptive random queries with majority vote, and 10 queries are too few for N=64 with that algorithm).

**Conclusion:** The "5-prim vs 6-prim separation" demonstrated by this benchmark is **entirely manufactured**. The benchmark swaps in a deliberately broken algorithm for the 5-prim case while giving 6-prim a pre-built AdviceTable containing the exact answer. This is not a comparison; it is a pantomime.

### Dishonesty #2: The "Self-Improvement: Second Run 0 Queries" Claim Is Numerically False

**Location:** `benchmarks/srs/run_benchmarks.py:74-99` + README.md:62-64

**The claim (README):** "First run: 13 queries (cold start) / Second run: **0 queries** (advice hit) / 1 advice entry seeded automatically"

**The reality (from the benchmark's own JSON output, line 136 of `benchmark_results.json`):**
```
"second_run_advice_hit": {
  "queries": 29,                ← NOT ZERO
  "primitives_used": ["E","C","A","V","Adv"],
  "notes": {"advice_hit": true, "used_advice": true}

```

The first run made 24 queries (also not 13, as the README claims). The second run made **29 queries — five MORE than the first run**. The advice stage did "hit" (the lookup succeeded), but the pipeline still ran E (16 queries) + A (8 queries) + V (5 queries) = 29 queries, plus Adv (0 queries, just a lookup). The `advice_hit=True` note in the result is technically accurate but functionally meaningless: the queries were already spent before the advice stage ran.

**Root cause:** The planner (`srs/planner.py:112-120`) sets `queries=0` when `Adv` is in the primitive set, on the theory that "Adv replaces E/A queries." But the pipeline (`srs/pipeline.py:42-87`) does not actually skip E/A/V — it runs every stage in sequence and sums their queries. The planner's cost model is fiction; the pipeline ignores it.

**Direct verification (Probe 3):** `rt.plan_task(t2)` returns `estimated_cost.queries=0`, but `rt.execute(t2)` returns `queries=29`. The planner and the runtime disagree by 29 queries on a 16-query-budget task.

**Conclusion:** The "self-improvement shows 0 queries" claim is **false**. It is contradicted by the benchmark's own output. The benchmark is reporting the planner's *estimate* as if it were the *measurement*.

### Dishonesty #3: The "14.2× Storage Reduction" From Compression Is Creative Accounting

**Location:** `srs/primitives/compression.py:35-74` + README.md:54

**The claim:** "C (Compression): 18 bytes storage vs E's 256 bytes → **14.2× storage reduction**"

**The reality:** The 14.2× ratio is manufactured by inconsistent storage accounting:

- **E's storage:** `budget * 16 = 16 * 16 = 256` bytes. The "16 bytes per query" is an arbitrary number — each query is a `(x, y)` tuple where `x` is a 12-bit integer and `y` is a single bit. Ideal storage: 13 bits = 1.625 bytes per query → 26 bytes total. CPython measurement: `sys.getsizeof((x, y))` ≈ 56 bytes per tuple → 896 bytes total. So E's "256" is neither the ideal minimum nor the measured reality — it is a number chosen to make C look good.

- **C's storage:** `(budget+7)//8 + budget = 2 + 16 = 18` bytes. The "2 bytes" is the packed response bits (16 bits → 2 bytes, correct). The "16 bytes" is "1 byte per query index" — but each query index is a 12-bit integer that needs 2 bytes minimum, not 1. So C under-counts its index storage by 2×. Corrected: `2 + 16*2 = 34` bytes.

- **Corrected ratio:** `256 / 34 = 7.5×` (still inflated by E's overcount). Under consistent ideal accounting (E ideal = 26 bytes, C ideal = 26 bytes — both store 16 queries × 13 bits), **the ratio is 1.0×**. C does not compress anything; it just relabels the same data.

- **Worse:** C does the **exact same work** as E (`work_units=4112` for both) and produces the **exact same answer**. The "compression primitive" is literally the execution primitive with a different storage formula. There is no Lempel-Ziv, no dictionary, no actual compression algorithm — despite the README claiming "Lempel-Ziv + dictionary" (README.md:104).

**Conclusion:** The 14.2× compression claim is **accounting fraud**. The C primitive is E with a smaller `storage_bytes` number printed in the output. No compression occurs.

## 4. Benchmark Methodology Rewrite

The current benchmark measures almost nothing correctly. Here is what it should measure:

### 4.1 Timing

```python
def measure(fn, *args, warmup=3, trials=30, **kw):
    for _ in range(warmup):
        fn(*args, **kw)
    times = []
    for _ in range(trials):
        t0 = time.perf_counter_ns()
        fn(*args, **kw)
        t1 = time.perf_counter_ns()
        times.append(t1 - t0)
    return {
        "median_ns": statistics.median(times),
        "p10_ns": sorted(times)[len(times)//10],
        "p90_ns": sorted(times)[9*len(times)//10],
        "cv_pct": statistics.stdev(times) / statistics.mean(times) * 100,
    }
```

Report median + IQR, not single-run. Use `perf_counter_ns` for sub-microsecond resolution. The current `0.013 ms` for Adv is below `time.perf_counter()` resolution and is pure noise.

### 4.2 Memory

```python
import tracemalloc
def measure_memory(fn, *args, **kw):
    tracemalloc.start()
    snapshot_before = tracemalloc.take_snapshot()
    r = fn(*args, **kw)
    snapshot_after = tracemalloc.take_snapshot()
    stats = snapshot_after.compare_to(snapshot_before, 'lineno')
    total = sum(s.size_diff for s in stats if s.size_diff > 0)
    tracemalloc.stop()
    return {"peak_alloc_bytes": total, "result": r}
```

Report `tracemalloc` peak per primitive. The current `storage_bytes` field is a formula; replace it with a measurement.

## 5. Performance Characterization — Where Does the Runtime Actually Spend Time?

I profiled the runtime to identify real bottlenecks.

### 5.1 The Dominant Cost: `hash_bit` Evaluation

Every primitive calls `hashlib.sha256(seed + x.to_bytes(8, 'big')).digest()` per query, then takes `[0] & 1`. SHA-256 is ~1 µs per call on modern hardware. At N=65536:
- E makes 16 queries × 1 hash per query + N hypothesis scorings × 16 hashes each = 16 + 65536×16 = ~1.05M hashes → ~1 second. Measured: 701 ms. ✓
- A makes 16 queries × 20 candidates × |alive| hashes per step. With |alive| halving each step: 20×(32768+16384+…+2) ≈ 20×65535 = ~1.3M hashes → ~1.3 seconds. Measured: 1392 ms. ✓

**Bottleneck:** SHA-256 evaluation. The runtime spends ~95% of its time in `hashlib.sha256`. The "work_units" field is a reasonable proxy (it counts hash calls), but the wall-time vs work_units ratio is ~1.3 µs per work unit, which is exactly the SHA-256 cost.

### 5.2 The Pipeline Overhead

The pipeline (`srs/pipeline.py`) runs every stage in sequence even when stages are redundant. For the warm-start case (advice available), the pipeline runs E (16 queries, ~2 ms) + C (0 queries, ~0 ms) + A (8 queries, ~5 ms) + V (5 queries, ~2 ms) + Adv (0 queries, ~0 ms) = ~9 ms total, even though the answer was known after Adv in 0 ms. **The pipeline wastes 9 ms on work that the planner already determined was unnecessary.**

### 5.3 The Planner Is Free

The planner (`srs/planner.py:plan`) runs in <0.1 ms (it is pure arithmetic on `log2(N)` etc.). It is not a bottleneck. But its output is ignored by the pipeline (see R4.5), so its speed is irrelevant.

### 5.4 Persistence Is Reasonable

`persistence.save` writes a JSON snapshot to disk. At 1 advice entry, this is ~200 bytes and <1 ms. Not a bottleneck. At 10⁶ advice entries (the hypothetical scale), this would be ~20 MB and ~100 ms — still acceptable, but the advice lookup itself would be O(1) due to dict hashing.

### 5.5 Memory

The dominant memory cost is the hypothesis list itself: N × 32 bytes raw, plus CPython overhead (~28 bytes per `bytes` object header) → N × 60 bytes. At N=65536: ~4 MB. At N=10⁶: ~60 MB. At N=10⁹: ~60 GB — **infeasible**. The runtime cannot scale to N=10⁹ without streaming hypotheses from disk, which it does not do.

The `alive` set in adaptivity is `set(range(N))` initially — another N × 28 bytes (CPython int overhead). At N=10⁶ this is 28 MB just for the alive set. At N=10⁹ it is 28 GB.

**Real bottleneck for scale:** Python object overhead. The runtime is fundamentally a single-process Python program holding all hypotheses in memory. It cannot reach N=10⁶ without significant memory pressure, and N=10⁹ is impossible without a complete rewrite.

### 5.6 Where Time Goes (Summary)

| Component | % of wall time at N=256 | % at N=65536 |
|-----------|------------------------|--------------|
| `hashlib.sha256` calls | ~85% | ~92% |
| Pipeline stage overhead | ~10% | ~5% |
| Persistence (in-flight save) | ~3% | <1% |
