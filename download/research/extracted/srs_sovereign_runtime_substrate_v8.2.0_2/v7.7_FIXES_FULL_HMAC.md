# v7.7 — Full-Snapshot HMAC + Rollback Protection (F12)

**Agent**: F12 (Full Snapshot Integrity Implementer)
**Scope**: Close the two HIGH-severity findings R17.4 (primitive_stats / execution_history not integrity-protected) and R17.5 (latest.json rollback attack) from R17's security audit.
**Predecessor**: v7.6 (HMAC-SHA256 for advice_table only, length-prefix encoding for fingerprints, Windows retry, ISO timestamps, jargon-free errors).
**Test gate**: 148 / 148 targeted pytest tests pass (130 pre-existing + 18 new security tests).

---

## 1. Problem Statement (R17 findings, recapped)

R17's security audit of the v7.5 runtime found 14 issues. v7.6 closed the
CRITICAL (R17.1: HMAC) and one HIGH (R17.3: length-prefix encoding). Two
HIGHs remained open:

### R17.4 — primitive_stats / execution_history unprotected (HIGH)

v7.6's `advice_hash` was an HMAC-SHA256, but it only covered
`advice_table`. An attacker with snapshots-dir write access could:

  - Tamper with `primitive_stats` (e.g. inject `FAKE_PRIM` with
    `runs=999, successes=999`) without invalidating the hash.
  - Tamper with `execution_history` (e.g. inject a malicious
    `task_id="x; rm -rf /"` or a 10 KB junk field).
  - Reset `_total_tasks` to 0 for anti-forensics.

The tampered data was loaded silently and exposed via
`capabilities()["primitive_stats"]` and `capabilities()["recent_executions"]`.

### R17.5 — latest.json rollback attack (HIGH)

`latest.json` had NO integrity protection. An attacker could swap its
`path` field to point at any older (legitimate) snapshot, and the runtime
would silently load stale state — e.g. rolling back advice to a
pre-disclosure state, or rolling back `_total_tasks` to evade rate
limits.

## 2. Fixes Applied

### Fix 1: Full-payload HMAC (`snapshot_hash`) — R17.4

**Files changed**:
  - `srs/persistence.py` — added `_compute_snapshot_hash(snap_dict)`
    (HMAC-SHA256 of the full payload, excluding the hash field itself).
  - `srs/persistence.py:save()` — replaced `payload["advice_hash"] = ...`
    with `payload["snapshot_hash"] = _compute_snapshot_hash(payload)`.
    The legacy `advice_hash` field is no longer written on new saves.
  - `srs/persistence.py:load_latest()` — verifies `snapshot_hash` against
    the full payload. On mismatch, logs a warning and returns `None`
    (the entire snapshot is rejected — no partial state is loaded).
  - `srs/types.py:Snapshot` — added `snapshot_hash: str | None = None`
    field. Kept `advice_hash` as a legacy field for backward compat.

**What's covered now**: every field in the snapshot dict is covered by
the HMAC, including `snapshot_id`, `timestamp`, `advice_table`,
`primitive_stats` (which itself contains `execution_history` and
`_total_tasks` as nested sentinel keys), `last_task_id`, `last_result`,
and the new `sequence` field. The only field excluded is `snapshot_hash`
itself (a hash can't include its own value).

**Security model unchanged from v7.6**: HMAC-SHA256 with the per-installation
secret key at `~/.srs/secret_key` (0600). An attacker who can write to the
snapshots directory but NOT to `~/.srs/secret_key` cannot forge a valid
`snapshot_hash`. The v7.6 SHA-256-only attack (recompute the public hash
after tampering) no longer works because the hash is now an HMAC.

**Verification (end-to-end)**:

```
1. saved snapshot: snap_f87d9075e78f.json
2. attacker tampered primitive_stats + recomputed SHA-256 hash
   WARNING srs.persistence: snapshot_hash mismatch for .../snap_f87d9075e78f.json
       (stored=c25e975177a1, actual=b831e7aa02a8); rejecting entire snapshot
3. rt2.primitive_stats has FAKE_PRIM? False
   rt2.primitive_stats = {}
   rt2.last_snapshot = None
   PASS: tampered primitive_stats was rejected (R17.4 fixed)
```

### Fix 2: Monotonic sequence + high-water mark (rollback protection) — R17.5

**Files changed**:
  - `srs/types.py:Snapshot` — added `sequence: int = 0` field.
  - `srs/persistence.py` — added:
    - `_compute_seq_hash(seq_data)` — HMAC-SHA256 of the sequence.json
      payload.
    - `_get_high_water_sequence(home)` — reads `home/sequence.json`,
      verifies HMAC, returns the `high_water` int. Returns 0 on any
      integrity failure (missing file, empty file, hash mismatch, wrong
      type, no `seq_hash` field — the last case defends against an
      attacker writing `{"high_water": 999999}` with no hash to
      suppress rollback detection).
    - `_update_high_water_sequence(home, seq)` — atomic write of
      `{"high_water": seq, "seq_hash": <HMAC>}`.
  - `srs/persistence.py:save()` — acquires an exclusive `file_lock` on
    `sequence.json` for the whole read-compute-write cycle:
    1. Read `high_water` via `_get_high_water_sequence`.
    2. `next_seq = high_water + 1`.
    3. Mutate `snap.sequence = next_seq` (so the caller's `Snapshot`
       object reflects the persisted sequence).
    4. Build the payload, compute `snapshot_hash`, write the snapshot
       file.
    5. Write `latest.json` (with its own exclusive lock as before).
    6. Update `sequence.json` via `_update_high_water_sequence` AFTER
       the snapshot is on disk — a crash between (4) and (6) leaves
       `high_water` conservative (lower than the snapshot's actual
       sequence), which means the next save will skip a sequence
       number but no rollback protection is lost.
  - `srs/persistence.py:load_latest()` — after the hash check, reads
    `snap_sequence` from the snapshot. If `snap_sequence >= 1` (i.e.
    a v7.7+ snapshot, not a legacy one), calls `_get_high_water_sequence`
    and rejects the snapshot if `snap_sequence < high_water`. If
    `snap_sequence > high_water` (e.g. a different process wrote it),
    advances the high-water mark to match.

**Why the `file_lock` on `sequence.json`**: without it, two concurrent
saves in different processes could both read `high_water=5`, both
compute `next_seq=6`, both write snapshots with `sequence=6`, and both
update `high_water` to 6 — producing two snapshots with the same
sequence number. The exclusive lock serializes the read-compute-write
cycle so each save gets a distinct, monotonically increasing sequence.

**Empty-file handling**: `file_lock(seq_path, exclusive=True)` creates
the file via `O_CREAT` if it doesn't exist (the lock is acquired on an
open file descriptor). So inside a `save()` call on a fresh home
directory, `seq_path.exists()` returns True even when no prior snapshot
has been written. `_get_high_water_sequence` now treats an empty file
(0 bytes) the same as a missing file (returns 0, no warning) so the
very first save doesn't log a spurious "corrupt sequence.json" warning.

**Backward compatibility**: legacy snapshots (v7.6 and earlier) have no
`sequence` field. `Snapshot.from_dict` defaults `sequence=0` for them.
`load_latest` only enforces the rollback check on `sequence >= 1` —
legacy snapshots (sequence 0) are always accepted (the worst case is
loading an old advice_table, which the `snapshot_hash`/`advice_hash`
check already covers).

**Verification (end-to-end)**:

```
1. saved snap1: snap_f098d0d641f3.json (seq=1)
2. saved snap2: snap_f7ee651ce6aa.json (seq=2)
3. high-water mark = 2
4. attacker replaced latest.json to point at snap1 (seq=1)
   WARNING srs.persistence: rollback detected: snapshot .../snap_f098d0d641f3.json
       has sequence=1 but high-water mark is 2; rejecting (possible rollback attack)
5. rt2.last_snapshot = None
   rt2.advice._table size = 0 (0 = fresh, >0 = loaded)
   PASS: rollback attack was prevented (R17.5 fixed)
```

### Fix 3: Backward compatibility — v7.6 snapshots migrate transparently

`load_latest` now has a three-way integrity check:

  1. **`snapshot_hash` present (v7.7+)** → verify HMAC over the full
     payload. On mismatch, return `None`.
  2. **`snapshot_hash` absent, `advice_hash` present (v7.6)** → verify
     HMAC over `advice_table` only. On mismatch, return `None`. On
     match, accept the snapshot and log an INFO message
     (`"loaded v7.6 snapshot ... will migrate to snapshot_hash on next save"`).
     The next `save()` writes the new `snapshot_hash` format.
  3. **Neither hash present (extremely old / untrusted)** → return
     `None` with a warning. Defense in depth — rejects snapshots that
     predate integrity protection entirely.

`save()` always writes `snapshot_hash` (never `advice_hash`) on new
saves, so the migration happens automatically the first time a v7.6
snapshot is loaded and re-saved.

### Fix 4: Constant-time hash comparison

Replaced `actual_hash != stored_hash` with `hmac.compare_digest(...)`
in `load_latest`. Closes a minor timing side-channel that R17 flagged
(R17.1 note: "String comparison via != (not constant-time) — minor
timing side-channel, hard to exploit"). `hmac.compare_digest` is
constant-time on equal-length strings, so an attacker measuring the
comparison time can't learn how many leading bytes of their forged hash
match the real one.

## 6. What This Does NOT Close

R17 had 14 findings. v7.6 closed R17.1 (HMAC) and R17.3 (length-prefix).
v7.7 closes R17.4 and R17.5. The remaining open findings are:

  - **R17.6 (MEDIUM)**: `inflight_*.json` has no HMAC. Tampering with
    `queries_made` would let an attacker resume a task with the wrong
    RNG offset. Out of scope for F12; recommend a follow-up that adds
    an HMAC to `save_in_flight` / `load_in_flight`.
  - **R17.7 (MEDIUM)**: ALREADY CLOSED in v7.6 (added `SafeJSONDecoder`
    with MAX_DEPTH=100 + `MAX_SNAPSHOT_SIZE` 10 MB cap).
  - **R17.8 (MEDIUM)**: `AdviceTable.from_dict` performs no input
    validation. Out of scope for F12.
  - **R17.9 (LOW)**: `Task.__post_init__` doesn't validate `task_id`
    (null bytes accepted). Out of scope for F12.
  - **R17.10 (LOW)**: snapshot_id based on time_ns + iso_now (no uuid
    entropy). Out of scope for F12.
  - **R17.11 (LOW)**: SRS_HOME unvalidated. Out of scope for F12.
  - **R17.12 (LOW)**: `random.Random` for verification-stage RNG.
    Soundness bound assumes non-adaptive adversary. Out of scope.
  - **R17.13 (LOW)**: task_id logged at INFO; potential log injection
    via control chars. Out of scope for F12.
  - **R17.14 (LOW)**: ALREADY CLOSED in v7.6 (`MAX_SNAPSHOT_SIZE`).
  - **R17.15 (INFO)**: 113 LOW bandit findings (96 B101 assert_used in
    self_test, 17 B311 random.Random). Not actionable.

### Known weakness in v7.7 rollback protection

If an attacker can DELETE `sequence.json` (they have snapshots-dir write
access), `_get_high_water_sequence` returns 0 and the rollback check is
skipped. The attacker could then swap `latest.json` to point at an old
snapshot and the runtime would load it.

Mitigations:
  1. The `snapshot_hash` (HMAC) still prevents the attacker from
     forging a fake snapshot — they can only roll back to a
     LEGITIMATE old snapshot whose hash is valid.
  2. Storing `sequence.json` outside the snapshots dir (e.g. in
     `~/.srs/sequence.json` alongside `secret_key`) would close this
     gap, but it's a behavior change that requires the runtime to know
     about two separate directories. Deferred to a future hardening
     pass.
  3. A more robust solution would store the high-water mark INSIDE the
     secret_key file (or a separate `~/.srs/state.json` that the
     attacker can't write). Also deferred.

For now, the v7.7 fix raises the bar: the attacker must BOTH delete
`sequence.json` AND swap `latest.json` (vs. v7.6 where they only needed
to swap `latest.json`). Combined with the HMAC on `sequence.json`
(preventing them from LOWERING the high-water mark), this is a
meaningful improvement over v7.6.

## 7. Security Score Impact

v7.6's security score was 7/10 (R17's audit). With v7.7 closing R17.4
and R17.5 (both HIGH), the estimated score moves to ~8/10:

  - **Integrity**: 6 → 8 (full-payload HMAC; was advice_table only).
  - **Anti-rollback**: 3 → 7 (monotonic sequence + high-water mark;
    was no protection).
  - **Backward compat**: 8 → 9 (v7.6 snapshots migrate transparently;
    constant-time comparison).
  - **Defense in depth**: 7 → 8 (three-way integrity check: snapshot_hash
    → advice_hash → reject).

The remaining gaps (R17.6 inflight HMAC, R17.8 AdviceTable validation,
R17.9 task_id validation, R17.10 snapshot_id entropy, R17.11 SRS_HOME
validation, R17.12 RNG predictability, R17.13 log injection) keep the
score below 9.
