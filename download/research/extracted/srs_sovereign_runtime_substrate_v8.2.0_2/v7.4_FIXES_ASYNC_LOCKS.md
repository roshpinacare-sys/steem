## Fix 1: `execute_async()` (R6.10)

### Problem

The SRS `Runtime.execute()` is CPU-bound (hash_bit queries + advice hash computation + JSON serialization of in-flight state) plus a small amount of file I/O. Calling `execute()` directly from an async context (e.g. an aiohttp handler) blocks the event loop for the full duration — typically 1–50 ms, up to 1+ s at N=16384. This starves any concurrent asyncio tasks.

### Fix

Added `Runtime.execute_async(task, resume=False) -> Result` to `srs/runtime.py`:

```python
async def execute_async(self, task: Task, resume: bool = False) -> Result:
    import asyncio
    loop = asyncio.get_event_loop()
    return await loop.run_in_executor(
        None, lambda: self.execute(task, resume=resume)
    )
```

**Design notes:**

- **Why `run_in_executor` and not `async def execute`?** The actual work is CPU-bound, not I/O-bound. A coroutine would not yield naturally — we'd still need `run_in_executor` to actually unblock the loop. Making `execute` itself a coroutine would force every caller to `await`, breaking the synchronous API. The async wrapper is the minimal, non-breaking addition.
- **Thread safety.** `execute()` already holds a per-task-id `threading.Lock` (R6.3 fix) and a `_state_lock` `threading.RLock` (R6.1/R6.2 fix), so multiple `execute_async` calls from different asyncio tasks are safe — they serialize on the per-task lock if they share a `task_id`, run in parallel if they don't.
- **`asyncio.get_event_loop()` vs `get_running_loop()`.** Inside a coroutine (which `execute_async` is), `get_event_loop()` returns the running loop. The deprecation warning only fires when called outside a coroutine with no running loop. The brief's reference implementation uses `get_event_loop()` so we match it for consistency.

### Verification

- `test_execute_async_returns_correct_result` — `asyncio.run(rt.execute_async(task))` returns a `Result` with the correct `task_id`, `correct=True`, and `primitives_used` populated.
- `test_execute_async_does_not_block_event_loop` — runs `execute_async(heavy_task)` and `asyncio.sleep(0.030)` concurrently via `asyncio.gather`. With `run_in_executor`, they overlap and total wall time ≈ 30 ms. If `execute_async` blocked the loop, total ≈ 50 ms. Asserts `< 45 ms` (concurrent).
- `test_execute_async_resume_flag` — `execute_async(task, resume=True)` passes the flag through to `execute()`.
- Runtime `self_test()` now also drives `execute_async` via `asyncio.run()` and asserts the returned `Result` matches the synchronous call.

## Fix 2: Cross-Process File Locking (R6.12)

### Problem

v7.3 added atomic writes (`_atomic_write_json` using tempfile + fsync + `os.replace`) so a single `latest.json` file is never torn. But two PROCESSES writing to the same home directory could still race: process A writes snap_A.json, process B writes snap_B.json, then both race to update `latest.json` — the loser's snapshot pointer is lost, and the winner's snap file may not yet be flushed. A reader in a third process could observe `latest.json` pointing at a snap file that doesn't exist yet.

### Fix

Added `fcntl.flock`-based cross-process locks to `srs/persistence.py`:

- `_lock_file(fileobj, exclusive=True/False)` — low-level flock acquire.
- `_unlock_file(fileobj)` — low-level flock release.
- `file_lock(path, exclusive=True)` — context manager that opens the file, acquires the flock, yields, and releases on exit (even on exception).

Applied to:

| Function | Lock | Why |
|----------|------|-----|
| `save()` | exclusive on `latest.json` | serialize the two index writers |
| `load_latest()` | shared on `latest.json` | allow concurrent readers, block writers |
| `save_in_flight()` | exclusive on `inflight_{task_id}.json` | serialize two processes resuming the same task |
| `load_in_flight()` | shared on `inflight_{task_id}.json` | block concurrent writers |
| `clear_in_flight()` | exclusive on `inflight_{task_id}.json` | prevent half-deleted reads |

**Design notes:**

- **Why lock `latest.json` but not `snap_*.json`?** Snap files have unique names (sha256 prefix of timestamp), so concurrent writers don't collide on them. Only the shared index file `latest.json` needs serialization.
- **Advisory locks.** `fcntl.flock` is advisory — only cooperating processes (i.e. those that also call `_lock_file`) are blocked. A non-cooperating process (e.g. `cat latest.json` from a shell) is unaffected.
- **Windows fallback.** `fcntl` is POSIX-only. On Windows, the locks degrade to no-ops with a one-time warning. The runtime still works there, just without cross-process safety (same as v7.3).
- **Context manager pattern.** All locks use `with file_lock(...):` so the lock is released even if the body raises. `test_file_lock_context_manager_releases_on_exception` verifies a crashed writer doesn't hold the lock forever.
- **Best-effort fallback.** If `file_lock` can't open the lockfile (e.g. permission denied), the function falls back to an unlocked operation, logging a debug message. The atomic-write guarantee from `_atomic_write_json` still holds; only the cross-process serialization is lost in this edge case.

### Verification

- `test_cross_process_lock_serializes_concurrent_writers` — spawns **3 subprocesses** that each call `persistence.save()` 50 times in a tight loop, all writing to the same `home` directory. Asserts: (a) all subprocesses exit 0; (b) `latest.json` is valid JSON; (c) the snap file it points at exists and is valid; (d) no leftover `.tmp_*` files. **150 concurrent saves, zero corruption.**
- `test_file_lock_context_manager_releases_on_exception` — acquires the lock, raises `RuntimeError` inside the body, catches it, then verifies a second acquisition succeeds immediately (no deadlock).

## Fix 3: Constructor Atomic Recover (R-REG-2)

### Problem

R13 found that `Runtime.__init__()` doesn't apply the R7.4 type checks that `recover()` does. A snapshot with a **valid `advice_hash`** but a **corrupt `primitive_stats`** field (e.g. a bit-flip turned the dict into the string `"i_am_not_a_dict"`) passes `load_latest()`'s integrity check (because the hash is over `advice_table`, not `primitive_stats`), then gets assigned to `self.primitive_stats`. The next `execute()` crashes with `AttributeError: 'str' object has no attribute 'setdefault'`.

This is the exact brick scenario R-REG-2 describes: the runtime starts up apparently fine, then crashes on the first user request.

### Fix

`Runtime.__init__()` now mirrors `recover()`'s atomic-recover pattern:

1. Try to load the snapshot via `persistence.load_latest()`.
2. If loaded, build candidate fields (`candidate_advice`, `candidate_stats`, `candidate_history`, `candidate_total`).
3. **Type-validate each** before assigning:
   - `advice_table`: wrapped in `try/except`, falls back to empty `AdviceTable` on `AdviceTable.from_dict` failure.
   - `primitive_stats`: must be a `dict`; non-dict resets to `{}`.
   - Per-primitive entries: must each be `dict`s; non-dict entries are dropped (this catches the case where `primitive_stats` is a dict but one of its values got corrupted).
   - `execution_history`: must be a `list`; non-list resets to `[]`.
   - `_total_tasks` (new in v7.4 — see Fix 5): must be `int`; non-int resets to `0`.
4. Assign all four fields at once. If anything raised, the runtime starts with fresh state.

On any validation failure, log a `WARNING` with the field name and the bad type, so the operator can see what was corrupted.

### Verification

- `test_runtime_init_atomic_recover_with_corrupt_primitive_stats` — creates a valid snapshot, corrupts `primitive_stats` to the string `"i_am_not_a_dict"` (keeping `advice_hash` valid), constructs a new `Runtime`, and asserts: (a) constructor doesn't crash; (b) `primitive_stats` is a `dict`; (c) `execute()` works on the recovered runtime.
- `test_runtime_init_atomic_recover_with_corrupt_per_primitive_stats` — same setup, but corrupts only ONE per-primitive entry (`primitive_stats["A"] = "corrupt_string"`). Asserts the corrupt entry is dropped while the rest of the stats survive.
- Runtime `self_test()` now also exercises this scenario end-to-end.

## Fix 4: Empty Hypotheses Validation (R-REG-3)

### Problem

R13 found that an empty hypotheses list passes `_validate_task()` because the existing `n > 0` guard short-circuits the range check when `n == 0`:

```python
# v7.3 (buggy):
if n > 0 and not (0 <= tgt < n):
    raise ValueError(...)
```

With `n == 0`, the `and` short-circuits and the check is skipped. The empty list then slips through to the pipeline, where `hypotheses[target_idx]` crashes with `IndexError`.

### Fix

`_validate_task()` in `srs/types.py` now explicitly rejects:

- **Empty hypotheses** for task kinds that require `target_idx` (identify, identify_hard, search, optimize, verify, amortize):
  ```python
  if n == 0:
      raise ValueError(
          f"task kind {task.kind!r} requires a non-empty "
          f"hypotheses list (got len=0); target_idx={tgt} has "
          f"nothing to index into"
      )
  ```
- **Negative `target_idx`** with a clearer error message (was previously caught by the range check but with an unclear "out of range [0, n)" message):
  ```python
  if tgt < 0:
      raise ValueError(
          f"payload['target_idx']={tgt} is negative; must be in "
          f"[0, {n})"
      )
  ```
- **Out-of-range `target_idx`** (`tgt >= n`) — unchanged from v7.3, just restructured for clarity.

### Verification

- `test_validate_task_rejects_empty_hypotheses` — `Task(kind="identify", payload={"hypotheses": [], "target_idx": 0})` raises `ValueError` matching `"non-empty"`.
- `test_validate_task_rejects_empty_hypotheses_with_nonzero_target` — same but with `target_idx=5`.
- `test_validate_task_rejects_negative_target_idx` — `target_idx=-1` raises `ValueError` matching `"negative"`.
- `test_runtime_execute_rejects_empty_hypotheses_at_entry` — `Runtime.execute()` rejects at entry, not in the pipeline.
- Existing `test_validate_task_rejects_out_of_range_target_idx` still passes (the `tgt >= n` branch matches `"out of range"`).

## Fix 5: `capabilities()` Label Fix (R-REG-6)

### Problem

R13 found that `capabilities()['total_executions']` is mislabeled. The implementation is:

```python
total_runs = sum(s.get("runs", 0) for s in primitive_stats.values()
                 if isinstance(s, dict) and "runs" in s)
```

This sums `stats["runs"]` across ALL primitives. A single `execute()` call that uses 4 primitives (`['Adv', 'A', 'C', 'V']`) increments `total_executions` by 4, not 1. The R13 verification test expected 8 after 8 concurrent executes; the actual value was 16–30.

### Fix

`capabilities()` in `srs/runtime.py` now exposes three fields:

| Field | Value | Truthful? |
|-------|-------|-----------|
| `total_primitive_runs` | `sum(stats["runs"] across all primitives)` | ✅ (the old misnamed value, now correctly named) |
| `total_tasks` | `self._total_tasks` (incremented once per `execute()` call) | ✅ (new, truthful execute() call count) |
| `total_executions` | alias of `total_tasks` | ⚠️ DEPRECATED — kept for backward compat with `test_integration_v7.py:192` and any external consumer. Will be removed in v7.5. |

The new `self._total_tasks` counter is:

1. Initialized to `0` in `__init__`.
2. Incremented inside the `_state_lock` critical section in `_execute_locked()` (so concurrent `execute()` calls don't lose increments — same race pattern as R6.1).
3. Persisted in `primitive_stats["_total_tasks"]` alongside `execution_history` (so it survives `store_state` / `recover` round-trips).
4. Type-validated on load in both `__init__` and `recover` (must be `int`, not `bool`).

The `capabilities()` output also filters out both sentinel keys (`execution_history` and `_total_tasks`) from the `primitive_stats` dict in the report, so they don't leak into the user-facing output.

### Verification

- `test_capabilities_reports_total_primitive_runs_and_total_tasks` — runs 5 `execute()` calls, asserts `total_tasks == 5` and `total_primitive_runs >= total_tasks`.
- `test_capabilities_primitive_stats_excludes_sentinel_keys` — asserts neither `execution_history` nor `_total_tasks` appears in `capabilities()['primitive_stats']`.
- `test_runtime_capabilities_total_tasks_persists_across_snapshots` — runs 3 tasks, persists, reloads, asserts `total_tasks == 3` (not 0 — the counter survives the round-trip).
- `test_runtime_capabilities_meaningful` (updated) — now exercises all three fields: `total_primitive_runs`, `total_tasks`, and the deprecated `total_executions` alias.
- Backward compat: `test_integration_v7.py:192` (`assert c["total_executions"] >= 1`) still passes because the alias is preserved.

## Fix 6: `--verbose`/`--quiet` as Subcommand Flags (R-REG-5)

### Problem

R13 found that `--verbose`/`--quiet` only work as global flags (before the subcommand):

```bash
python3 srs/cli.py --verbose execute identify 64    # worked
python3 srs/cli.py execute identify 64 --verbose    # FAILED: "unrecognized arguments: --verbose"
```

### Fix

Added `_add_logging_flags(parser, is_subparser=False)` helper in `srs/cli.py` and called it on EVERY subparser:

```python
def _add_logging_flags(parser, is_subparser: bool = False) -> None:
    default = argparse.SUPPRESS if is_subparser else False
    parser.add_argument("--verbose", "-v", action="store_true", default=default, ...)
    parser.add_argument("--quiet", "-q", action="store_true", default=default, ...)
```

**The `default=argparse.SUPPRESS` trick:** when a subparser has `default=argparse.SUPPRESS` on an argument, argparse does NOT set the attribute if the user didn't pass the flag. This means a global `--verbose=True` is preserved when the subcommand doesn't repeat it. Without this, the subparser's `default=False` would silently overwrite the global value.

**Merge semantics after parsing:**

| Global flag | Subcommand flag | Result | Notes |
|-------------|-----------------|--------|-------|
| `--verbose` | (none) | `verbose=True` | inherited from global (SUPPRESS preserves it) |
| (none) | `--verbose` | `verbose=True` | subparser sets it |
| `--verbose` | `--verbose` | `verbose=True` | idempotent |
| `--verbose` | `--quiet` | `verbose=True, quiet=True` | verbose wins in `_configure_logging` (same as v7.3) |
| (none) | (none) | `verbose=False` | default |

`_configure_logging` uses `getattr(args, "verbose", False)` so it handles the case where the attribute wasn't set at all (SUPPRESS).

### Verification

- `test_cli_verbose_as_subcommand_flag` — `cli.main(["--home", tmp, "capabilities", "--verbose"])` exits 0.
- `test_cli_quiet_as_subcommand_flag` — same with `--quiet`.
- `test_cli_verbose_global_plus_subcommand_no_flag_inherits` — parses `["--verbose", "capabilities"]` and asserts `args.verbose is True` (the SUPPRESS trick works).
- Manual: `python3 srs/cli.py execute identify 64 --verbose` produces 26 DEBUG/INFO log lines; without `--verbose`, only 2.
