# v7.5 Roast: Cross-Platform Compatibility of the v7.4 SRS Runtime

**Agent:** R15 (Cross-Platform Roaster)
**Target:** `/home/z/my-project/download/srs/` (v7.4.0)
**Date:** 2025
**Test platform:** Python 3.12.13 on Linux (with simulated Windows `fcntl` absence)

---

## 1. Executive Summary

The v7.4 SRS Runtime was developed and tested exclusively on Linux. A
systematic cross-platform audit against Windows, macOS, and BSD reveals
**12 distinct findings** spanning path handling, file I/O atomicity,
encoding, event-loop APIs, and environment-variable expansion.

The headline news is **mixed**:

- **Good:** The `fcntl` degradation path (F6 fix) works correctly. When
  `fcntl` is unavailable (Windows), the runtime emits a one-time warning
  and degrades to no-op locks. All 13 module self-tests PASS under a
  simulated Windows environment (no `fcntl`). The `Path()` usage is
  consistent and avoids hardcoded `/` separators. `hashlib.sha256`,
  `int.from_bytes(..., "big")`, and `json.dumps(sort_keys=True)` are all
  byte-deterministic across platforms.

- **Bad:** No `open()` call in the entire codebase specifies
  `encoding="utf-8"` (18 occurrences). On Windows, the default encoding
  is `cp1252`, which produces CRLF line endings and will crash with
  `UnicodeEncodeError` the moment anyone sets `ensure_ascii=False` on a
  `json.dump`. The `asyncio.get_event_loop()` call in `execute_async`
  is deprecated in Python 3.10+ and raises `RuntimeError` in some 3.12
  contexts. `os.replace()` — the linchpin of the atomic-write strategy —
  fails with `PermissionError` on Windows if the target file is open by
  another process, which is exactly the scenario the v7.4 `file_lock`
  was supposed to prevent (but can't, because `file_lock` is a no-op on
  Windows).

- **Ugly:** The runtime works on Windows for **single-process** use, but
  **concurrent multi-process** use (two CLI invocations sharing
  `~/.srs`) is broken on Windows: a reader holding `latest.json` open
  for the ~1 ms duration of `json.load` will cause a concurrent
  writer's `os.replace` to crash with an unhandled `PermissionError`.

**Cross-platform score: 6/10** — works, but by accident rather than by
design, and only for the single-process case.

## 4. Top 3 Cross-Platform Failures (Detailed)

### Failure 1: `os.replace()` PermissionError on Windows (R15.2)

**The scenario:** Two CLI invocations share `~/.srs/snapshots/`. Process A
calls `srs snapshot` (which calls `store_state()` → `save()` →
`_atomic_write_json()` → `os.replace(tmp, latest.json)`). Process B calls
`srs recover` (which calls `load_latest()` → `open(latest.json)` →
`json.load(f)`).

**On Linux:** `open(latest.json)` for reading does NOT prevent another
process from `os.replace`-ing the file. Linux uses advisory locking; the
file can be renamed while open. The reader's file descriptor continues to
point at the old inode (which is now unlinked). The reader sees the old
content. No crash.

**On Windows:** `open(latest.json)` for reading acquires a **mandatory
sharing lock**. Any attempt by another process to rename or delete the
file during the read window fails with `WinError 32` ("The process cannot
access the file because it is being used by another process"), which
surfaces in Python as `PermissionError`. The `os.replace(tmp_path, path)`
call at `persistence.py:278` raises `PermissionError`.

**The code's response:** `_atomic_write_json` has an `except Exception:`
block (line 290) that unlinks the tempfile and **re-raises**. So the
`PermissionError` propagates through `save()` → `store_state()` → the
CLI, which crashes with:

```
PermissionError: [WinError 32] The process cannot access the file because
it is being used by another process: '...\\.srs\\snapshots\\.tmp_XXX.json'
-> '...\\.srs\\snapshots\\latest.json'
```

**Why `file_lock` doesn't help:** v7.4 added `file_lock()` (R6.12 fix)
to serialize cross-process access. But `file_lock` uses `fcntl.flock`,
which is POSIX-only. On Windows, `file_lock` is a **no-op** (yields
`None`, does nothing). So the lock provides zero protection on Windows,
and the mandatory-lock collision is unprevented.

**Fix:** Implement a Windows-specific lock using `msvcrt.locking()` (byte-
range lock on the file descriptor) inside `file_lock()`. Alternatively,
add a retry loop around `os.replace`:

```python
import time
for attempt in range(5):
    try:
        os.replace(tmp_path, path)
        break
    except PermissionError:
        if attempt == 4:
            raise
        time.sleep(0.01 * (2 ** attempt))  # 10, 20, 40, 80 ms
```

### Failure 2: No `encoding="utf-8"` on Any `open()` Call (R15.1)

**The scenario:** A user on Windows runs `srs execute identify 64
--persist`. The `store_state()` call writes `latest.json` via
`_atomic_write_json`, which does `os.fdopen(fd, "w")` (text mode, default
encoding). On Windows, the default encoding is `cp1252` (Windows-1252),
not UTF-8.

**Why it doesn't crash TODAY:** `json.dump(data, f, indent=2,
default=str)` defaults to `ensure_ascii=True`, which escapes all non-ASCII
characters to `\uXXXX` sequences. The resulting output is pure ASCII,
which `cp1252` can encode without error. So the write succeeds.

**Why it WILL crash tomorrow:** Any of the following changes will break
Windows:
1. A developer adds `ensure_ascii=False` to `json.dump` (common for
   readability — produces human-readable Unicode instead of `\uXXXX`
   escapes). On Windows, `cp1252` cannot encode emoji, CJK characters, or
   any character outside Latin-1. `UnicodeEncodeError` crashes the save.
2. Python 3.15+ enables UTF-8 mode by default (PEP 686), changing the
   default encoding to UTF-8. Files written on Windows 3.14 (cp1252)
   become unreadable on Windows 3.15+ (UTF-8) if they contain bytes in
   the 0x80-0x9F range (cp1252-specific characters like `€`, `™`).
3. A non-JSON text file is written (e.g., a log file, a CSV export).
   Non-ASCII content crashes immediately.

**The secondary problem (CRLF):** Even with ASCII content, text-mode
writes on Windows translate `\n` to `\r\n`. A snapshot file written on
Windows has CRLF line endings; the same file written on Linux has LF.
If these files are committed to Git, every line shows as changed in the
diff. The `_compute_advice_hash` function (which hashes
`json.dumps(...).encode()`) is unaffected because `json.dumps` produces
`\n` (not platform-translated) and `.encode()` produces UTF-8 bytes. So
advice hashes match across platforms. But the on-disk files differ.

**Fix:** Add `encoding="utf-8", newline=""` to every `open()` and
`os.fdopen()` call:

```python
# Before:
with os.fdopen(fd, "w") as f:
    json.dump(data, f, indent=2, default=str)

# After:
with os.fdopen(fd, "w", encoding="utf-8", newline="") as f:
    json.dump(data, f, indent=2, default=str)
```

The `newline=""` disables newline translation, ensuring LF-only output on
all platforms.

### Failure 3: `asyncio.get_event_loop()` Deprecation (R15.3)

**The scenario:** A user calls `await rt.execute_async(task)` from within
an async web framework (FastAPI, aiohttp). The `execute_async` method
(`runtime.py:242-279`) does:

```python
import asyncio
loop = asyncio.get_event_loop()
return await loop.run_in_executor(None, lambda: self.execute(task, resume=resume))
```

**On Python 3.9 and below:** `get_event_loop()` returns the running loop
if called from within a coroutine. Works fine.

**On Python 3.10-3.11:** Emits a `DeprecationWarning` if there is no
current event loop. If called from within a running coroutine, returns
the running loop. Works but warns.

**On Python 3.12+:** Behavior changed. If called from the main thread
with no running event loop, raises `RuntimeError: There is no current
event loop in thread 'MainThread'`. (Verified in this roast: Python
3.12.13 raised `RuntimeError` when called outside a running loop.)

**On Python 3.14 (planned):** `get_event_loop()` without a running loop
will always raise `RuntimeError`.

**Why the self-test doesn't catch it:** The self-test calls
`asyncio.run(rt.execute_async(task))`. `asyncio.run` creates a running
event loop, so by the time `execute_async`'s body executes (it's a
coroutine, only runs when awaited), there IS a running loop.
`get_event_loop()` returns it. No error.

**The real-world failure:** If a user calls `execute_async` from a
synchronous context WITHOUT `asyncio.run()` — for example, creating a
coroutine object and passing it to a custom event loop manager —
`get_event_loop()` may fail. More importantly, the code is using a
deprecated API that will break in Python 3.14.

**Fix:** Use `asyncio.get_running_loop()` (raises clearly if no loop) or
`asyncio.to_thread()` (Python 3.9+, simpler):

```python
# Option A: get_running_loop (raises if no loop, not deprecated)
loop = asyncio.get_running_loop()
return await loop.run_in_executor(None, lambda: self.execute(task, resume=resume))

# Option B: to_thread (simpler, Python 3.9+)
return await asyncio.to_thread(self.execute, task, resume=resume)
```

### Fix 2 (HIGH): Retry `os.replace` on Windows `PermissionError`

**File:** `srs/persistence.py`, in `_atomic_write_json`

```python

def _atomic_write_json(path, data, indent=2):

                                     dir=str(path.parent))
    tmp_path = Path(tmp_name)

            json.dump(data, f, indent=indent, default=str)
            f.flush()

    except Exception:
        try:
            tmp_path.unlink(missing_ok=True)
        except OSError:
            pass
        raise
```

## 8. Conclusion

The v7.4 SRS Runtime is **mostly cross-platform compatible** for
single-process use: all 13 self-tests pass under a simulated Windows
environment (no `fcntl`). The `fcntl` degradation path is well-designed
and correctly emits a one-time warning.

However, the runtime has **three significant cross-platform gaps** that
prevent it from being production-ready on Windows:

1. **Concurrent multi-process use is broken on Windows** (R15.2): the
   `os.replace` atomic-write strategy collides with Windows mandatory
   file locking, and the no-op `file_lock` provides zero protection.

2. **Encoding is not explicit** (R15.1): 18 `open()` calls omit
   `encoding="utf-8"`. This works today only because `json.dump` defaults
   to `ensure_ascii=True`, but it's a latent bug waiting for any change
   to `ensure_ascii=False` or a non-JSON text file write.

3. **`asyncio.get_event_loop()` is deprecated** (R15.3): the
   `execute_async` method uses a deprecated API that raises `RuntimeError`
   in Python 3.12 and will be removed in 3.14.

With the six specific fixes proposed in Section 6, the runtime can reach
**9/10 cross-platform compatibility** — the remaining 1 point being the
inherent inability to provide cross-process file locking on Windows
without a native `msvcrt.locking()` implementation.
