## Fixes Applied

### Fix 1: JSON depth limit (R17.7) — `srs/persistence.py`

**Problem.** Python's stdlib `json` module uses recursive-descent
parsing. A deeply-nested JSON document (e.g. 50 000 opening brackets)
blows the CPython recursion stack and raises `RecursionError`, which is
NOT a subclass of `JSONDecodeError` or `OSError`. The existing
`except (JSONDecodeError, OSError)` blocks in `load_latest`,
`load_in_flight`, and `list_snapshots` did not catch it — a single
malicious snapshot file would propagate the `RecursionError` up through
`Runtime.__init__` and brick every CLI command.

**Fix.** Added `SafeJSONDecoder(json.JSONDecoder)` which pre-scans the
raw input character-by-character for structural openers (`{` / `[`) and
raises `ValueError` if nesting depth exceeds `MAX_DEPTH = 100`. The
pre-scan:

- Tracks `in_string` state so bracket characters inside JSON string
  literals (e.g. `"[[[[["`) do not falsely trip the limit.
- Handles `\\` escape sequences so an escaped quote (`\"`) inside a
  string does not prematurely exit string mode.
- Is O(N) single-pass; cannot itself be DoS'd by depth.
- Delegates to `super().decode()` unchanged once the pre-scan passes, so
  the parser semantics are identical for well-formed input.

The `MAX_DEPTH = 100` constant is deliberately conservative: real-world
snapshots are never deeper than ~5 (Snapshot has 7 top-level fields,
each with at most 2 levels of nesting for `primitive_stats` /
`execution_history`). CPython's default recursion limit is 1000, so
100 leaves a 10× safety margin before `RecursionError` would even be
possible.

`_safe_json_load(f)` is a thin wrapper that injects `SafeJSONDecoder`
into `json.load`. Every `json.load(f)` call in `persistence.py` was
replaced with `_safe_json_load(f)` — 8 call sites total: 3 in
`load_latest` (latest.json locked + unlocked reads, snapshot file
read), 2 in `list_snapshots`, 2 in `load_in_flight`, 1 in `self_test`.

All `except (json.JSONDecodeError, OSError)` blocks were widened to
`except (ValueError, json.JSONDecodeError, OSError)` so the
`SafeJSONDecoder`'s `ValueError` is caught and treated as "corrupt
file" rather than propagated.

### Fix 2: AdviceTable.from_dict validation (R17.8) — `srs/primitives/advice.py`

**Problem.** `from_dict` was a one-liner: `t._table = dict(d); return t`
with no validation. Combined with the (separately fixed) R17.1
advice-hash bypass, an attacker with filesystem write access could
inject arbitrary values (strings, lists, None, huge ints) as the "answer"
returned by `lookup`. The runtime would then return that value as the
cached answer with `advice_hit=True` and `queries=0`.

**Fix.** Added strict type validation:

- `d` must be a `dict` (rejects str / list / None / int / tuple).
- Each key must be `str` (JSON object keys are always str, but a
  hand-constructed Python dict could have int keys that would break the
  `f"{h_hash}:{target_idx}"` lookup format).
- Each value must be a non-negative `int`. `bool` is explicitly rejected
  (`isinstance(True, int)` is True in Python, but `True` as an "answer
  index" is a sign of corruption).
- Negative ints are rejected (advice values are hypothesis indices).

All violations raise `ValueError` with a descriptive message. The
caller (`Runtime.__init__` and `Runtime.recover`) wraps
`AdviceTable.from_dict` in `try/except Exception` and falls back to an
empty `AdviceTable`, so a corrupt advice table degrades gracefully to
"no advice" instead of crashing the runtime.

### Fix 3: Snapshot size cap (R17.14) — `srs/persistence.py`

**Problem.** No size cap on snapshot files. A multi-GB snapshot would
OOM the process when `load_latest` called `json.load` on it. The
R17.14 PoC demonstrated a 19.8 MB snapshot with 1M advice entries
loaded in <5s, but extrapolated that ~1GB would OOM.

**Fix.** Added `MAX_SNAPSHOT_SIZE = 10 * 1024 * 1024` (10 MB) module
constant. `load_latest` now `stat()`s the snapshot file before opening
it and returns `None` (with a warning) if the file exceeds the cap.
`list_snapshots` skips oversized files rather than loading them just to
extract metadata.

The cap is exposed as a module-level attribute (`persistence.MAX_SNAPSHOT_SIZE`)
so deployments can override it:

```python
from srs import persistence
persistence.MAX_SNAPSHOT_SIZE = 50 * 1024 * 1024  # 50 MB for a fat deployment
```

The 10 MB default is generous: realistic snapshots with 10K advice
entries are ~500 KB; even 1M entries is ~20 MB (which would be
rejected, forcing the user to either prune advice or raise the cap).

### Fix 4: task_id validation (R17.9) — `srs/types.py`

**Problem.** `Task.__post_init__` did not validate `task_id`. The
default factory `uuid.uuid4().hex[:12]` always produces a safe id, but
a caller could pass a custom `task_id` containing control characters
(e.g. `"evil\x00task"`), path separators (`"../etc/passwd"`), or other
hostile content. These would propagate to logging (R17.13 log
injection) and execution_history (R17.4 untrusted-history exposure).

**Fix.** Added `_sanitize_task_id(task_id)` function and a call to it
at the end of `Task.__post_init__`:

- Non-string `task_id` raises `TypeError` (programmer error).
- A string `task_id` matching `^[a-zA-Z0-9_-]{1,64}$` is returned
  unchanged (the common case — the default factory output always
  matches).
- A string `task_id` with invalid characters has each invalid character
  replaced with `_` and is truncated to 64 chars.
- If the result is empty (e.g. input was all invalid characters), falls
  back to `uuid.uuid4().hex[:12]` so the Task always has a non-empty id.

**Why sanitize rather than reject?** Existing callers may pass ids with
spaces or other punctuation that worked by accident before. Raising
would break them. Sanitization preserves caller intent (e.g. `"my task 1"`
becomes `"my_task_1"`) while closing the security hole.

The `Task` dataclass is not `frozen`, so we use `object.__setattr__`
to mutate `task_id` in `__post_init__` (works for both frozen and
non-frozen dataclasses — defensive against a future `frozen=True`).

### Fix 5: secrets.SystemRandom for verification (R17.12) — `srs/primitives/verification.py`

**Problem.** `verify()` required `rng` as a positional argument with no
default. The runtime always passed a `random.Random` instance (seeded
from `sha256(task_id)`), which is statistically sound for the
soundness bound `P(verified=True | wrong) <= 2^-k` BUT fails against an
adaptive adversary who can predict the seed and pre-compute a passing
candidate. The bound assumes a non-adaptive adversary.

**Fix.** Changed `rng: random.Random` to `rng: random.Random | None = None`.
When `rng is None`, the function constructs `secrets.SystemRandom()` —
a CSPRNG backed by the OS entropy source (`/dev/urandom` on Linux,
`CryptGenRandom` on Windows). This enforces the non-adaptive-adversary
assumption even against an attacker who can observe the runtime's state.

**Backward compatibility.** Positional callers (the old calling
convention `verify(hyps, 7, 8, 12, 5, rng)`) still work — they pass
`rng` as the 6th positional arg, which now has a default but accepts
the explicit value. Keyword callers who omit `rng` get the secure
default. `execute_identify` (the wrapper used by the pipeline) still
passes the caller-supplied `rng` through, so reproducibility
(`random.Random(seed)`) is preserved for tests and replays.

`self_test` was extended with a call to `verify(hyps, 7, 8, 12, 5)`
(no rng) to exercise the `None` → `SystemRandom` path.

## Verification

### Deeply-nested JSON rejected (R17.7)

```python
>>> from srs.persistence import SafeJSONDecoder
>>> import json
>>> json.loads("[" * 200 + "]" * 200, cls=SafeJSONDecoder)
ValueError: JSON nesting depth exceeds 100
>>> json.loads("[" * 50_000 + "]" * 50_000, cls=SafeJSONDecoder)
ValueError: JSON nesting depth exceeds 100
>>> json.loads('{"a": {"b": {"c": [1, 2, 3]}}}', cls=SafeJSONDecoder)
{'a': {'b': {'c': [1, 2, 3]}}}
```

### Invalid advice types rejected (R17.8)

```python
>>> from srs.primitives.advice import AdviceTable
>>> AdviceTable.from_dict("not a dict")
ValueError: AdviceTable.from_dict requires dict, got str
>>> AdviceTable.from_dict({"key": "string_value"})
ValueError: advice value must be int, got str
>>> AdviceTable.from_dict({"key": -1})
ValueError: advice value must be non-negative, got -1
>>> AdviceTable.from_dict({"key": True})
ValueError: advice value must be int, got bool
>>> AdviceTable.from_dict({"abc123:7": 7})  # valid
<AdviceTable with 1 entry>
```

### Snapshot size cap (R17.14)

```python
>>> from srs import persistence
>>> persistence.MAX_SNAPSHOT_SIZE
10485760  # 10 MB
# A snapshot > 10 MB causes load_latest to return None with a warning.
```

### task_id sanitization (R17.9)

```python
>>> from srs.types import Task
>>> t = Task(kind="identify", payload={"hypotheses": [b"x"], "target_idx": 0},
...          task_id="evil\x00task")
>>> t.task_id  # null byte replaced with _
'evil_task'
>>> t = Task(kind="identify", payload={"hypotheses": [b"x"], "target_idx": 0},
...          task_id="../etc/passwd")
>>> t.task_id  # path separators replaced
'_______etc_passwd'
```

### SystemRandom for verification (R17.12)

```python
>>> from srs.primitives.verification import verify
>>> import hashlib
>>> hyps = [hashlib.sha256(f"h{i}".encode()).digest() for i in range(64)]
>>> verify(hyps, 7, 7, 12, 5)  # rng=None → SystemRandom
{'verified': True, 'verification_calls': 5, 'soundness_epsilon': 0.03125}
```
