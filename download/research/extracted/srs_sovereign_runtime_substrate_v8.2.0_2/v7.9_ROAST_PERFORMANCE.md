# v7.9 ROAST — Performance Re-Profile After Security Hardening (R20)

**Agent:** R20 (Performance Re-Roast)
**Date:** 2025-06-15
**Target:** `srs/` at `/home/z/my-project/download/srs/` (v7.8)
**Baseline:** R12 (v7.3 profile) and F5 (v7.4 perf fix)
**Question:** Has v7.5–v7.8 security hardening introduced new performance bottlenecks?

---

## 1. Executive Summary

**VERDICT: No regression on the hot path (execute()); measurable regression on the persistence path (store_state/recover). The F5 fix (gating `save_in_flight` behind `resume=True`) continues to insulate the per-call execute() cost from the v7.7/v7.8 security machinery. The persistence regression is real but acceptable for the threat model it buys.**

R12's headline finding was that `save_in_flight` consumed **75.8% of execute() wall time** in v7.3 — writing the 625-int `rng.getstate()` tuple as JSON on every call. F5 eliminated that in v7.4 by (a) gating `save_in_flight` behind `resume=True` (default `False`) and (b) skipping `rng_state` serialization entirely on the resume path. The result was a **5.81× speedup** (865 µs → 149 µs warm).

v7.5–v7.8 then layered on six pieces of security hardening that all touch the persistence layer:

| Fix | Feature | Per-call cost added |
|-----|---------|--------------------|
| F12 / v7.7 | `snapshot_hash` HMAC-SHA256 over full payload + monotonic `sequence` field + `sequence.json` high-water mark | HMAC compute (1×) on save, HMAC verify (1×) on load |
| F13 / v7.7 | `SafeJSONDecoder` char-by-char depth pre-scan (MAX_DEPTH=100) | Linear in payload size (≈30 µs/KB) |
| F14 / v7.8 | `inflight_hash` HMAC on `inflight_*.json` files | HMAC compute (1×) on save_in_flight, verify (1×) on load_in_flight |
| F15 / v7.8 | `_safe_log_value()` on every logger.* call site (28+ sites) | ~0.8 µs per call × ~6 calls per execute = ~5 µs/execute |
| F15 / v7.8 | `SafeFormatter` post-process of formatted log message | Negligible (only fires when a log record is actually emitted) |
| F6 / v7.4 | `fcntl.flock` on `latest.json`, `inflight_*.json`, `sequence.json` | ~4.3 µs per acquire+release (uncontended) |

- `file_lock` is called **300 times = 6× per cycle**. Each acquire+release is ~4 µs uncontended = **24 µs per cycle** of fcntl overhead.
- `_compute_snapshot_hash` + `_compute_seq_hash` + HMAC verifies: **~30 ms cumulative / 50 cycles = 600 µs per cycle** of HMAC + JSON serialization work (mostly JSON, HMAC itself is <1 µs).

## 5. HMAC Overhead Measurement

### 5.1 HMAC-SHA256 vs plain SHA-256

| Payload | Size | HMAC-SHA256 | SHA-256 | Overhead | Overhead % |
|---------|------|-------------|---------|----------|------------|
| Small advice table (10 entries) | 170 B | 1.22 µs | 0.34 µs | +0.87 µs | +253% |
| Medium advice table (100 entries) | 1790 B | 2.21 µs | 1.34 µs | +0.87 µs | +65% |
| Full snapshot payload (100-task advice + 100-entry history) | 20867 B | 13.59 µs | 12.56 µs | +1.03 µs | +8.2% |

**Verdict:** HMAC's per-call overhead vs plain SHA-256 is **<1 µs** at any payload size. The cryptographic padding (ipad/opad XORs + double hash) is essentially free at typical snapshot sizes. R17.1's switch from plain SHA-256 (v7.3) to HMAC-SHA256 (v7.6+) is **not a meaningful performance cost**.

### 5.2 SafeJSONDecoder overhead (THE actual regression)

| Payload | Size | Safe decoder | Plain `json.load` | Overhead | Overhead % | µs/KB safe | µs/KB plain |
|---------|------|--------------|-------------------|----------|------------|------------|-------------|
| `{}` | 2 B | 1.99 µs | 0.84 µs | +1.15 µs | +138% | 1020 | 429 |
| Small dict (5 entries) | 40 B | 3.79 µs | 1.32 µs | +2.47 µs | +187% | 97 | 34 |
| `latest.json` (typical) | 135 B | 5.83 µs | 1.40 µs | +4.42 µs | +315% | 44 | 11 |
| `inflight_*.json` (typical) | 305 B | 11.43 µs | 2.36 µs | +9.07 µs | +384% | 38 | 8 |
| `sequence.json` | 94 B | 4.65 µs | 1.20 µs | +3.45 µs | +288% | 51 | 13 |
| Small snapshot (5-task advice) | 425 B | 15.44 µs | 3.13 µs | +12.31 µs | +393% | 37 | 8 |
| Medium snapshot (100-task advice) | 20638 B | 640.49 µs | 96.11 µs | +544.37 µs | +566% | 32 | 5 |

**Verdict:** `SafeJSONDecoder`'s char-by-char Python pre-scan is **5–10× slower per KB** than CPython's C `json` decoder. The overhead is linear in payload size. For typical small files (~1 KB), the absolute cost is ~12 µs/call — acceptable. For larger snapshots (~20 KB), it's **544 µs/call** — material.

## 7. Top 5 Performance Bottlenecks (Ranked)

### #1 — `SafeJSONDecoder` char-by-char pre-scan (NEW in v7.7, R17.7)

**Cost:** ~30 µs/KB on small files, ~32 µs/KB on large files. For a 20 KB snapshot, that's **+544 µs per `load_latest()` call** (+571% over plain `json.load`).

**Why it's #1:** It's the largest single v7.8-specific overhead, and it fires on EVERY `load_latest()` / `load_in_flight()` / `_get_high_water_sequence()` call. A single `store_state() + recover()` cycle does **4 SafeJSONDecoder decodes**. At small payload sizes (~1 KB), it's ~50 µs of pure pre-scan overhead per cycle; at 20 KB it's ~2.2 ms per cycle.

**Why it exists:** Defense against RecursionError DoS (R17.7) — without the depth cap, a malicious snapshot with 50,000 nested brackets would crash the runtime. The pre-scan is correct, but it's implemented in pure Python instead of C.

**Mitigation:** Either (a) replace the Python char-by-char pre-scan with a regex-based depth check (single C-level scan), or (b) use `json.loads(s, cls=...)` with a `parse_int`/`parse_float` hook that tracks depth during the actual C parse, or (c) gate the pre-scan behind a size threshold (skip for files < 1 KB; malicious tiny files can't trigger RecursionError anyway because the recursion depth is bounded by file size).

### #2 — `_get_secret_key()` re-reads `~/.srs/secret_key` on every HMAC call (NEW in v7.7, R17.1)

**Cost:** 5 disk syscalls per `store_state + recover` cycle (one per HMAC compute or verify). Cumulative: **24 ms / 50 cycles = 480 µs per cycle** just to re-read the same 32-byte key 5 times.

**Why it's #2:** It's the second-largest v7.8-specific overhead. Each call does:
```
Path.home() / ".srs" / "secret_key"  → pathlib path construction
parent.mkdir(parents=True, exist_ok=True)  → mkdir(2) syscall (no-op if exists)
key_path.exists()  → stat(2) syscall
key_path.read_bytes()  → open(2) + read(2) + close(2)
```
That's 4–5 syscalls per HMAC computation, for a key that **literally never changes** during a process lifetime.

**Mitigation:** Cache the key in a module-level variable after first read. Add a `_invalidate_secret_key_cache()` function for tests that swap out the key file.

### #3 — `advice._fingerprint` is O(N) and runs on every warm `execute()` (PRE-EXISTING, R12 finding)

**Cost:** 36% of warm `execute()` wall time (29 ms / 80 ms profiled = 290 µs under profiler, ~52 µs without profiler per warm call at N=256). Scales linearly with N.

**Why it's #3:** This is the same bottleneck R12 called out — `advice._fingerprint` SHA-256s the entire hyps list to produce the cache key. It is **NOT** a v7.8 regression; it predates the security hardening. But it's still the dominant warm-path cost and now larger than the v7.8 security overhead.

**Mitigation (unchanged from R12):** Hash the hypothesis set once at Task construction (or cache by `id(hyps)` + len + first/last bytes) and use the cached hash as the advice key. Reduces warm-path O(N) to O(1).

### #4 — `store_state()` does 3 atomic writes (NEW in v7.7: +1 for `sequence.json`)

**Cost:** v7.4 did 2 atomic writes per `store_state()` (snap_*.json + latest.json). v7.8 does 3 (snap_*.json + latest.json + sequence.json). Each atomic write is ~350 µs (tempfile + JSON encode + fsync + os.replace). The +1 write adds **~280 µs per `store_state()` call**.

**Why it's #4:** Unavoidable for the rollback protection design (R17.5 requires sequence.json to be HMAC-protected and updated atomically after the snapshot write). The order is correct: write snapshot → write latest.json → update sequence.json (so a crash leaves sequence conservative).

**Mitigation:** Combine `latest.json` + `sequence.json` into a single `index.json` file. One atomic write instead of two. Saves ~280 µs per `store_state()`.

### #5 — `_safe_log_value` adds ~5 µs per `execute()` (NEW in v7.8, R17.13)

**Cost:** ~0.8 µs per call × 6 calls per execute = ~5 µs per warm `execute()`. That's 5% of warm wall time at our 96 µs/call baseline.

**Why it's #5:** It's the only v7.8-specific overhead that fires on the hot path (every `execute()` call, not just persistence). It's small in absolute terms but it's the one cost that wasn't present in v7.4's hot path.

**Mitigation:** Make `_safe_log_value` a no-op when logging is disabled (i.e. check `logger.isEnabledFor(DEBUG)` before calling `_safe_log_value` at each site). Or, simpler, replace the Python char-by-char strip with `re.sub(r'[\x00-\x1f\x7f-\xff]+', '', value)[:max_len]` (one C-level regex).

## 9. Specific Optimizations Required

### 9.1 Cache `_get_secret_key()` (HIGH impact, LOW effort) — eliminates bottleneck #2

Replace the current implementation:
```python
def _get_secret_key() -> bytes:
    key_path = Path.home() / ".srs" / "secret_key"
    key_path.parent.mkdir(parents=True, exist_ok=True)
    if key_path.exists():
        return key_path.read_bytes()
    ...
```

With:
```python
_SECRET_KEY_CACHE: bytes | None = None

def _get_secret_key() -> bytes:
    global _SECRET_KEY_CACHE
    if _SECRET_KEY_CACHE is not None:
        return _SECRET_KEY_CACHE
    key_path = Path.home() / ".srs" / "secret_key"
    ...
    _SECRET_KEY_CACHE = key
    return key

def _invalidate_secret_key_cache() -> None:
    """For tests that swap the key file."""
    global _SECRET_KEY_CACHE
    _SECRET_KEY_CACHE = None
```

**Expected speedup:** Eliminates 5 disk-syscall sequences per `store_state + recover` cycle. Estimated savings: **~480 µs per cycle** (35% of the +609 µs persistence regression).

### 9.2 Replace `SafeJSONDecoder` char-by-char pre-scan with a regex-based depth check (HIGH impact, MEDIUM effort) — eliminates bottleneck #1

The current implementation iterates over every character in Python:
```python
for c in s:
    if in_string:
        if escape: escape = False
        elif c == "\\": escape = True
        elif c == '"': in_string = False
        continue
    ...
```

Replace with a single C-level regex that counts open brackets OUTSIDE string literals:
```python
import re
# Match brackets that are NOT inside a JSON string literal.
# This is approximate but conservative — it over-counts depth if a string
# contains an unescaped quote followed by a bracket, which would never
# happen in valid JSON. SafeJSONDecoder rejects invalid JSON anyway via
# the underlying json.JSONDecoder.
_BRACKET_RE = re.compile(r'"(?:\\.|[^"\\])*"|\{|\[')

def _max_depth(s: str) -> int:
    depth = 0
    max_depth = 0
    for m in _BRACKET_RE.finditer(s):
        tok = m.group()
        if tok == '{' or tok == '[':
            depth += 1
            if depth > max_depth:
                max_depth = depth
        else:
            # String literal — skip
            pass
    # Note: this doesn't decrement on '}' or ']', so it counts CUMULATIVE
    # opens, not actual depth. For DoS protection, cumulative opens is the
    # right metric (RecursionError is triggered by total open brackets
    # in the parser's recursion stack).
    return max_depth
```

Or simpler — gate the pre-scan by size:
```python
def _safe_json_load(f):
    if hasattr(f, 'seek'):
        pos = f.tell()
        f.seek(0, 2)
        size = f.tell()
        f.seek(pos)
        if size < 1024:  # Small files can't trigger RecursionError
            return json.load(f)
    return json.load(f, cls=SafeJSONDecoder)
```

**Expected speedup:** Eliminates the 30 µs/KB pre-scan overhead. For a 20 KB snapshot, saves **~544 µs per `load_latest()` call**. For a typical 1 KB snapshot, saves ~30 µs.

### 9.3 Combine `latest.json` + `sequence.json` into a single `index.json` (MEDIUM impact, MEDIUM effort) — eliminates bottleneck #4

Currently `save()` does 3 atomic writes (snap + latest + sequence). Combine `latest.json` (snapshot_id, path, timestamp, sequence) with `sequence.json` (high_water, seq_hash) into a single `index.json`:
```json
{
  "latest": {"snapshot_id": "...", "path": "...", "timestamp": "...", "sequence": 42},
  "high_water": 42,
  "index_hash": "<HMAC over both fields>"
}
```

**Expected speedup:** Eliminates 1 atomic write per `save()` = **~280 µs per `store_state()` call**. Also eliminates 1 fcntl.flock acquisition.

### 9.4 Cache `advice._fingerprint` by `id(hyps)` (HIGH impact on warm path, MEDIUM effort) — eliminates bottleneck #3 (PRE-EXISTING from R12)

R12 already recommended this; v7.8 didn't address it. The warm path is dominated by `advice._fingerprint` (36% of wall time at N=256, growing to ~80% at N=16384). Cache the SHA-256 by `id(hyps)` so the same list isn't re-hashed on every `execute()`:
```python
class AdviceTable:
    _fingerprint_cache: dict[int, str] = {}  # id(hyps) -> fingerprint
    
    def _fingerprint(self, hyps):
        key = id(hyps)
        if key in self._fingerprint_cache:
            return self._fingerprint_cache[key]
        # ... existing computation ...
        self._fingerprint_cache[key] = result
        return result
```

**Expected speedup:** Eliminates ~52 µs per warm `execute()` at N=256. At N=16384, saves **~4 ms per warm execute** (the warm path's dominant cost).

### 9.5 Gate `_safe_log_value` behind `logger.isEnabledFor()` (LOW impact, LOW effort) — eliminates bottleneck #5

```python
if logger.isEnabledFor(logging.DEBUG):
    logger.debug("execute: start task_id=%s ...", _safe_log_value(task.task_id))
```

**Expected speedup:** Eliminates ~5 µs per warm `execute()` when DEBUG logging is disabled (the default). Combined with the regex-based replacement in 9.2, eliminates the entire R17.13 hot-path cost.

## 10. Conclusion

**Has v7.5–v7.8 security hardening regressed performance?**

- **On the hot path (`execute()`): NO.** Same-machine delta is +3.4% warm, +1.8% cold — within noise. F5's `save_in_flight` gating continues to insulate the per-call cost.
- **On the persistence path (`store_state()` / `recover()`): YES, materially.** +60.5% / +178.8%. The regression is attributable to specific, identifiable additions:
  - SafeJSONDecoder char-by-char pre-scan (largest single cost)
  - `_get_secret_key()` re-reading the key file on every HMAC call (5× per cycle)
  - +1 atomic write per save (sequence.json)
  - HMAC computation itself (negligible — <1 µs overhead vs plain SHA-256)
  - fcntl.flock (negligible — 4 µs per acquire+release)

**The persistence regression is acceptable for the threat model** (snapshot tampering, rollback attacks, RecursionError DoS, log injection) but is fixable with three surgical changes:
1. Cache `_get_secret_key()` (saves ~480 µs/cycle, 35% of the regression)
2. Replace SafeJSONDecoder's pre-scan with a regex or size-gated check (saves ~544 µs/cycle on large snapshots, ~30 µs on small)
3. Combine latest.json + sequence.json into a single index.json (saves ~280 µs/cycle)

**Total potential savings:** ~800 µs/cycle on small payloads, ~1.6 ms/cycle on 20 KB payloads. This would bring v7.8 persistence performance back to within 10% of v7.4-simulated baseline.

**Recommendation:** Ship v7.8 as-is. Schedule optimizations 9.1 and 9.2 for v7.9 (both are <50 LOC changes with clear test coverage). Defer 9.3 (index.json merge) and 9.4 (advice._fingerprint cache) to v7.10 — they're larger surface-area changes that need more test coverage.
