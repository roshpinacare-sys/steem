## 1. Executive Summary

The v7.1 SRS Runtime has the right *shape* — Pipeline, Planner, Persistence, Primitives, Improvement — but four of its seven primitives are non-functional inside the pipeline, the planner is detached from the pipeline's actual behavior by a factor of 3.7×, and the "in-flight recovery" advertised in the docstring is theatre. The architect's admitted issue ("stages don't share state") is real and I confirm it, but it is the *tip* of the iceberg: the same root cause (no `PipelineState` carried between stages) silently breaks verification, compression, resume, and the cost model. The verification stage always returns `verified=True` because `runtime.py:95-96` passes the ground-truth `target_idx` as the candidate. The compression stage is dead because `pipeline.py:61` aggregates storage with `max()`, so C's smaller storage is discarded. The Q stage for search tasks calls `quantum.execute_identify` (the BBBV no-advantage identify) instead of `grover_search`, so the planner's "Grover O(√N)" estimate never matches reality. `execute(task, resume=True)` sets a private `task._resumed_from` attribute that no stage ever reads; the pipeline runs from scratch. There is no `try/finally` around pipeline execution, so a single raised primitive leaks an `inflight_*.json` file forever. Concurrent `execute()` calls lose primitive-stat updates (verified: 8 threads → V got 7/8 runs). `plan('unknown_kind')` raises `AttributeError` because `TASK_AXIS.get(kind, "time")` returns `"time"` and `CostEstimate` has no `time` field. The architect's 9/10 is **not justified**. Real score: **4/10**. The missing point isn't "stages don't share state" — it's "the architecture silently lies about what it does, and the test suite asserts names instead of behavior, so the lies pass."

## 3. Top 3 Critical Issues

### 3.1 R1.1 — Verification Stage is Theatre

**Location:** `runtime.py:95-96`
```python
elif p == "V":
    pipe.add("V", verification_stage, verify_budget=5,
             candidate=task.payload.get("target_idx", 0))
```

**What's wrong:** The `candidate` argument to `verification_stage` is set to `task.payload["target_idx"]` — the GROUND TRUTH answer that the runtime is supposed to discover. Inside `verification_stage` (`pipeline.py:183`), `candidate = kw.get("candidate", target)`. Then `verification.verify` (`primitives/verification.py:26-27`) short-circuits: `if candidate_idx == target_idx: return {"verified": True, ...}`. So verification ALWAYS returns `verified=True`, regardless of what the previous stages actually concluded.

**Empirical proof:** I executed a task with `budget=1, required_primitives=["E","A","V"]`. The pipeline returned `correct=False, answer=0` (wrong — adaptivity couldn't identify in 1 query) but `verified=True`. The verification stage "verified" an answer that wasn't even produced by the pipeline. CLI exit code 3 (`verify-fail`) is **unreachable**.

**Why this is critical:** The V primitive is one of the seven advertised primitives. The entire point of V is to catch wrong answers probabilistically. If V always returns True, the runtime provides zero correctness guarantees. The `soundness_epsilon = 2^-k` claim in the result notes is a lie — the empirical soundness is `epsilon = 0` (wrong answers are never caught).

**Fix:** Requires R1.2 (PipelineState). The verification stage must receive the previous stage's `answer` as `candidate`, not the ground truth. Concretely:
```python
# In Pipeline.execute, after each stage:
state.answer = r.get("answer", state.answer)
# When adding V stage:
pipe.add("V", verification_stage, verify_budget=5)  # no candidate arg
# In verification_stage:
def verification_stage(state, task, rng, **kw):
    candidate = state.answer  # from previous stage, NOT ground truth
    ...
```

**Test that would catch it:**
```python
def test_verification_catches_wrong_answer():
    hyps = [hashlib.sha256(f"h{i}".encode()).digest() for i in range(64)]
    task = Task(kind="identify",
                payload={"hypotheses": hyps, "target_idx": 7, "n_features": 12},
                budget=1,  # too small — adaptivity will be wrong
                required_primitives=["E", "A", "V"])
    rt = Runtime(home=Path(tempfile.mkdtemp()))
    r = rt.execute(task)
    assert not r.correct, "budget=1 should fail"
    assert r.verified is False, "V must catch the wrong answer"
```
This test currently fails: `verified` is `True`.

### 3.2 R1.2 — Pipeline Stages Don't Share State (The Architect's Admitted Issue, With Consequences)

**Location:** `pipeline.py:56-72`

**What's wrong:** `Pipeline.execute` calls each stage as `stage.fn(task=task, rng=rng, **stage.args)`. Each stage receives only the original `Task` and `rng` — never the output of previous stages. There is no `PipelineState` threaded through. Concretely:

- `execution_stage` makes 16 queries and returns `answer=best_idx`.
- `compression_stage` doesn't see E's transcript; it just reports a storage number.
- `adaptivity_stage` re-runs 16 queries from scratch (it has its own `alive = set(range(len(hyps)))`), ignoring E's work entirely.
- `verification_stage` can't see A's answer, so `runtime.py` hacks around it by passing `target_idx` as `candidate` (→ R1.1).
- `advice_stage` doesn't see previous stages' answers; if advice misses, it returns a no-op dict, and the pipeline's final `answer` is whatever the LAST answer-producing stage said.

The architect wrote: *"stages still don't share state mid-pipeline. Fixing that requires a larger refactor of the stage signatures."* This is true. But the consequence is not just "suboptimal" — it's that **three primitives (C, V, Adv) are non-functional in the pipeline**, and the planner's cost model assumes state-sharing that doesn't happen (R1.4).

**Fix:** Introduce a `PipelineState` dataclass:
```python
@dataclass
class PipelineState:
    alive: Set[int] = field(default_factory=set)
    queries: List[Tuple[int, int]] = field(default_factory=list)
    answer: Optional[int] = None
    correct: Optional[bool] = None
    verified: Optional[bool] = None
    transcript: List[Any] = field(default_factory=list)
    budget_remaining: int = 0
    storage_bytes: int = 0
    work_units: int = 0
    depth: int = 0
    notes: Dict[str, Any] = field(default_factory=dict)

# Stage signature becomes:
StageFn = Callable[[PipelineState, Task, random.Random, Any], PipelineState]

# Pipeline.execute threads state:
def execute(self, task: Task, rng: random.Random) -> Result:
    state = PipelineState(alive=set(range(len(task.payload["hypotheses"]))),
                          budget_remaining=task.budget)
    for stage in self.stages:
        state = stage.fn(state, task, rng, **stage.args)
    return Result(task_id=task.task_id, answer=state.answer, ...)
```

This is the "larger refactor" the architect deferred. It is required, not optional.

**Test that would catch it:**
```python
def test_adaptivity_reuses_execution_transcript():
    hyps = [hashlib.sha256(f"h{i}".encode()).digest() for i in range(64)]
    task = Task(kind="identify",
                payload={"hypotheses": hyps, "target_idx": 7, "n_features": 12},
                budget=16, required_primitives=["E", "A"])
    rt = Runtime(home=Path(tempfile.mkdtemp()))
    r = rt.execute(task)
    # If A reuses E's transcript, total queries < 2 * budget
    assert r.queries <= task.budget + 2, \
        f"A should reuse E's transcript; got {r.queries} queries"
```
Currently `r.queries == 22` (16 from E + 6 from A).

### 3.3 R1.4 — Planner Estimates Are 3.7× Off From Reality

**Location:** `planner.py:75-130` vs `pipeline.py:56-87`

**What's wrong:** The planner's `estimate_cost` assumes primitives "replace" each other. For `["E","C","A"]` with `n=64, budget=16`:
- Line 80-81: `if not has_a: queries = max(queries, budget)` — E's queries are SKIPPED because `has_a` becomes True when A is processed.
- Line 94-95: `q_a = min(budget, log2(n))` = 6; `queries = q_a`.
- Final estimate: `queries = 6`.

But the pipeline actually runs **both** E and A as independent stages:
- `execution_stage` makes `budget=16` queries.
- `compression_stage` makes 0 queries.
- `adaptivity_stage` makes up to `budget=16` queries (breaks early at ~6 when `alive <= 1`).
- `Pipeline.execute` sums them: `total_queries = 16 + 0 + 6 = 22`.

**Empirical proof:** I ran `rt.plan_task(task)["estimated_cost"]["queries"]` → `6`. Then `rt.execute(task).queries` → `22`. The planner is off by **3.7×**.

**Why this is critical:** The planner's entire purpose is to pick the lowest-cost primitive set. If the cost model doesn't match the pipeline's behavior, the planner's choices are meaningless. The "cost-model planner" is theatre. The architect's roast-fix table claims: *"Planner now uses cost model, not dict lookup (#6)"* — but the cost model is wrong.

**Root cause:** The planner models primitives as if they share state (A "replaces" E's queries), but the pipeline runs them independently (no state sharing, per R1.2). The planner and pipeline are detached.

**Fix:** Two options, pick one:
1. **Make the pipeline match the planner:** Skip E when A is present. The pipeline becomes `[C, A, V]` (no E). Then planner's "A replaces E" is accurate.
2. **Make the planner match the pipeline:** `estimate_cost` should ADD queries across stages: `queries = E.budget + A.min(budget, log_n) + V.verify_budget`. Then `plan()` would correctly prefer `[A]` alone (6 queries) over `[E, A]` (22 queries).

Option 2 is more honest. Option 1 requires R1.2 first.
