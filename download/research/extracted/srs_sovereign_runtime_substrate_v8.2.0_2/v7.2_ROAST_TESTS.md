# v7.2 Roast: Test Quality Audit of v7.1 SRS Runtime Suite

**Agent:** R2 (Test Quality Roaster)
**Scope:** `tests/test_srs_runtime.py` (39 tests) + `tests/test_integration_v7.py` (11 tests) = 50 tests
**Architect's claim:** 50/50 passing, 0 tautologies, test quality 10/10.
**Method:** Read every test, read every module under test, then *probed each assertion in a live Python session* to determine whether it can fail when the claim it claims to verify is actually false.

---

## 1. Executive Summary

The v7.1 suite is **substantially better than v7.0** — the architect really did delete the eleven `assert self_test() == "X OK"` tautologies and replace them with tests that call into real module functions. That part is genuine progress and deserves credit.

But "0 tautologies" is **false**. After live probing, I count:

- **3 hidden tautologies** (assertions that are true by construction of the implementation under test, not by behavior).
- **6 circular / self-referential assertions** (the test uses the result to predict the result).
- **5 conditional / disjunctive assertions** that are vacuously satisfied because one branch is unreachable in practice.
- **4 misleading-name tests** whose docstring or function name makes a claim the assertion does not verify — including one **CRITICAL** case where the named property (`r2.queries == 0` on second run) is *actually false* in the implementation, and the test passes anyway because the assertion only checks `len(advice._table) >= 1`.
- **2 off-by-N wiggles** where the math gives an exact answer but the test uses a loose bound.
- **7 missing edge cases** that the suite never exercises (empty input, N=1, budget=0, budget=-1, out-of-range target, wrong advice, true resume).
- **5 integration tests that are still self_test-and-check-PASSED in disguise**, or that create an object and never call it.
- **1 test that pollutes `/tmp`** with a non-`TemporaryDirectory` path.

**Real test-quality score: 6 / 10.** The architect's 10/10 is not justified. The suite is good enough to ship, but it is not airtight, and the worst offender (`test_runtime_self_improvement_second_run_uses_advice`) is actively misleading because its name promises a guarantee the runtime does not deliver.

The single most important finding: **the runtime's advice optimization is broken in `Runtime.execute()`** — when advice is pre-seeded, the second run still makes 27 queries because the pipeline runs every stage to completion regardless of whether `Adv` hits. The test whose name promises to catch this passes anyway, because the assertion was weakened to "advice table has ≥1 entry".

## 3. Top 3 Worst Tests (Detailed Analysis)

### #1 — `test_runtime_self_improvement_second_run_uses_advice` (R2.1, CRITICAL)

**What the name promises:** After a first successful identification, the runtime seeds its advice table; a second run of the same task should hit advice and complete in **0 queries**.

**What the assertion checks:** `len(rt.advice._table) >= 1`.

**Live probe:**
```python
rt = Runtime(home=Path(tmp))
task = Task(kind="identify", payload={...}, budget=16)
r1 = rt.execute(task)   # r1.queries=22, r1.correct=True
r2 = rt.execute(task)   # r2.queries=27, r2.correct=True  ← NOT 0!
len(rt.advice._table)   # 1  ← assertion passes
```

**Why the second run makes 27 queries, not 0:** `Runtime.execute()` builds a `Pipeline` from the planned primitive set `[E, C, A, V, Adv]` and calls `pipe.execute(task, rng)`. `Pipeline.execute()` runs **every stage to completion** in order, accumulating `total_queries += r.get("queries", 0)` from each stage. `execution_stage` makes `budget=16` queries. `adaptivity_stage` makes 6 queries. `verification_stage` makes 5. `advice_stage` makes 0 (it hits) — but by then 27 queries have already been spent. The advice is consulted last and its answer is discarded (each stage overwrites `answer`).

**The bug:** The runtime never short-circuits the pipeline when advice hits. The cost model claims `queries=0` for `[E,C,A,V,Adv]`, but the actual execution makes 27 queries. The planner's cost estimate is therefore a **lie** — it does not predict the runtime's actual behavior.

**The test's sin:** It is named after the property "second run uses advice (0 queries)" but only asserts "advice has ≥1 entry". The assertion would pass even if `r2.queries == 10000`. The test gives a false sense that the advice optimization works.

**Required replacement:**
```python
def test_runtime_self_improvement_second_run_uses_advice():
    with tempfile.TemporaryDirectory() as tmp:
        rt = Runtime(home=Path(tmp))
        hyps = [hashlib.sha256(f"h{i}".encode()).digest() for i in range(64)]
        task = Task(kind="identify",
                    payload={"hypotheses": hyps, "target_idx": 7, "n_features": 12},
                    budget=16)
        r1 = rt.execute(task)
        assert r1.correct
        r2 = rt.execute(task)
        assert r2.correct
        assert r2.queries == 0, f"advice should short-circuit; got {r2.queries}"
        assert r2.primitives_used == ["Adv"]
```
This test will **fail today** — which is the entire point of having a test suite. The current passing test is worse than no test, because it conceals a real architectural defect.

### #2 — `test_adaptivity_prunes_alive_set` (R2.2, CRITICAL)

**What the name promises:** "After each query, the alive set should not grow." The docstring elaborates: with `budget=1`, the alive set should be roughly halved.

**What the assertion checks:** `r["queries"] == 1`.

**Why this is a tautology:** `adaptivity.execute_identify` sets `queries_made = 0` and increments it once per loop iteration (`queries_made += 1` inside `for _ in range(budget)`). With `budget=1`, the loop runs once, so `queries_made == 1` is true **by construction of the loop counter**, not by any behavioral property. The alive-set pruning claim — the entire reason the test exists — is not measured at all.

The test author even acknowledges this in a comment: `# We can't directly check alive set size, but queries should be 1`. They wrote the test knowing it didn't measure the claimed property, and shipped it anyway.

**Required replacement:** Add a `trace` mode to `adaptivity.execute_identify` that returns the alive-set size after each query, then assert the sequence is monotonically non-increasing and roughly halves per step.

```python
def test_adaptivity_prunes_alive_set_monotonically():
    rng = random.Random(42)
    N = 256
    hyps = [hashlib.sha256(f"h{i}".encode()).digest() for i in range(N)]
    r = adaptivity.execute_identify(hyps, 100, 12, 12, rng, _trace=True)
    sizes = r["notes"]["alive_sizes"]  # [256, ~128, ~64, ~32, ~16, ~8, ~4, ~2, 1]
    assert sizes[0] == N
    assert all(sizes[i+1] <= sizes[i] for i in range(len(sizes)-1))
    assert sizes[-1] == 1
    # Roughly halving:
    for i in range(len(sizes)-1):
        assert sizes[i+1] <= sizes[i] * 0.6 + 1  # allow some slack
```

### #3 — `test_scheduling_adds_parallel_depth` (R2.3, HIGH)

**What the name promises:** "S should add parallel depth beyond adaptivity's sequential depth."

**What the assertion checks:** `r_s["depth"] >= r_a["depth"]`.

**Why this is a hidden tautology:** Look at `scheduling.execute_identify` (lines 30–54):
```python
for _ in range(budget):
    ...
    depth += 1  # sequential query
    parallel_depth = max(1, math.ceil(...))
    depth += parallel_depth  # parallel pruning depth
```
So `scheduling.depth == adaptivity.depth + sum(parallel_depth_per_step)`, and `parallel_depth = max(1, ...) >= 1` always. Therefore `scheduling.depth >= adaptivity.depth + budget > adaptivity.depth` — the assertion **cannot fail** unless `budget == 0` (which the test doesn't use).

Live probe: `r_a.depth=8`, `r_s.depth=23`. The 15-unit gap is `parallel_depth * queries_made = 2.5 * 6 ≈ 15` (approximate). The test could fail to detect a regression where `parallel_depth` is hardcoded to 1 instead of computed from `log2(N)/log2(W)`.

**Required replacement:**
```python
def test_scheduling_adds_parallel_depth():
    rng1 = random.Random(42)
    rng2 = random.Random(42)
    hyps = [hashlib.sha256(f"h{i}".encode()).digest() for i in range(256)]
    r_a = adaptivity.execute_identify(hyps, 100, 12, 16, rng1)
    r_s = scheduling.execute_identify(hyps, 100, 12, 16, rng2, n_workers=8)
    # parallel_depth per step = max(1, ceil(log2(N)/log2(W))) = max(1, ceil(8/3)) = 3
    expected_extra = r_a["queries"] * 3
    assert r_s["depth"] == r_a["depth"] + expected_extra
    # Also: more workers should reduce parallel depth
    r_s2 = scheduling.execute_identify(hyps, 100, 12, 16, random.Random(42), n_workers=256)
    assert r_s2["depth"] < r_s["depth"]  # 256 workers → parallel_depth=1
```

### 4.2 Statistical power gaps

- `test_verification_wrong_candidate_caught_with_high_probability`: 50 trials, k=10, threshold ≤2 escapes. Statistically this is OK (P(false-fail) ≈ 6×10⁻⁴), but the threshold of 2 is conservative. A proper one-sided binomial test would set the threshold at 1 escape for 50 trials (still P(false-fail) ≈ 5%).
- `test_quantum_grover_can_fail`: 20 trials, `success_prob=0.1`, threshold ≥10 failures. As shown in R2.16, this passes 59% of the time even when `success_prob=0.5`. **Insufficient statistical power.**
