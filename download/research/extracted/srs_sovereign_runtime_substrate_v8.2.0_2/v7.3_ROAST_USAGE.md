# v7.3 Roast — Real-World Usage Simulation (Agent R10)

**Agent**: R10 (Real-World Usage Simulation Roaster)
**Target**: SRS Runtime v7.2.0 at `/home/z/my-project/download/srs/`
**Methodology**: Execute every documented usage scenario verbatim, capture exact output and error text, report what a real developer would experience.
**Date**: 2025-07-17

---

## 1. Executive Summary

I treated the SRS Runtime v7.2 as a black box and ran the eight usage scenarios a real developer would run on first contact with the package. The headline finding is **catastrophic**: the runtime cannot be instantiated with default settings because `srs.persistence.default_path()` is **referenced four times across `persistence.py` and `runtime.py` but never defined**. Every CLI command that creates a `Runtime()` without an explicit `--home` flag crashes with `AttributeError`. The `--help` flow works, `list-kinds` works, and `self-test` works (it uses tempdirs internally), but every other command — `capabilities`, `snapshot`, `recover`, `execute`, `plan`, `bench` — requires the user to know to pass `--home`. The README and `--help` text say `--home` is *optional* (default: `~/.srs/snapshots/`), but the default path is broken.

Beyond that showstopper, I documented:
- **Two more CRITICAL bugs**: `execute identify 999999999` causes an uncontrolled memory blow-up (the CLI materialises a list of 1 billion 32-byte SHA-256 digests, ~200 GB) and is OOM-killed by the kernel; corrupting `latest.json` or any `snap_*.json` with invalid JSON causes an unhandled `JSONDecodeError` traceback that aborts the entire CLI.
- **Six HIGH bugs**: `list-kinds` reports 8 valid kinds but `execute` accepts only 5; the planner reports `queries=0` whenever any advice exists regardless of whether the advice applies (actual run made 13 queries vs planned 0); `bench` ignores `--home` and writes its results to a hardcoded path inside the package directory; orphaned snapshots accumulate unboundedly; `recover` ignores in-flight task state when no snapshot exists; `execute verify` is effectively a no-op (`verification_calls=0` against planned 5, returns `verified=False` with `soundness_epsilon=1.0`).
- **Multiple MEDIUM issues**: `capabilities.total_executions` counts primitive-runs not task-runs; `success_rate` treats `correct=None` (verify tasks) as failure; self-test emits a scary "advice hash mismatch" warning that is actually expected behaviour; the advice-hash warning is printed twice on recover.
- **Several LOW issues**: negative/zero budget not validated; `snapshot` on an empty home succeeds silently with no warning; read-only home directories cause Python tracebacks; no CLI surface for resuming interrupted tasks (only Python API).

**Scenario pass/fail**: 4 PASS, 4 FAIL out of 8 scenarios when run exactly as documented (Scenario 1 fails because `capabilities` crashes; Scenario 3 fails because `execute ... --persist` then `snapshot` then `recover` works only if `--home` is passed; Scenario 5 produces a result but writes to the wrong location; Scenario 7 includes a hard OOM crash and two unhandled JSONDecodeErrors).

**Usability score: 3 / 10.** The runtime is usable for an expert who knows to pass `--home` everywhere, but a first-time user following the README will hit `AttributeError` on `capabilities` and conclude the package is broken. The CLI surface is internally inconsistent (`list-kinds` vs `execute` accept different kind sets), and the most-asked-for operation (`execute verify`) is a no-op that returns success-ish output while reporting `verified=False`.

## 3. Top 3 Worst User Experiences

### Worst UX #1: First-time user runs `srs capabilities` and gets a Python traceback

**Reproduction** (verbatim from the scenario brief):
```bash
$ cd /home/z/my-project/download
$ python3 srs/cli.py capabilities
Traceback (most recent call last):
  File "/home/z/my-project/download/srs/cli.py", line 342, in <module>
    sys.exit(main())
             ^^^^^^^^^^^^^^^^^^^^^^^
  File "/home/z/my-project/download/srs/cli.py", line 324, in main
    return cmd_capabilities(args)
             ^^^^^^^^^^^^^^^^^^^^^^
  File "/home/z/my-project/download/srs/cli.py", line 115, in cmd_capabilities
    rt = Runtime(home=args.home)
         ^^^^^^^^^^^^^^^^^^^^^^^^
  File "/home/z/my-project/download/srs/runtime.py", line 38, in __init__
    self.home = persistence._coerce_path(home or persistence.default_path())
                                                 ^^^^^^^^^^^^^^^^^^^^^^^^
AttributeError: module 'srs.persistence' has no attribute 'default_path'
```

**Why this is the worst**: `capabilities` is the very first command a curious user runs after `--help`. The traceback is a developer-facing error message — there is no friendly "no home directory configured, please pass --home" hint. The user has no way to know that the fix is to pass `--home /tmp/foo`. The `--help` text explicitly says `--home` is optional with default `~/.srs/snapshots/`, so the user has no reason to believe they need to pass it.

The root cause is a one-line missing function: `persistence.default_path()` is **referenced at `persistence.py:98`, `persistence.py:119`, `persistence.py:158`, and `runtime.py:38`** but is **never defined** anywhere in the `srs/` package. A grep for `def default_path` returns zero matches in `/home/z/my-project/download/srs/`. The function does exist in the older `srs_runtime/srs/persistence.py` (line 16) — strongly suggesting that during the v7.2 refactor, the function was deleted but its callers were not updated. This means **v7.2 was shipped without ever being run end-to-end via the CLI**, because every command except `self-test`, `list-kinds`, and `--help` triggers the crash. The 65/65 test suite passes only because every test passes `home=Path(tmpdir)` explicitly.

**Severity**: CRITICAL. This is the single most damaging bug in the release. It blocks first-time adoption entirely.

### Worst UX #2: `execute identify 999999999` causes silent OOM kill

**Reproduction**:
```bash
$ python3 srs/cli.py --home /tmp/srs_h execute identify 999999999
# (long pause, then kernel kills the process)
$ echo $?
137   # SIGKILL from OOM
```

No output, no error message, just a killed process. The user has no idea what happened.

**Why this happens**: `cmd_execute` in `cli.py:134` does:
```python
n = args.n
hyps = [hashlib.sha256(f"h{i}".encode()).digest() for i in range(n)]
```

This materialises a Python list of `n` 32-byte digests **before any validation or execution**. For `n=999_999_999`, that is approximately 32 GB of `bytes` objects plus list overhead — observed peak RSS was 198 MB for `n=1_000_000` (linear, ~200 bytes/hypothesis including Python object overhead), so `n=10^9` projects to ~200 GB. The kernel OOM-kills the process long before that.

**Why this is the second-worst**: There is no input validation. `argparse` accepts any integer for `n`. The CLI does not check `n <= some_reasonable_bound` (e.g., 10 million). A user who passes a large number by mistake (e.g., intending `--budget 999999999` but typing `n` instead) gets a silent kill with no diagnostic. Worse, the system may freeze or kill other processes before the kernel reaps this one.

For comparison, `n=100_000` succeeds in 2.6 s with 38 MB peak RSS, and `n=1_000_000` succeeds in 24 s with 198 MB peak RSS. So the threshold for disaster is somewhere around `n=10^7` to `n=10^8` on a typical laptop.

**Severity**: CRITICAL. Silent data loss / system instability.

### Worst UX #3: Corrupting a snapshot file crashes the CLI with a Python traceback

**Reproduction**:
```bash
$ echo "garbage}{not valid json" > /tmp/srs_corrupt/snap_<id>.json
# (or just corrupt latest.json)
$ python3 srs/cli.py --home /tmp/srs_corrupt recover
Traceback (most recent call last):
  File "/home/z/my-project/download/srs/cli.py", line 342, in <module>
    sys.exit(main())
  ...
  File "/home/z/my-project/download/srs/persistence.py", line 124, in load_latest
    meta = json.load(f)
           ^^^^^^^^^^^
  ...
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

**Why this is the third-worst**: Snapshots are JSON files on disk. Disk corruption, partial writes (power loss mid-write), concurrent writers, accidental user edits, or `git pull` conflicts can all produce invalid JSON. The persistence module's `load_latest` and `load_in_flight` call `json.load(f)` with **no try/except**, so any malformed JSON aborts the entire CLI with a raw Python traceback.

The R3.2 fix (advice hash mismatch) demonstrates that the team knows how to handle corruption gracefully — when the advice table's SHA-256 hash doesn't match, the code logs a warning and discards the advice instead of crashing. The same pattern should be applied to JSON parsing: catch `JSONDecodeError`, log a warning naming the corrupt file, treat it as if the snapshot didn't exist, and let the user continue. The infrastructure is there (the `list_snapshots` function already uses `try/except (json.JSONDecodeError, KeyError): continue`); it just wasn't applied to `load_latest` and `load_in_flight`.

Compounding the problem: the crash happens during `Runtime.__init__`, which means **every CLI command** that constructs a Runtime (`capabilities`, `snapshot`, `recover`, `execute`, `plan`) fails. A user with one corrupt snapshot cannot even run `srs capabilities` to inspect their state. They have to manually `rm` the corrupt file from the filesystem.

**Severity**: CRITICAL. One corrupt file bricks the entire CLI.

## 5. Performance Observations

All measurements taken on the sandbox host (Python 3.12.13, single-core).

| Operation | Wall time | Peak RSS | Notes |
|-----------|-----------|----------|-------|
| `cli.py self-test` (all 13 modules) | 125 ms | ~30 MB | Fast. The scary "advice hash mismatch" warning is printed during the persistence self-test's intentional tamper test — expected, but should be silenced or moved behind a `-v` flag. |
| `cli.py --home … bench` (full 5-section suite) | 1.40 s | ~40 MB | 30 trials per primitive. CV% ~20-30% indicates noisy timing — would benefit from more trials or warmup. |
| `cli.py --home … execute identify 64` (cold) | 80-110 ms (CLI startup) + 0.5-0.9 ms (execute) | ~30 MB | CLI startup dominates. The actual task execution is sub-millisecond. |
| `cli.py --home … execute identify 64` (warm, advice hit) | 80-110 ms (CLI startup) + 0.5-0.9 ms (execute) | ~30 MB | Advice hit makes `queries=0` but wall time is essentially unchanged because the task was already sub-millisecond. The "self-improvement" benefit is invisible at this scale. |
| `cli.py --home … execute identify 100000` | 2.6 s | 38 MB | Scales linearly in `n` (mostly the SHA-256 list materialisation). |
| `cli.py --home … execute identify 1000000` | 24 s | 198 MB | Linear extrapolation: `n=10^7` → ~4 minutes, 2 GB. `n=10^8` → ~40 minutes, 20 GB. `n=10^9` → OOM kill. |
| `cli.py --home … execute identify 999999999` | (killed) | (OOM) | Silent SIGKILL. No output. |
| 10 concurrent `execute identify 64 --persist` | ~0.5 s wall (parallel) | ~30 MB each | All 10 succeeded, no corruption, but left 9 orphaned snapshots (2.2 KB each = 22 KB total). At 10,000 runs, this would be 22 MB of orphans. |
| Python API: 5 tasks + persist + recover | 19 ms (total) | ~30 MB | Fast. But `capabilities.total_executions` reported 12 (counting primitive-runs, not task-runs) — misleading. |

**Key observations**:

1. **CLI startup dominates wall time** for small tasks. A user running `srs execute identify 64` pays ~80 ms of Python interpreter + import overhead for ~1 ms of actual work. For batch usage, the Python API is 80× faster (5 tasks in 19 ms vs 5×80 ms = 400 ms via CLI).

2. **The "self-improvement" feature has no measurable wall-time benefit** at typical scales. With advice: 0.5 ms. Without advice: 0.9 ms. The 0.4 ms difference is below timing noise (CV ~25%). The benchmark's claim that "second run = 0 queries" is true but the user-perceived benefit is invisible.

3. **Memory scales linearly in `n` with no upper bound**. The `hyps = [hashlib.sha256(...) for i in range(n)]` line in `cli.py:134` is the bottleneck. A streaming/generator-based approach or an `n <= 10_000_000` guard would prevent the OOM kill.

4. **Concurrency is safe but wasteful**. POSIX atomic writes to `latest.json` prevent corruption, but every `store_state()` call creates a new snapshot file (`snap_<hash>.json`) with a fresh hash. Old snapshots are never deleted. There is no `prune` or `gc` command. Over time, the home directory grows unboundedly.

## 6. Usability Score: 3 / 10

**Justification**:

- **Discoverability (1/3)**: `--help` is clean. `list-kinds` is helpful. But the very first command a curious user runs (`capabilities`) crashes. There is no "getting started" guide in the CLI; the README exists but is not surfaced.
- **Reliability (1/3)**: Three CRITICAL bugs (default_path missing, OOM on large n, JSON corruption crashes). The runtime is not robust to malformed input or partial writes.
- **Consistency (1/2)**: `list-kinds` (8 kinds) vs `execute` (5 kinds) is a glaring inconsistency. `plan verify` (soundness 0.03) vs `execute verify` (soundness 1.0) is another. The CLI says `--home` is optional but it is effectively required.
- **Error quality (0/2)**: 7 of 12 error scenarios produce unhelpful output (tracebacks, silent kills, nonsense values). Only the R5.6/R5.10 fixes demonstrate good error messages; the rest of the surface does not meet that bar.

**Total: 3/10.** Below the threshold for "usable by someone who hasn't read the source code."

## 7. Specific Improvements Required

The following are ordered by severity and impact.

### CRITICAL (blocks adoption)

1. **Define `persistence.default_path()`**. Add the missing function:
   ```python
   def default_path() -> Path:
       return Path.home() / ".srs" / "snapshots"
   ```
   This single fix unblocks `capabilities`, `snapshot`, `recover`, `execute`, `plan`, and `bench`. It is a one-line change. **This is the highest-priority fix in the entire v7.3 cycle.**

2. **Validate `n` before materialising the hypotheses list**. In `cmd_execute`, add:
   ```python
   if args.n < 1:
       print(f"Error: n must be >= 1, got {args.n}", file=sys.stderr); return 1
   if args.n > 1_000_000:
       print(f"Error: n={args.n} exceeds safe upper bound (1,000,000). "
             f"For larger n, use the Python API with a streaming hypotheses source.",
             file=sys.stderr); return 1
   ```
   The 1 M threshold corresponds to ~200 MB peak RSS, which is safe on any modern machine.

3. **Wrap all JSON loads in `persistence.py` with try/except**. In `load_latest`, `load_in_flight`, and `list_snapshots` (already done), catch `JSONDecodeError` and `KeyError`, log a warning naming the corrupt file, and return `None` (treat as missing). Example for `load_latest`:
   ```python
   try:
       with open(snap_path) as f:
           d = json.load(f)
   except (json.JSONDecodeError, OSError) as e:
       logger.warning("snapshot file %s is corrupt (%s); ignoring", snap_path, e)
       return None
   ```

### HIGH (degrades trust)

4. **Reconcile `list-kinds` with `execute`**. Either (a) add `amortize`, `optimize`, `store` to `execute`'s argparse `choices`, or (b) remove them from `TASK_AXIS` if they're not executable. Currently `plan amortize` works but `execute amortize` doesn't — a user following `list-kinds` output will hit argparse errors.

5. **Make the planner advice-aware per-hypotheses-set, not just per-table**. The planner currently treats `advice_available = bool(self.advice._table)` as a binary signal. If ANY advice exists, it reports `queries=0`. But advice is keyed by `(hypotheses_hash, target_idx)`, so for a new hypotheses set the advice won't apply. The planner should call `advice.lookup(hyps, target_idx)` (or at minimum check whether a matching key prefix exists) and report `queries=0` only on a real hit.

6. **Make `bench` respect `--home`**. The benchmark currently writes to a hardcoded `benchmark_results.json` in the package directory. Change it to `Path(args.home) / "benchmark_results.json"` (or to `cwd / "benchmark_results.json"` with a clear message). The current behaviour silently writes into the user's package install, which may be read-only.

7. **Implement snapshot pruning**. Add a `prune` subcommand (or auto-prune on `snapshot`) that keeps only the last N snapshots (default 10). The current unbounded growth will fill the disk over time.

8. **Make `recover` check for in-flight tasks even without a snapshot**. Currently `cmd_recover` returns "No snapshot found" if there's no snapshot, ignoring any `inflight_*.json` files. Move the `resume_interrupted()` check outside the `if rt.recover():` block:
   ```python
   rt = Runtime(home=args.home)
   recovered = rt.recover()
   inflight = rt.resume_interrupted()
   if not recovered and not inflight:
       print("No snapshot or interrupted task found"); return 1
   # ... report whatever was found
   ```

9. **Fix `execute verify` to actually verify**. Currently `execute verify 64` returns `verified=False, verification_calls=0` against a planned 5 calls. The V stage is effectively a no-op. Either implement real verification (the planner says 5 calls should be made) or remove `verify` from the execute choices until it's real.

### MEDIUM (degrades polish)

10. **Rename `capabilities.total_executions` to `total_primitive_runs`** (or compute it as the number of distinct task executions, which is `len(self.execution_history)`). The current name is misleading: 5 task executions report as `total_executions: 12`.

11. **Treat `correct=None` as "not applicable" in `success_rate`**. Verify tasks return `correct=None`; the current code counts them as failures (`if r.correct:` is falsy for None). Either exclude them from the denominator or count them as successes (since the task ran without error).

12. **Suppress the "advice hash mismatch" warning during `self-test`**. The persistence self-test intentionally tampers with advice to verify the hash check works. The resulting warning is scary for users running `srs self-test`. Either move the tamper test behind a `verbose` flag or wrap it in a `logging.disable(logger.warning)` context.

13. **Deduplicate the advice-hash-mismatch warning on `recover`**. The warning is printed twice because `Runtime.__init__` calls `load_latest` and then `cmd_recover` calls `rt.recover()` which calls `load_latest` again. Either skip the auto-load in `__init__` when a recover is imminent, or have `recover()` reuse the already-loaded snapshot.

14. **Validate `--budget`**. Reject `--budget < 0` with a clear error. Currently `--budget -1` produces nonsense cost estimates (`work_units: -1280`).

### LOW (nice-to-have)

15. **Add a `--resume` flag to `execute`**. Currently resuming an interrupted task requires the Python API (`rt.execute(task, resume=True)`). A `--resume <task_id>` CLI flag would surface this to users.

16. **Warn when snapshotting an empty runtime**. `srs snapshot` on a fresh home succeeds silently with no warning that there's nothing meaningful to snapshot. A "no executions to snapshot; snapshot will be empty" warning would help.

17. **Handle read-only home directories gracefully**. Currently `PermissionError` is uncaught and produces a traceback. Catch it and emit a friendly "home directory is not writable" message.

18. **Make `plan` and `execute` agree on `soundness_epsilon`**. `plan verify` reports `soundness_epsilon: 0.03125`; `execute verify 64` reports `soundness_epsilon: 1.0`. These should match (or `execute` should explain why the planned value wasn't achieved).

---

## 8. Conclusion

The SRS Runtime v7.2 ships with a **showstopper bug** (`default_path` undefined) that makes the CLI unusable for first-time adoption, plus two more CRITICAL bugs (OOM on large `n`, JSON corruption crashes) that affect production use. The 65/65 test suite passes only because every test passes `home=Path(tmpdir)` explicitly, bypassing the broken default. The CLI surface is internally inconsistent (`list-kinds` vs `execute` accept different kind sets), the planner's advice-awareness is too coarse (treats any-advice as advice-for-this-task), and `execute verify` is effectively a no-op.

The fixes are well-understood: define `default_path`, validate `n`, wrap JSON loads in try/except, reconcile kind lists, prune old snapshots, and make `bench` respect `--home`. None of these require architectural changes. The v7.3 cycle should focus on **operational readiness** rather than new features.

**Estimated effort to reach usability 7/10**: 2-3 days of focused engineering, addressing CRITICAL items 1-3 and HIGH items 4-9.
