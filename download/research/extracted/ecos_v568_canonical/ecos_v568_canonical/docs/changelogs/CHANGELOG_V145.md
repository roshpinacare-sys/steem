## Why This Phase

V144 completed the auth system with email verification and password reset. But two blockers remained:

1. **Email tokens went nowhere.** `emailVerificationService` could generate tokens, but without a real delivery provider, they only printed to stdout in dev mode. Production users could never receive verification emails.

2. **No public URL.** Design partner demos needed a live instance. Stripe webhooks needed a public HTTPS endpoint. First real users needed something to sign up on.

V145 removes both blockers in a single focused release. The system is now **genuinely production-deployable** in under 10 minutes.

## [V145-SMTP-01] `lib/smtpEmailProvider.js`

Real email delivery with **zero new npm dependencies** — pure Node.js built-ins only.

### Two providers in one file

**Resend API** (preferred — `RESEND_API_KEY` env var):
- Calls `api.resend.com/emails` via `node:https`
- Free tier: 3,000 emails/month
- Easiest setup: one env var

**SMTP** (fallback — `SMTP_DSN` env var):
- Pure Node.js TCP/TLS socket SMTP implementation
- Supports STARTTLS (port 587), direct TLS (port 465), plain (port 25)
- Compatible with: Postmark, SES, Mailgun, Gmail, any SMTP provider
- `SMTP_DSN=smtps://user:pass@smtp.provider.com:465`

### Email templates

Both `verify_email` and `reset_password` produce multipart MIME emails:
- Plain text + HTML versions in one message
- Token embedded as a `?token=...` query parameter in a link
- `ECOS_BASE_URL` env var controls the link domain
- `EMAIL_FROM` env var controls the sender address

### Server integration

At startup, if `RESEND_API_KEY` or `SMTP_DSN` is configured:
```javascript
emailVerificationService.setDeliverFn(smtpEmailProvider.deliver.bind(smtpEmailProvider));
```
If neither is set, startup logs one info message. No crash, no behavior change — dev stdout log continues to work.

## [V145-DEPLOY-01] Production Deployment Artifacts

### `.env.production`
Complete template with every env var documented:
- Tier labels: required / optional / required-for-payments / required-for-email
- Generation commands for secrets
- Examples for every SMTP provider

### `render.yaml`
One-click Render.com deployment:
- Web service (Node) + Postgres database pre-configured
- Health check path: `/api/v1/health`
- Auto-deploy on push to main
- `JWT_SECRET` auto-generated by Render

### `fly.toml`
Fly.io deployment configuration:
- Region selector (default: `iad` — US East)
- HTTP health check on `/api/v1/health`
- Auto-stop/start for cost savings

### `Dockerfile` — Health check added
```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \
  CMD node -e "require('http').get('http://localhost:3000/api/v1/health', ...)"
```
Used automatically by Docker, Render, Railway, Fly.io, ECS, and Kubernetes readiness probes.

### `scripts/smoke-live.js`
9-step smoke validation against any live ECOS URL:

| # | Check |
|---|-------|
| 1 | `GET /health` → 200 + `{status:'ok'}` |
| 2 | Health contains `version` field |
| 3 | `GET /chain/proof` → intact field present |
| 4 | `POST /auth/register` → 201 + accessToken |
| 5 | `POST /auth/login` → 200 + tokens |
| 6 | `GET /auth/me` with JWT → correct email |
| 7 | `GET /sovereign/stats` → totalInferences present |
| 8 | Unknown path → 404 |
| 9 | Responses include `X-Agent-Id` header |

Usage:
```bash
node scripts/smoke-live.js https://ecos-api.onrender.com
# or:
SMOKE_URL=https://ecos-api.fly.dev npm run smoke:live
```
