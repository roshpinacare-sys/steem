## 1 · POST-HOC ATTACK — rewrite `expected`/`hypothesis`, re-seal, no trace

**Mechanism.** `expected`/`hypothesis` live only in adaptations.json, which the machine rewrites and re-seals every learn step. `verifyStateIntegrity` recomputes sha256 of whatever payload is present — an attacker (engine bug, sibling process, anything running as user `z`) who edits the text and recomputes the hash leaves an internally-consistent store. `resolveAdaptedRoleFrom` (the consumption path) reads **only `toRole`** — it is structurally blind to prediction content, so a rewritten prediction changes nothing the executor would notice.

**The kill-shot sequencing.** `recordPrediction` (adaptations.mjs:306-329) reads `a.expected`/`a.hypothesis` **from the mutable store at fire time** and journals that text as the prediction of record. Therefore a rewrite performed **any time between now and the FIRST firing** is faithfully journaled as "what the machine predicted", and the journal — the artifact whose entire purpose is to make the prediction unforgeable — will vouch for the forgery. That window is **OPEN RIGHT NOW** (0 prediction.recorded rows exist; pending rewards = 0; firing still pending).

**What limits it (found, verified):**
1. **Git pins**: commits `e75195f` (15:48:02Z) and `c578f35` (16:29:47Z) both track state/adaptations.json; both contain the identical `expected`/`hypothesis` strings (`e75195f` content hash-sealed `e84abb0c…`, independently verified by L-1d at 15:44Z). A post-15:48 rewrite would diverge from both.
2. **Code-deterministic re-derivation** (strongest): the proposal text is generated by templates (adaptations.mjs:214-215) from exec-log evidence. Any reviewer with the git-tagged code + exec-log can recompute the original text — I did, and it matches. A rewritten store text that differs from the re-derived text is *provable* tampering, even against a re-sealed store.
3. **Cross-auditor pin**: l1b-causality.md (mtime 16:00Z) quotes the expected text; L-1b's pure replay was byte-identical.

**Residual exposure that remains:** all three pins live on the same filesystem/user as the attacker (git history is rewriteable via rebase; cognition-round files are plain files; re-derivation trusts git-tagged code, which the same actor edited this round). **No pin inside the engine is tamper-evident.** The engine-internal append-only journal — the thing R209 added precisely to close this — never receives the prediction text at proposal time.

**Verdict: VIABLE, window open, not eliminated.** Detection is possible only by out-of-engine comparison; the engine alone cannot prove its own prediction was not rewritten pre-fire.

## 2 · TIMING ATTACK — can prediction.at == exec.at, or invert?

Code order in `executeAs` (signer.mjs): partition (654) → per adapted partition: `recordPrediction` (671, `at` = `new Date().toISOString()` sampled at call) → `buildTx` (673) → `await broadcastTx` (675, network, 3 nodes × 8s timeout) → exec row appended with a **second** `new Date()` sample (677).

- Honest-path ordering is real: within one event-loop turn the prediction is appended **before** the tx is even built, and the exec row's `at` is sampled only after network I/O returns. Same-ms equality is empirically impossible on the ok path (network RTT) — but **nothing asserts it**: no code or artifact requires `exec.at > prediction.at`; the relation exists only by construction, and only inside one process's memory.
- Both timestamps are wall-clock (`new Date()`), not monotonic. An NTP step backward between the two samples can invert ordering. No proof uses CLOCK_MONOTONIC.
- **Journal-level ordering is UNPROVABLE from disk.** prediction rows go to events.jsonl; exec rows go to exec-log.jsonl — two different files, no shared sequence numbers, no cross-references, both churned by many writer modules. The only ordering evidence an external reviewer has is the `at` strings themselves (self-asserted by the same writer) and file mtimes (forgeable, constantly updated). "prediction_time < action_time" is currently **not provable for an external reviewer at all** — it is only *consistent* with the journal.
- What would make it provable: (a) reorder to `buildTx → recordPrediction(…, txid) → broadcast` — the txid (sha256 of serialized tx) is fully determined pre-broadcast (steemtx.mjs:249 uses deterministic RFC6979 low-s; ref-block comes from the already-fetched dgpoRes at signer.mjs:639-644, expiration from build-time clock) — then bind `PR.txid == E.txid`; (b) per-row hash chaining inside a SINGLE journal that carries both rows; (c) anchor the journal-head hash on-chain (the organism already posts weave custom_json checkpoints) — the chain's block timestamp is the only clock the machine does not control.

**Verdict: honest-path ordering holds by construction but is externally unverifiable; inversion/stamping is unguarded; no monotonic or cryptographic ordering proof exists.**
